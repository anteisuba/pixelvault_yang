# Scene · 调查 / 可行性 / 技术选型（research.md）

> 覆盖："XX 能不能做"、"A 方案还是 B 方案"、竞品调研、技术预研（spike）。产出是**拍板依据**，不是代码。当前会话完成，不要求固定模型。

## 场景自查（先从上下文和代码回答，仅询问实质缺口）

1. **核心问题一句话？判据是什么？**——什么样的结论算"可行"/"选 A"（成本上限、延迟要求、能力底线），先定判据再调查，避免调完还是拍不了板。
2. **时间盒与深度？**——快扫（<1h，结论±方向）/ 深调研（官方文档+竞品实测）/ 最小原型验证（spike 代码）。
3. **约束前提？**——预算（如 RunPod 月 $2-5 硬上限这类）、技术栈边界、直连优先原则、合规红线。
4. **输出形态？**——对话结论+图示 / 调研文档（**默认** `docs/references/research/<模块>/<中文主题>-YYYY-MM.md`，按模块分子目录，每模块一份「模块整理」；**文件名须中文**）/ 可跑原型。已有所属文档则更新；纯问答或短调查在对话交付，不强制新文档。
5. **拍板后去向？**——直接执行 / 存备用 / 判死。调研件完成使命后：稳定结论并进对应域的 `docs/references/` 文档，原件直接删（无归档目录，历史从 git 取）。

## 本场景工作流

1. 从请求确定判据；无法推断且影响结论时再询问 owner。
2. **官方一手资料**（WORKFLOW 联网核验优先级：官方 API 文档 > SDK > model card > 公告）；动向类可用本地 OpenCLI（twitter/hf/arxiv/reddit 适配器）。
3. 竞品实测（需要时）：可用浏览器工具实际走一遍竞品流程，截图留证。
4. 最小原型（需要时）：**spike 代码是丢弃式的**——放 scratchpad 或独立分支，绝不合入 main。
5. 产出：现状 → 可选方案对比（成本/能力/风险三列）→ **推荐方向和理由** → 待 owner 拍板的问题（选择框形式）。**调研正文写入 `docs/references/research/<模块>/`**，不要平铺在 `docs/references/` 根目录。
6. 未决取舍交 owner 确认；用户已授权调查后实施且契约明确时继续。仅跨会话交接使用 task packet；稳定结论回写现有 references。

## 必读清单

`references/product.md`（判断是否偏离双核北极星）· 相关 `references/domains/<域>.md` · 对话中的在飞约束（别重复调研，先查 memory；旧评审 `archive/reviews/` 已删 2026-08-07，需要时从 git 历史取）

## 禁改范围默认值

**仅调查请求不改产品代码**（发现无关 bug 报告，不顺手修）· spike 代码不进 main · 不因"调查顺利"跳过拍板直接开工。

## 验证标准

结论可拍板（判据逐条有答案）· 关键事实有官方出处链接 · 方案对比含成本与风险 · 推荐明确不骑墙。
