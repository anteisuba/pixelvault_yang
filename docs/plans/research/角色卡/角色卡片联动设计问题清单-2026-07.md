# 角色卡片（Cards）联动设计 — 问题清单与方向（2026-07）

> 状态：**设计问题文档，非实现授权、非已确认 page 规范**。  
> 核心矛盾：卡片功能骨架已较完整，但 **「如何与其它功能联动，而不是孤立卡库」** 尚未产品化收口。  
> 相关：`docs/references/product.md`、`project-map.md`、`domains/canvas.md`、`pages/node-canvas.md`；酒馆类工具对标见 `LoRA提示词与角色工具对标调研-2026-07.md`（**对角色卡更有关，对图像 LoRA 提示词次要**）。

## 0. 一句话

| 点             | 内容                                                                                                     |
| -------------- | -------------------------------------------------------------------------------------------------------- |
| **卡是什么**   | 可复用的 **创作身份/约束包**（角色一致性为核心；画风/声/景为旁系）                                       |
| **卡不是什么** | 不是第二个 Studio，不是第二个 LoRA 库，不是聊天产品                                                      |
| **设计卡死点** | 不是缺管理页 UI，而是 **卡 ↔ 画布 / Studio / LoRA / Assets / 视频** 的契约未写成「用户一句话能懂」的联动 |
| **建议态度**   | 先定 **联动契约与生命周期**，再开 Cards 域 UI 三方向；期间少做大改版                                     |

## 1. 现状事实（代码 + 产品文档）

### 1.1 产品定位（已有）

- Cards：**角色卡为核心**；画风 / 声音 / 背景卡为复用素材；配方卡不做独立管理页（`product.md`）。
- 一致性来自 **卡片 + 镜头规格 + 参考约束**，不靠单条 prompt（视频/画布分工）。
- VoiceCard **可绑** CharacterCard；画布链路设想：`Character → Voice → Script → Shot/Video`。
- project-map：卡域 **功能完整**；你想做的是 **「一个角色的多模态容器」+ 与文件夹/项目融合** —— 属跨域架构，不是只改 `/cards` 皮肤。

### 1.2 角色卡数据里已有（可联动的「钩子」）

`CharacterCardRecord` 等已包含例如：

| 字段/能力                                       | 联动潜力                                      |
| ----------------------------------------------- | --------------------------------------------- |
| `sourceImages` / `sourceImageEntries`（多视角） | → Studio 参考图、画布角色节点参考、一致性评分 |
| `characterPrompt` / `modelPrompts`              | → 出图/镜头身份段；**不是**本轮动作全文       |
| `attributes`                                    | → 结构化外貌，辅助生成与助手                  |
| `loras`                                         | → 与 LoRA 栈桥接（可选挂载推荐）              |
| `variants` / `parentId`                         | → 同角色多画风/多版本                         |
| `stabilityScore` / refine / score               | → 「这张生成像不像该卡」反馈环                |
| cardify（生成结果转卡）                         | → 从作品回流成身份                            |

StyleCard / BackgroundCard / VoiceCard 另有 service 与 Studio 上下文消费。

### 1.3 今日联动的「散点」

| 域           | 已有触点                                                                           | 缺口（用户感知）                                         |
| ------------ | ---------------------------------------------------------------------------------- | -------------------------------------------------------- |
| **Studio**   | context 挂 characters/styles；生成可带 `characterCardIds`；存 StyleCard / 卡片选择 | 「用卡生成」是否一等入口、用完是否回写卡                 |
| **画布**     | 角色/背景节点、音色、吞噬/卡匣叙事、与全局卡分类对齐的意图                         | **卡库 ↔ 节点** 是「实例化」还是「引用」；回写规则不清   |
| **LoRA**     | 卡上可挂 `loras` 字段                                                              | 与 Generate 挂载栈、Library「使用此 LoRA」未形成统一故事 |
| **Assets**   | 素材可进卡、可被参考                                                               | 文件夹 vs 卡 vs Project 三套聚合未融合                   |
| **Prompts**  | 配方/血缘                                                                          | 卡是否绑定默认 recipe 未产品化                           |
| **Gallery**  | 公开作品                                                                           | 卡是否公开、是否带「同人设再创作」未定                   |
| **视频脚本** | `characterCardId` 一致性模式                                                       | 与画布节点投影是否同一身份源                             |

**结论：** 不是没有联动代码，而是 **缺少一张「身份从哪里来、到哪里去、谁能改」的总图**，所以卡容易被用成「单独管理页」。

## 2. 设计目标：卡是「总线」，不是「孤岛」

### 2.1 推荐产品句（待 owner 改）

> **卡片 = 跨 Studio / 画布 / 资产 的可引用身份源。**  
> 生成与剪辑发生在工作台；卡负责 **记住是谁、长什么样、用什么声/画风、可选带什么 LoRA**，并在需要时 **被实例化进某一镜**。

### 2.2 三层模型（对齐你曾提过的聚合设想）

```text
L0  资产（Assets）     单次生成结果 / 上传文件（原子媒体）
L1  卡片（Cards）      身份聚合：多参考图 + 文案 + 可选声/LoRA/画风偏好
L2  项目/场景          多张卡 + 多条流水线（Project / 画布工程）
```

| 层  | 用户心智              | 错误设计                       |
| --- | --------------------- | ------------------------------ |
| L0  | 「这张图/这段视频」   | 强迫每张图都建卡               |
| L1  | 「这个角色/这种画风」 | 卡里塞完整分镜与生成按钮全家桶 |
| L2  | 「这一部短片/这一案」 | 卡库与项目完全无关             |

### 2.3 与酒馆/CAI 的正确关系

| 学                                   | 不学                                    |
| ------------------------------------ | --------------------------------------- |
| 身份字段化、稳定层 vs 本轮层、可带走 | 聊天主 UI、超长 Definition 当唯一编辑器 |
| 「设定可复用到很多局」               | 世界书第一期做全                        |

见 `LoRA提示词与角色工具对标调研-2026-07.md` —— **用于 Cards，不用于 LoRA tag 语法**。

## 3. 联动地图（设计时必填）

下列每条都要在未来 page/域文档里变成 **「入口 / 带什么状态 / 回写什么」**。

### 3.1 画布（最优先想清楚）

| 问题           | 选项（勿全选，先定默认）                                                                                                        |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 节点与卡的关系 | **A 引用**（节点存 `characterCardId`，媒体可覆盖） / **B 快照**（拖入时拷贝参考与 prompt） / **C 混合**（默认引用，锁定后快照） |
| 从卡到画布     | 卡库「用于当前工程」→ 生成/更新角色节点 + 可选绑 Voice                                                                          |
| 从画布到卡     | 「升格为卡」/ 回写新参考图 / 仅更新 prompt                                                                                      |
| 镜头/视频      | 收割时：卡的参考图是否自动进 Seedance `@Image`；音色是否随角色                                                                  |
| 与流水线 W1–W3 | 投影 ScriptDoc 时角色行是否 **必须** 绑已有卡或可内联新建                                                                       |

**建议默认（可驳）：C 混合——引用保证改卡能影响未锁定镜头；单镜可覆盖参考；「定妆通过」后可选锁定快照。**

### 3.2 Studio 图/视频/音频

| 模态          | 联动                                                                          |
| ------------- | ----------------------------------------------------------------------------- |
| Image         | 选角色卡 → 注入参考图 + 身份 prompt 段；生成后可「加入该卡参考」或 cardify    |
| Video（轻量） | 短片一致性模式已有 `characterCardId`；与画布长视频分工保持：Studio 轻、画布重 |
| Audio         | Voice 绑角色卡；试听/TTS 结果可进卡的声音位                                   |
| 3D            | 远期：定装图来自卡 → 3D → 多视角回写卡（现搁置）                              |

### 3.3 LoRA

| 联动      | 说明                                                                        |
| --------- | --------------------------------------------------------------------------- |
| 卡 → LoRA | 卡上 `loras` = **推荐挂载**，进入 Generate/画布时 **确认后** 进栈（不暗挂） |
| LoRA → 卡 | Library「用此 LoRA 创建/更新角色卡」可选；触发词写入卡的 identity 段        |
| 边界      | **出图执行仍在 Generate/画布**；卡页不复制整台 LoRA 工作台                  |

### 3.4 Assets / Project（**强烈建议联动；卡不是第二素材库**）

> 产品优先级里已有「资产化闭环（Assets / Prompts / Cards / Gallery）」；project-map 也写过 **角色收集容器 × 文件夹/卡融合**。  
> 结论：**应该联**，但是 **引用关系 + 筛选/钉选**，不是把 `/assets` 和 `/cards` 合成一张表。

#### 三层分工（再钉一次）

```text
L0  Assets（素材）   原子媒体：生成结果 / 上传 / 收藏 / 进文件夹
L1  Cards（身份）    从素材里「钉」出：谁、标准像、多视角、可选声
L2  Project / 画布   用哪些卡、拍哪几镜（素材仍可散落在 L0）
```

|                | Assets                   | Cards                        |
| -------------- | ------------------------ | ---------------------------- |
| 用户心智       | 「我有哪些图/视频/音频」 | 「这个角色/画风是谁」        |
| 粒度           | 每条 Generation / 上传   | 多条媒体 + 文案 + 约束的聚合 |
| 谁负责浏览海量 | ✅ 网格/文件夹/批量      | ❌ 不做第二套素材浏览器      |
| 谁负责身份一致 | ❌                       | ✅                           |

#### 该联的五条边（按价值）

| #   | 方向              | 用户一句话                      | 短中期怎么做                                                       | 中长期                                  |
| --- | ----------------- | ------------------------------- | ------------------------------------------------------------------ | --------------------------------------- |
| 1   | **素材 → 卡**     | 「这张图加入角色参考 / 建成卡」 | 详情/多选：加入卡源图、cardify、创建卡时从 Assets 选               | 同左 + 批量钉参考                       |
| 2   | **卡 → 素材**     | 「看这个角色相关的全部图」      | 卡详情「相关素材」→ Assets 筛选（tag / 来源 cardId / 深链）        | 虚拟「角色相册」视图                    |
| 3   | **素材作定妆源**  | 「从库里挑多视角做标准像」      | 建卡/编辑：`AssetSelectorDialog` 多选进 `sourceImages`             | 视角标签（front/side…）与素材元数据对齐 |
| 4   | **生成回流**      | 「这张像他，收进卡」            | 生成后：加入待审参考 / 询问写回（见 §5.3）                         | 一致性评分通过再进正式源图              |
| 5   | **文件夹 ↔ 角色** | 「这个文件夹就是 Alice」        | **不强制 1:1**；可选：文件夹备注/钉卡、或卡上「关联文件夹 id」深链 | 一角色一逻辑容器（仍可多文件夹）        |

#### 和 Seedance / 画布的关系

- 卡上的 `sourceImages` **本质上应是 Assets（或 R2 上的同一批媒体）的引用/拷贝 URL**，不是平行宇宙。
- 编译投喂 Seedance 时：卡只是 **选哪些 L0 素材进 `image_urls`** 的策划层（见 §10）。
- 画布节点覆盖图：也常常来自 **Assets 选择器**，与「从卡补图」并列。

#### 明确不要做（防 CRM 化）

| 禁                                    | 原因                                                    |
| ------------------------------------- | ------------------------------------------------------- |
| 强制「一卡 = 一物理文件夹」且迁移文件 | 破坏 Assets 双维组织（系统分类 × 项目树）；迁移贵、易丢 |
| 卡页复制整页 Assets 浏览器            | 双份网格、双份批量；维护炸                              |
| 每张素材必须绑卡才能用                | 海量 B-roll / 场景图不需要身份                          |
| Generation 表与 Card 表硬合并         | 域职责不同；用关联字段即可                              |

#### 与 Project 的边界

|      | Project（素材文件夹义）  | 画布工程 / 短片案          |
| ---- | ------------------------ | -------------------------- |
| 钉卡 | 可选：本项目常用角色集合 | 工程 cast：本片出场卡      |
| 素材 | 文件夹里的图视频         | 节点上的实例 / 锁定快照    |
| 关系 | 弱：方便找               | 强：生成与锁定权威（§9.1） |

**短中期推荐默认（可驳）：**  
① 建卡/加参考 **必须能从 Assets 选**；② 卡详情能 **跳到相关素材**；③ 生成结果 **可选写回卡**；④ **不做** 文件夹强制合并。  
这样卡是总线、Assets 仍是仓库——和 product「批量管理归 Assets、不塞回 Studio」一致。

### 3.5 Gallery / Prompts

| 联动    | 说明                                                |
| ------- | --------------------------------------------------- |
| Gallery | 后置：公开作品「同人设」是否暴露卡 id（隐私默认关） |
| Prompts | 卡可挂默认个人 recipe 链接；不把公共配方塞进卡管理  |

## 4. 用户旅程（用联动讲故事，而不是讲 CRUD）

### 旅程 A — 定妆到一镜（最小闭环）

```text
素材/生成图 → 创建角色卡（多视角）
    → Studio 或画布「用此卡」
    → 出设定图 / 镜头图（身份来自卡，动作来自本轮 prompt）
    → 可选：结果写回卡参考 / 一致性评分
```

### 旅程 B — 短片流水线（画布主线）

```text
卡库选 1–N 角色（+ 可选场景/画风卡）
    → 想法/剧本 → 投影节点（角色节点绑定卡）
    → 批量出素材 → 视频节点
    → 工程保存；卡仍在卡库供下一部复用
```

### 旅程 C — LoRA 角色

```text
Library 选 LoRA → 创建/绑定角色卡（触发词+样例图）
    → 画布/Generate 用卡出定妆
    → 再进镜头（卡提供视觉，LoRA 提供能力）
```

设计 Cards UI 时，**每一屏都应能回答：我现在在 A/B/C 的哪一步**，而不是「我在管理数据库行」。

## 9. §5.1 调查结论（无直接同类产品时的可迁移参照）

> **诚实前提：** 业界没有「PixelVault 式角色卡 + 画布 + Seedance」一体的现成竞品说明书。  
> 能参照的是三类**可迁移模式**，再压成我们自己的默认：  
> 1）**AI 影视一致性工作流**（reference sheet / 分镜锁定 / 换装新表）；  
> 2）**对话角色卡**（酒馆/CAI：永久人设 vs 本轮覆盖）；  
> 3）**视频模型真实 API 契约**（Seedance 只吃 `image_urls` + `@ImageN` 等，**不吃卡对象**）。

### 9.1 Q1 — 同一角色多镜：以卡为准还是以节点覆盖为准？锁定？

#### 业界在干什么（可迁移）

| 来源模式                  | 实际做法                                                       | 对我们的含义                           |
| ------------------------- | -------------------------------------------------------------- | -------------------------------------- |
| AI 短片 / Runway·Kling 类 | **每个镜头用参考图（或 Character ID）钉身份**；场景/动作按镜改 | 身份有「库里的标准像」，镜头侧可再钉图 |
| 换装 / 剧情服装变化       | **服装大变 = 新 reference sheet**，不是改一句 prompt           | 节点覆盖参考图是一等能力，不是 bug     |
| 酒馆 / CAI                | **角色 Definition 稳**；scenario / 用户消息本轮可偏            | 「卡 = 永久层」；「镜头 = 本轮层」     |
| 影视定妆                  | 定妆通过后 **look book 锁定**；单镜临时改妆不回写主 look       | 需要 **锁定 / 快照** 概念              |

#### 三种权威模型（产品选项）

| 模型                 | 行为                                                                  | 优点                              | 风险                              |
| -------------------- | --------------------------------------------------------------------- | --------------------------------- | --------------------------------- |
| **A 永远以卡为准**   | 每镜生成前从卡拉最新源图+身份 prompt                                  | 改一次卡，全片跟新                | 单镜试装/脏参考被全局冲掉；难排演 |
| **B 永远以节点为准** | 拖入时拷贝，之后与卡脱钩                                              | 单镜自由                          | 卡库形同虚设；同角色多镜易漂移    |
| **C 混合（推荐）**   | 默认 **引用卡**；节点可 **覆盖** 参考/本镜变体；**锁定** 后冻结为快照 | 改库影响未锁镜；定妆/成片镜不漂移 | 要讲清「引用 / 覆盖 / 锁定」三态  |

#### 推荐默认：**C 混合**

```text
卡（L1 身份源）
  │  引用 characterCardId
  ▼
角色节点 / 镜头角色槽
  ├─ 默认：读卡最新 sourceImages + 身份段
  ├─ 覆盖：本镜换参考图 / 换 variant / 临时妆造（不自动回写卡）
  └─ 锁定（定妆通过 / 成片通过）：快照当时 media + prompt 片段
        → 之后改卡 **不影响** 已锁镜
```

| 规则         | 建议                                                                                      |
| ------------ | ----------------------------------------------------------------------------------------- |
| **默认权威** | 未锁定 → **卡赢**（节点空槽从卡补）                                                       |
| **覆盖权威** | 节点显式填了参考 / 选了 variant → **节点赢**（仅该镜）                                    |
| **锁定权威** | 锁定后 → **快照赢**（卡与节点再改都不动已锁 payload）                                     |
| **锁什么**   | 至少：`image_urls` 将用的图 URL 列表、选用的 variantId、身份 prompt 片段、可选 voice 绑定 |
| **何时锁**   | 用户点「定妆通过 / 锁定此镜」；或成片提交成功后可选自动锁（默认 **手动** 更安全）         |
| **解锁**     | 明确二次确认；解锁后回到「引用卡 + 可覆盖」                                               |
| **UI 话术**  | 避免工程师词「权威」；用 **「跟随角色卡 / 本镜覆盖 / 已锁定」**                           |

**不要做成：** 静默「永远最新卡」覆盖用户已调好的一镜（会毁掉排演信任）。

### 9.2 Q2 — 卡是否允许没有源图（纯文案卡）？

#### 分层答案（按消费端，不是一句 yes/no）

| 消费端                                   | 纯文案卡够不够 | 原因                                                    |
| ---------------------------------------- | -------------- | ------------------------------------------------------- |
| **对话/剧本/助手**（身份说明、台词性格） | 可以           | 模型吃文本；酒馆类产品本就如此                          |
| **文生图（无参考）**                     | 勉强           | 仅靠 `characterPrompt`；一致性弱，像「提示词收藏」      |
| **图生图 / IP-Adapter 类**               | **不够**       | 要图                                                    |
| **Seedance Reference / 多数视频身份锁**  | **不够**       | API 身份主要靠 **`image_urls` + `@ImageN`**，不是卡字段 |
| **一致性评分 / refine**                  | **不够**       | 要对着视觉源                                            |

#### 本仓库现状（事实）

- `CreateCharacterCardSchema`：**`sourceImages` 最少 1 张**（创建即强制有图）。
- 这与「视频/多镜一致性」主战场一致，不是历史偶然。

#### 业界对照

| 产品类型                             | 源图要求                                          |
| ------------------------------------ | ------------------------------------------------- |
| 酒馆 / CAI                           | 头像可选；**核心是文本 Definition**               |
| Runway / Kling / Seedance 一致性视频 | **参考图（或多视角 sheet）是身份锁的主输入**      |
| AI 影视实践                          | costume 变了还要 **新 sheet**，说明图不是装饰字段 |

#### 推荐默认

| 层级                           | 规则                                                                                          |
| ------------------------------ | --------------------------------------------------------------------------------------------- |
| **CharacterCard 产品主路径**   | **创建必须 ≥1 张源图**（维持现状）                                                            |
| **「视频可投喂 / 画布 cast」** | 至少 1 张 **可作身份锁的静帧**（脸/全身清晰优先）；多视角更好                                 |
| **纯文案**                     | **不要叫角色卡主类型**；可降级为：草稿笔记、剧本角色行、未来「文本人设草稿 → 再出定妆图建卡」 |
| **Voice-only**                 | 走 VoiceCard；可 **绑** 角色卡，但不替代源图                                                  |
| **例外若以后要做**             | `status=DRAFT` 且 **禁止** 进入 Seedance 参考收割；UI 标明「缺视觉，无法锁脸」                |

**一句话：**  
卡可以有很多文案，但 **「能当跨镜身份源」的卡必须带图**；纯文案最多是草稿层，不是 Seedance 可吃的身份。

### 9.3 Q3 — variants：用户心智是「换装」还是「分叉角色」？

#### 业界在干什么

| 模式                      | 典型说法                                            | 行为                                                        |
| ------------------------- | --------------------------------------------------- | ----------------------------------------------------------- |
| **换装 / 造型变体（主）** | Runway：同一 face ref → 不同 outfit；电商 lookbook  | **同一人**，服装/场景造型变；常 **新参考图** 进该造型的镜头 |
| **分镜用不同 sheet**      | 剧情中段换装 → **新 reference sheet**               | 不是改同一 sheet 上的一行字                                 |
| **画风分叉**              | 本仓 `variantLabel` 示例：Anime / Realistic / Chibi | 同一 identity 的 **渲染方言**，接近分叉但仍「是 TA」        |
| **真分叉角色**            | 双胞胎、平行宇宙、年龄差极大                        | 更像 **新卡 + 可选 parent 血缘**，不是日常 variant          |

#### 本仓库字段暗示

- `parentId` + `variantLabel` + `variants[]`：已是 **一父多子** 结构。
- 标签示例偏 **画风/媒介**（Anime、3D），不是「战斗服 / 便装」专用——但产品可两者兼容。

#### 推荐默认：**主心智 =「同一角色的造型/画风模式」；真分叉是显式动作**

```text
角色（根卡）= 谁
  ├─ variant「便装」     → 换装（默认）
  ├─ variant「战斗服」   → 换装
  ├─ variant「动画风」   → 画风模式
  └─ 「另存为新角色」    → 真分叉（新根卡，可记 derivedFrom）
```

| 维度        | 换装 / 模式（默认 variant）      | 真分叉                               |
| ----------- | -------------------------------- | ------------------------------------ |
| 用户一句话  | 「还是她，今天换这身」           | 「另一个角色，只是长得像」           |
| 身份评分    | 对着 **同一 identity** 评        | 独立评分                             |
| 改根卡外貌  | 可提示「是否同步到各 variant」   | 不同步                               |
| 进 Seedance | 选中的 variant 的源图进 `@Image` | 另一套 `@Image`                      |
| 命名        | 便装 / 校服 / 写实 / 三视图包    | 新名字，不进 variants 列表当「衣服」 |

**UI 默认文案建议：**

- 主按钮：**「添加造型 / 版本」**（不要一上来写「分叉」）
- 高级：**「另存为独立角色」**

**和 Q1 的衔接：**  
多镜换装 = 该镜选用 **对应 variant**（或节点覆盖图），**不是**改根卡唯一源图硬扛全片。

## 10. 如何把「卡」投喂给 Seedance（关键：卡不是模型 token）

### 10.1 硬事实（你的判断是对的）

| 事实                                                                      | 含义                                                              |
| ------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| Seedance Reference **没有** `characterCardId` / 卡 JSON 字段              | 模型 **不理解**「这是一张角色卡」                                 |
| 真实输入只有：`prompt` + `image_urls[]` + `video_urls[]` + `audio_urls[]` | 身份靠 **像素参考 + `@ImageN` 绑定**                              |
| prompt 里写长段外貌且与图冲突                                             | 业界共识：**脸会漂**；应 **瘦 prompt，胖参考**                    |
| 本仓路径已是 harvest 图 → `@名→@ImageN` + legend（见画布调研）            | 缺的是 **「从卡编译出这批图/句」** 的产品契约，不是再发明模型 API |

**结论：**  
卡是 **产品侧身份总线**；投喂 Seedance 时必须经过 **`compileCardForSeedance`（逻辑名）→ 原始媒体 + 短指令**。  
**永远不要**把整张卡当一个 token 塞进 prompt 指望模型「读懂卡」。

### 10.2 编译流水线（推荐产品契约）

```text
用户：某视频节点 + 绑定角色卡（或节点覆盖 / 锁定快照）
                    │
                    ▼
          resolveIdentityPayload(镜)
          ├─ 若已锁定 → 用快照 media + 身份片段
          ├─ 若节点覆盖 → 用节点图 +（可选）卡的 voice
          └─ 否则 → 用卡（或所选 variant）的源图排序结果
                    │
                    ▼
          compileForSeedance(identity, scene, motion, voice?)
                    │
                    ├─ image_urls:  排序后的静帧 URL（cap≤9 全图预算内）
                    ├─ video_urls:  运动/运镜参考（来自视频节点，不是卡本体）
                    ├─ audio_urls:  可选；VoiceCard / 台词轨
                    └─ prompt:      legend + 动作/镜头（身份描写极薄）
                    │
                    ▼
          fal …/seedance-2.0/…/reference-to-video
```

### 10.3 卡字段 → Seedance 字段映射

| 卡上有什么                         | 是否进 Seedance    | 怎么进                                                    |
| ---------------------------------- | ------------------ | --------------------------------------------------------- |
| `sourceImages` / entries（多视角） | **主身份输入**     | 进 `image_urls`；prompt：`@Image1 is the character…`      |
| `referenceImages`（精选参考）      | 优先于杂乱源图     | 排序时加权                                                |
| `characterPrompt` / attributes     | **薄注入或不注入** | 最多短句「保持与参考一致」；**禁止**把整段人设当主 prompt |
| `modelPrompts`                     | 一般 **不**进视频  | 那是出图 family 方言                                      |
| `loras`                            | **不**进 Seedance  | Seedance 不吃 Civitai LoRA；仅出图链路                    |
| `variants`                         | 间接               | 先解析「当前用哪个 variant」再取其图                      |
| Voice 绑定                         | 可选               | → `audio_urls` 或口型相关音频槽                           |
| 卡 id / 名 / tags / JSON           | **不进模型**       | 仅产品侧追溯、legend 人类可读名可进 prompt 前缀           |

### 10.4 源图排序（投喂质量 > 数量）

在全视频节点 **总图 cap≤9** 下，建议角色相关优先级（可调）：

1. 锁定快照指定图
2. 本镜节点覆盖图
3. variant 精选 / `referenceImages`
4. `front` / `three_quarter` 源图
5. `side` / `detail`
6. 其余源图

**多角色一镜：** 每角色 1–2 张脸/半身，留槽给场景与关键帧；prompt 里 **分别** `@Image1=Alice` `@Image2=Bob`。

### 10.5 Prompt 模板（身份锁，不是读卡）

**推荐形态（导演指令 + 绑定）：**

```text
@Image1 is Character A (face and outfit). @Image2 is the environment.
A walks toward camera, subtle smile. Match lighting to @Image2.
Camera: slow dolly-in. 24fps cinematic.
```

**反模式：**

```text
[CharacterCard]
name: Alice
attributes: { hair: ..., eyes: ... }
sourceImages: [...]
characterPrompt: (200 字外貌)
...整段 JSON...
```

模型不会「解析卡片协议」；多余外貌词还会和 `@Image` **打架**。

业界可迁移提示（Seedance 文档/教程共性）：

- `@Image` = **Identity Lock（常量）**
- `@Video` = 运动/运镜
- 文本 = 动作与调度
- 参考图清晰、少水印；身份相关 tag **靠前**

### 10.6 与现有画布路径的对齐

| 已有                     | 卡接入时只加什么                                                               |
| ------------------------ | ------------------------------------------------------------------------------ |
| 节点 harvest 上游图/视频 | **角色卡编译结果**作为图源之一（与角色节点等价或写入角色节点）                 |
| `@名 → @ImageN` + legend | 卡显示名可当 `@名` 的人类侧；发出仍是 `@ImageN`                                |
| `requiresReferenceImage` | 无图卡 **不得** 静默提交；UI 引导「先定妆出图」                                |
| 预览「查看发送内容」     | 必须能看到 **编译后的 URL 列表 + 最终 prompt**，让用户确认「模型实际吃到什么」 |

### 10.7 能力边界（产品话术）

| 可承诺                                        | 不可承诺                              |
| --------------------------------------------- | ------------------------------------- |
| 把卡 **编译** 成 Seedance 能吃的参考图+绑定句 | Seedance「认识」角色卡对象            |
| 多镜同一套编译规则 + 锁定后稳定               | 100% 脸不漂、换装不漂                 |
| 换装用 variant/新 sheet 提高成功率            | 只靠改 `characterPrompt` 完成换装视频 |
| 无图卡用于剧本/草稿                           | 无图卡直接高质量视频身份锁            |

### 10.8 最小实现切片（有授权后再做）

1. **纯函数** `resolveCardVisualRefs(card | variant | override | lock) → URL[]`
2. **纯函数** `buildSeedanceIdentityPrompt({ refs, actionPrompt }) → string`（瘦身份）
3. 画布：角色绑定卡 → 收割时合并进现有 harvest
4. 预览：展示编译结果
5. 门禁：无图 → 阻断 Seedance 身份路径并提示定妆

**不**需要 Seedance 官方支持「卡」；只需要我们当好 **compiler**。

## 11. 调查来源（§9–10）

| 类型          | 来源                                                                    | 用到的结论                                        |

| AI 影视一致性 | TMFF 等：costume change → **新 reference sheet**                        | 换装 ≠ 改旧 sheet；支撑 Q1 覆盖 + Q3 造型 variant |
