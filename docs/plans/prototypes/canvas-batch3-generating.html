§1

提案：一个器件，遮罩只在有东西要遮时才上

按 §17.3 定下的判据 —— running 是「唯一带动效的那一档」，它要说清「在跑、时长未知」， 但不该抢注意力。

器件恒定一条不定式扫光条 + 「生成中」文案，四个落点全用它
遮罩看情况底下有内容要遮（已有媒体 / 深窗）才上白遮罩；空态没东西可遮，就不上

为什么选条而不是扫光。生成动辄 30s 以上，而扫光是「表面在动」—— 在 82% 白遮罩上它非常弱（渐变峰值只有墨色 10%），长任务里用户会怀疑是不是卡住了。 条是「有个进程在推进」，同样不承诺时长，但明确得多。

还有一条更要紧的：它让上传和生成落到同一条轴上 —— 有真实百分比 = 确定式条（宽度随进度），拿不到百分比 = 不定式条（固定宽度来回扫）。 同一个器件，两种行为，用户一眼分得清哪个能预估完成时间。 现在上传只有文字里的百分比 + 一个 sr-only 的 progressbar，视觉上根本没有条。
⚠ 遮罩统一到 82%（图片族那一档）而不是 70%：70% 下深窗透上来太多， 文字压在半黑半白上。82% 两种底下都是稳定的浅面。 blur 同时统一到 2px（现在 C/D 是 Tailwind 的 4px）。
§2

要你拍板的两件

① 器件选哪个？ 我建议 不定式扫光条（上面 A′–D′ 那版）。 若你更想要最安静的一档，也可以反过来统一到扫光（A 那版）铺到四处 —— 代价是长任务反馈很弱。
② 顺带把「上传中」也纳入同一条轴吗？ 上传有真实百分比（走 XHR 字节数），今天却只在文案里给数字、视觉上没有条。 纳入后：上传 = 确定式条 + 数字，生成 = 不定式条，一眼分得清。 我建议 纳入，但这超出了 #14 记的范围，所以问一句。 不纳入的话上传保持现状（扫光 + 文字百分比），与生成分家。
