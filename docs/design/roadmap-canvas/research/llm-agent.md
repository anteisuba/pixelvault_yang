### 共同能力（合并成一条路由的公共底座）

1. OpenAI 兼容或近似的 chat/messages + SSE 流式（Anthropic 事件名不同，仓库已各写一份 parser）。
2. 函数/工具调用 + JSON Schema 结构化输出 —— 五家全有，是「五动词」工具层唯一可以统一的契约。
3. 推理档位（effort / thinking_level / reasoning_effort）—— 五家都有旋钮，只是 Fable 5.1 与 grok-4.6 关不掉。
4. 图像输入 —— 除 `deepseek-v4-pro` 外全部支持（DeepSeek 要切 flash 档）。
5. Prompt/context caching —— 五家全有，但 DeepSeek 自动、OpenAI 自动、Gemini 与 Anthropic 要显式标记。
6. 长上下文（500k–1.05M）+ 大输出预算。

### 各家独有能力（只能做成「能力探测 + 降级」，不能进公共层）

- **OpenAI**：`file_search` 向量库、`tool_search` 按需加载工具、Conversations API 永久会话对象、`sources` 全量来源清单。
- **Gemini**：Google Search grounding 自带 `searchEntryPoint` 与法定展示要求、URL context（≤20 URL/34MB）、视频与音频原生输入、thought summaries。
- **Grok**：X Search（社媒一手源）、Collections Search、inline markdown 引用。
- **DeepSeek**：峰谷两价（谷时半价，UTC 非 01–04/06–10 工作日）、cache 命中价低两个数量级、384K 输出。
- **Claude**：memory 工具（客户端落盘，可映射到本项目 Prisma）、context editing + 服务端 compaction、web search dynamic filtering（结果先过代码过滤再进上下文）、强制引用与 `cited_text`、strict tool use。

## B · 搜索能力设计（5 条可落地改进）

行业做法对照：OpenAI Deep Research 明确把流程拆成「澄清 → 改写 → 执行」，API 版把前两步交给调用方，靠 `max_tool_calls` 控成本（https://developers.openai.com/api/docs/guides/deep-research）；Perplexity 分成 Sonar（带引用的答案）与 Search API（纯 `results[]`，带 `search_domain_filter` ≤20 域、`search_recency_filter`、`search_context_size`、`max_tokens_per_page`，https://docs.perplexity.ai/api-reference/search-post）；Anthropic 把「过滤」放进代码执行再进上下文；Gemini 把引用做成字符区间锚定。

1. **把「查证」的一次 Serper 打法换成分档的 context size（自建，改动小）** —— 仓库 `WEB_SEARCH` 只有 `defaultNumResults: 6` 一个旋钮，而 OpenAI/Perplexity 都把「取多少正文」和「取几条」分开。按 §9.1 的 `questionType` 分三档正文预算（`fact_lookup` 低 / `style_technique` 高），Serper credit 不变但注入 token 降一半。
2. **来源白/黑名单下沉到 provider 原生参数（接官方内置搜索）** —— §9.3 的 `ProjectRule.sourceAllow/Deny` 目前只能在自建管线里过滤；OpenAI（各 100 域）、Anthropic（allowed/blocked 二选一）、Grok（各 ≤5 域）都有原生域名过滤。当路由落在这三家且用户开了白名单，直接用内置搜索 + 原生过滤，省掉 Serper credit，且过滤发生在检索侧而不是结果侧。
3. **引用锚定改成区间锚（自建，需要契约变更）** —— 现在证据卡只有 `title/url/snippet`，结论那一句与证据之间没有可验证的对应关系。Gemini 的 `start_index/end_index` 与 Anthropic 的 `cited_text`（≤150 字、不计 token）都是把引用锚到**正文片段**。建议 `AssistantOperatorEvidenceSchema` 加 `citedText`，由归纳那一次结构化输出必须逐句给出所引片段 —— 这也是治「结论那一句是编的」最便宜的闸。
4. **去重与印证引入「同源家族」判定（自建）** —— `corroboration` 现在按源个数算，但多家媒体转载同一篇稿会造成循环印证假象。加一条：同 registrable domain、或 snippet 相似度超阈值的，算一个印证单位；`RESEARCH_SOURCE_META.authorityRank` 在家族内只留最高的那条。
5. **深研档：一次澄清 + 有上限的多轮（自建，接 OpenAI 模式）** —— 现在 `maxRefetchRounds: 1` 是死代码分支。按 Deep Research 的三步法，把「澄清」接到已有的问题卡（一次只问一个），改写后允许 2–3 轮扩检，硬上限用 `max_tool_calls` 式的总调用数而不是墙钟（`totalTimeoutMs: 25_000` 对深研档必然踩满）。⚠ 深研档必须走 background + 轮询，不能塞进 `maxDuration = 60` 的那条路由。

## C · 助手体验对齐（8 条差距与建议）

对照产品：ChatGPT memory（https://help.openai.com/en/articles/8590148-memory-faq）· Claude 记忆与聊天检索（https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context）· 隐身对话（https://support.claude.com/en/articles/12260368-use-incognito-chats）· Anthropic 团队记忆（https://www.anthropic.com/news/memory）。

1. **记忆写入时机**：Claude 是「聊天进行中按主题存」，不是会话结束后总结；仓库 §7.5 是 `done` 帧前结账一次。建议保留每轮结账，但对「用户明确说的偏好/事实」即时写入上下文卡草稿，别等轮末压缩 —— 压缩会把「下周三截稿」这类硬事实磨成模糊句。
2. **记忆可见可编**：ChatGPT 有 memory summary 可逐条编辑并显示「2 小时前更新」，Claude 可在设置里按主题查看/删除。仓库已有「改」入口（§7.7）但只作用于**本轮**结论块，缺一个跨轮的「助手记住的全部」总览页。建议在设置弹层加一页，复用 `rounds` + `ContextCard`。
3. **来源可溯的「为什么这么答」**：ChatGPT 的书本图标会列出本次回答用到的 custom instructions / 过往对话 / 文件 / 记忆。仓库的证据 chip 只覆盖检索证据，不覆盖「哪张上下文卡、哪条项目规则参与了这次回答」。建议 `done` 帧补 `contextUsed` 数组，渲染成一行折叠的来源条。
4. **敏感类目默认不记**：Claude 默认排除健康/宗教/政治等主题记忆，需用户显式开启。仓库 §8 的上下文卡没有类目黑名单。建议在 `propose_context_card` 服务端加一层类目拒绝（不是 prompt 约束），与「服务端不落库」那条一起构成双闸。
5. **隐身/临时模式**：ChatGPT Temporary Chat 与 Claude 隐身对话都是「不读记忆也不写记忆」的完整一档。仓库只有 `RESEARCH_MODES.off`（管联网）没有管记忆的开关。建议加一个会话级 `ephemeral` 标记：不注入 `rounds`、不结账、不提议上下文卡。
6. **思考过程展示**：Gemini 给 `thinking_summaries: "auto"` 的摘要（非原始思维链），Anthropic 把 `thinking_delta` 与 `text_delta` 分开。仓库 §3.6 只有「五个动词各一句」的加载态，而 `llm-text.service.ts` 明确丢弃 `thinking_delta`。建议：仅对支持**摘要**的家（Gemini）渲染一行可折叠的思考摘要，⛔ 不要去展示 Fable 5.1 的原始 thinking（官方默认 `display: "omitted"`，且展示原始链是把模型的草稿念给用户听）。
7. **分析看图/看页/看视频的入口统一**：Gemini URL context 一次可吃 20 个 URL/34MB 且支持 PDF 与图片，Anthropic 有独立 `web_fetch`，仓库 `URL_READER.maxUrlsPerTurn: 3` 且只走 Jina 文本。建议把「读网页」做成能力探测：落在 Gemini 路由时直接用 URL context（拿得到 PDF 与图），其余家回落 Jina —— 这是「看」这一组现在最明显的能力落差。
8. **反问澄清与撤销**：仓库已有「一次只问一个」的问题卡（§3.4）和「改组必须带 `inverse`」（§10），这两条比多数产品做得更硬，**不要动**。差距在于：澄清目前只发生在动手前，而 Deep Research 的澄清是发生在**检索改写前**。建议把 §9.1 的「改写」那一步允许吐一次澄清问题（复用问题卡），条件是 `questionType` 判为 `general` 且主体词歧义 —— 「无限大 时夜」那类踩空正是缺这一问。

未核实项：Gemini 3.8 Flash / 3.5 Flash-Lite 的具体上下文与输出 token 上限（官方 models 页只给描述，未列数值）；xAI 与 DeepSeek 的速率限制形态；OpenAI deep research 页当前仍列 `o3-deep-research` / `o4-mini-deep-research`，与 GPT-6/5.6 代次是否对齐未核实。
