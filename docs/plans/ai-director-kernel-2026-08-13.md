### ✅ C1 路由抢夺已修（2026-08-21，199 测绿 + 真机复验）

**根因确证（推翻了我列的三个候选）**：不是能力闸没抛、不是 Gemini 侧失败被吞、不是没走到视觉线——**视频真的挂上去了、Gemini 真的采了 101,923 个 VIDEO token**。坏的是**两条线同时认领同一条 URL**：检索线把 YouTube 页读回一句 `401 Unauthorized`（Jina 返 HTTP 200、正文里写着 401，所以回执如实记 `ok`），模型据此宣布「后台拿不到这个视频」，转去背记忆，还给它挂了 `[1]`。
⭐ **决定性对照组**（同机同 key 同型号同视频，唯一差别是那条 401 证据在不在）：有证据→**19:13（错）**；无证据→**18:41（对）**。

**修法：一条 URL 只能被一条线认领**（`VIDEO_LINK_OWNER_LINE`，穷举 Record 无兜底，新增 kind 必须当场声明归属）：

| kind                                 | 归属       | 行为                                                         |
| ------------------------------------ | ---------- | ------------------------------------------------------------ |
| youtube / video-file                 | **视觉线** | 注入视频引用；检索线不得 url_reader                          |
| platform-page（B站/X/抖音）          | **检索线** | 不解流（边界 16），元数据卡 + 上传引导，URL 仍进 `plan.urls` |
| web（含认不出 id 的 YouTube 频道页） | **检索线** | url_reader 照读                                              |

另加①b：链接全被视觉线接走且剩余文本没点名外部主语时**不打源**（避免拿「这个视频有多长」去 Serper 搜回一堆无关页）。

**设计席补的一处（agent 无权改）**：`RESEARCH_EVIDENCE_DIRECTIVE` 原文说「具体数字只能来自证据或声明未知」——这让模型**在规则上无法说出它在附件视频里亲眼看到的时长**，与 §4.1 把 `observation` 当一等 basis 直接冲突。已补两条：①允许「本轮附件中直接观察到的」作为第三种来源（要报出句柄如 "video #1"），并明写**「你对某作品的记忆永远不算来源」**；②**「读网页失败」≠「附件不可用」**——页面读不了就说页面读不了，不许由此宣布附件视频不可用、更不许拿记忆顶上。

**真机复验（同一道题）**：

- ✅ 日志 `Research skipped by planner {reason: "video link belongs to the vision line — nothing left to search"}`，回执 `null` —— **抢夺消失**。
- ✅ **视频分析确认通着**：追问「能看到画面吗」→ 逐秒描述开头（3Blue1Brown 蓝棕虹膜 logo · π 卡通角色 · 28×28 像素网格里的手写「3」），帧级细节记忆编不出来。
- ⚠ **但时长仍答 19:13**。判读：**时长是元数据问题不是画面问题**——视觉模型按帧采样，看得见画面却数不准总长；同一套设置 agent 探针得 18:41、本轮得 19:13，**是模型侧方差不是我们的 bug**。
  - **候选修法（未做，需拍板）**：时长/发布日/标题这类元数据不该指望视觉模型数出来，应在挂视频时**一并取元数据注入**（YouTube oEmbed 免 key 可取时长），让模型有 `source` 可引。

⚠ **本节原诊断（「注入了计数级摘要，缺 LoRA 栈明细」）是错的**。实测：

**三条设计约束（都是踩过或差点踩的）**：

1. **放用户提示不放系统提示**。块里含用户自己写的提示词/负面提示词，放进系统提示等于给用户可控文本系统级权威。放用户提示同样满足协议里那句「attached context 里可见的算已知」，且前置 + 预留预算后不会被上下文压缩截掉。
2. ⛔ **规格必须标成「当前表单值」，不能冒充成「这批用的参数」**。该批实际参数在 `snapshot` 里，而列表接口的 select **不返回它**；表单上的是实时值，用户出图后拖一下滑杆就变。说成「这批用的」就是喂谎。

- EvidenceItem 带 `retrievedAt` + `sourceTier: 'official' | 'community' | 'social'`（UI 露层级：「官方文档说的」≠「推上有人说」）。
- 🔬 **证据形态要分「文本」和「已结构化标签」两种**（切片 0 实测追加）。萌百 `prop=categories`、danbooru 共现 tag、Fandom infobox 字段**本身就是结构化标签，不需要再过一次 LLM 提取**——长离的「粉发 · 挑染 · 金瞳 · 下双马尾 · 开胸高领衫 · 黑色过膝袜」是分类名直出，可以直接进提示词。**少一次提取就少一处幻觉面**，而幻觉恰恰就发生在这道题上（两臂都答错发色）。所以 `kind` 除了 `'text' | 'image'` 还要有 `'tags'`：载荷是字符串数组 + 出处，渲染成 chip 而不是引文段落。

- ResearchRun 即缓存：同问题近期查过直接复用带戳旧证据（TTL 按源层：social 短、文档长），标注「查于 X 小时前」。

#### 3.3.1 🔬 MediaWiki 按站能力表（切片 0 实测，2026-08-18）

原写法「一个连接器吃全族」**只在传输层成立**。实测每站可用的 prop 模块不同，连接器必须按站降级，不能只写一条取正文的路：

| 站          | `prop=extracts`          | `prop=revisions`（wikitext） | `action=parse`         | 取正文走哪条                    |
| ----------- | ------------------------ | ---------------------------- | ---------------------- | ------------------------------- |
| 维基百科 zh | ✅ 4563 字               | ✅ 38882 字                  | ✅                     | extracts                        |
| 萌娘百科    | ✅ 2775 字               | ❌ `action-notallowed`       | ❌ `action-notallowed` | extracts（**拿不到 wikitext**） |
| Fandom      | ❌ **未装 TextExtracts** | ✅ 2521 字                   | ✅                     | revisions / parse               |
| ~~wiki.gg~~ | ❌ 401                   | ❌ 401                       | ❌ 401                 | **整站不可达，不进首版**        |

**萌百是按 API 模块白名单拦，不是按 UA 或速率拦**（四种 UA 全 200；12 并发全 200，最慢 260ms；礼仪式 UA 即可，不必伪装浏览器）：

| 模块                                                | 萌百         | 连接器用途                                            |
| --------------------------------------------------- | ------------ | ----------------------------------------------------- |
| `action=opensearch`                                 | ✅           | 角色名 → 页名                                         |
| `action=query&generator=search`                     | ✅           | 全文搜索                                              |
| `action=query&list=search`                          | ❌           | ⚠ **标准写法反而被封——照抄 MediaWiki 官方文档会踩空** |
| `prop=extracts`                                     | ✅           | 正文                                                  |
| `prop=categories`                                   | ✅ 24 个     | **外观特征已是结构化标签**，见 §3.1 的 `kind:'tags'`  |
| `prop=pageimages`                                   | ✅ 1139×1654 | 立绘直出                                              |
| `prop=revisions` / `action=parse` / `list=allpages` | ❌           | 拿不到 wikitext、不能枚举                             |

另外两个实现前提：

- ⚠ **MediaWiki 的「拒绝」是 HTTP 200 + body 里的 `error.code`，不是 4xx。** 见 §3.4 第 1 闸。
- ⚠ **页名要按站解析**：zh.wikipedia 上「鸣潮」不存在，条目是繁体「鳴潮」；萌百是简体「长离」。跨站查同一个 IP 必须各自过一次 `opensearch`/`list=search`，不能拿一个页名打全族。
- ⚠ **英文源字段要回中文源核对本地化译名**（Fandom `weapon = Sword` ↔ 中文「迅刀」）。切片 0 在这上面出过一次错，见 §2 勘误。

### 3.4 防幻觉五道闸（全部结构保证，不靠模型自觉）

> 🔬 **切片 0 把这五道闸从「理论上要有」变成「实测证明必须有」**：开检索**没有**降低幻觉率（两臂都是 14.3%），只是换了幻觉的位置。加检索而不加闸，等于把「诚实弃权」换成「自信编造」。

1. **grounded 显性化**：`no_evidence` ≠ `failed`；UI「未取得联网证据」badge。
   ⚠ **判据不能只看 HTTP 状态码**：MediaWiki 的拒绝是 **HTTP 200 + body 里的 `error.code`**（如 `action-notallowed`）。只看状态码会把「这个源被封了」（=`failed`，该换源/该提示）当成「查到了空结果」（=`no_evidence`，该告诉用户没搜到）——正是这道闸要区分的两件事被混掉。每个连接器必须自己声明「怎么算失败」，不能共用一条 `response.ok`。
2. **引用必须真实**：关键论断带 `[n]` 指向证据包内真实 EvidenceItem；`llm-output-validator` 扩一条规则——幻引用=输出不可用，打回重试（照 script-doc 线的结构化重试模式）。
   🔬 **实证**：开检索后问「这个 YouTube 视频多长」，模型拿到 Serper 摘要里的**标题**，就自信报出「19 分 13 秒」（真值 18 分 40 秒）——**摘要里根本没有时长，是补出来的**。无检索时同一题它诚实答「我访问不了这个链接」。这条闸拦的就是这个：证据包里没有的数字，不许出现在结论里。
3. **basis 四分类**：来源声明 / 观察 / 推断 / 无法确认，UI 呈现有区分。
   🔬 **「带对冲的幻觉」必须归到推断/无法确认，不能因为对冲过就放行**：实测答案先声明「我无法实时联网获取」，然后仍给出「大约 1,500 到 2,500 张」（真值 3,644）。**声明不确定不豁免编造具体数字**——凡是具体的数字/日期/名称，basis 只能是 `source` 或 `unknown`，不能是「我推断大约」。
4. **新鲜度**：`retrievedAt` 全链 + Serper 时间过滤（「最新」类意图触发，🔬 `tbs=qdr:w` 实测生效）；证据冲突（wiki 说 A、X 说 B）呈现「两说+各自日期」，不擅自裁决。
5. **源优先级**：域内权威 API > 通用网搜；`sourceTier` 露出。
   🔬 **实测支持「不平均用力」**：LoRA 生态题（Civitai 底模/触发词、HF 许可、跨族挂载）**两臂 5/5 全对**，模型自身记忆足够可靠；错的全集中在 **IP 角色**与**时效**两组。所以查询规划器（§3.2）应当按意图**决定要不要检索**，而不是所有问题一律打源——省钱、省延迟，且少一次「半懂就敢说」的机会。

### 4.3 视频分析多路（边界 17 落地）

- 能力矩阵三值化：`video: 'native' | 'frames' | false`（现状 `src/constants/assistant.ts` 的 `ASSISTANT_MEDIA_CAPABILITIES` 是 `video: boolean`）。Gemini=native（主路，🔬 已实测可用）；Qwen-VL 补 DashScope video 分支（现状是硬抛「不支持」，抛的是未实现——形态照 Gemini 分支抄，**配额仍未实测，缺 key**）；豆包=验证通过后候选。
- **抽帧管线**（通用退路，先做）：worker ffmpeg，**确定性抽帧策略 + 帧集落 R2/ResearchRun**（审片可复现：owner 翻案时看的必须是同一组帧）；让所有图片模型（GPT-5/Claude/Qwen）= frames。owner 规则许可依据：「使用系统明确抽取的关键帧序列」合法，禁的是封面冒充。
- **按任务路由**：运镜/节奏/动作质量 → native 优先，借不到就明说「需 Gemini 或 Qwen key」（Hard Rule 8 走 QuickSetupDialog）；一致性审片 → frames 够用且便宜（本质是逐帧比对）。

#### 🔬 4.3.1 成本杠杆（切片 0 实测，替代原「超阈值确认」的单一手段）

Gemini 视觉 token **≈ 5,450 / 分钟，随时长线性**（18m41s = 101,923；1h00m02s = 326,504，两点算出来一致）。但 `videoMetadata` 提供了两个更便宜的旋钮：

| 配置                                                     | VIDEO token | 相对全片 |
| -------------------------------------------------------- | ----------- | -------- |
| 全片 18m41s（默认帧率）                                  | 101,923     | 100%     |
| `videoMetadata: { startOffset, endOffset }` 裁 0:00–1:00 | 5,460       | **5%**   |
| `videoMetadata: { fps: 0.2 }` 全片                       | 42,787      | 42%      |

**所以「超阈值确认」改成「先降级再问」**：超过阈值时**先按任务自动降级**（一致性审片本来就不需要满帧满长——裁片段或降到 fps=0.2），把确认卡留给「用户明确要求全片满帧分析运镜」这一种情况。原写法一超时长就弹卡打断用户，在有 5% 这个旋钮的前提下是不必要的摩擦。

#### ⚠ 4.3.2 两个实现坑（实测踩过，不记一定再踩）

1. **thinking token 从 `maxOutputTokens` 里扣**。给 800 实测得到 `thoughtsTokenCount=765` / 正文 31 字 / `finishReason=MAX_TOKENS`——表现是「视频分析回了半句就没了」，极易误判成模型能力不行或视频太长。视频分析的输出预算必须给足（实测 3000 够）。
2. **视频不可访问回 `403 PERMISSION_DENIED`，不是 404**。直译给用户就成了「你的 API key 没权限」，会把人引去查 key。必须映射成「这个视频不可访问（可能已删除或非公开）」——这条同时是 §3.4 第 1 闸「失败语义要分开」在视觉线的落点。

三洞修法：①能力判定改用**未截断**的 references，`slice` 移到两个 throw 之后（第 9 个是视频＋路由不支持时，`ASSISTANT_VIDEO_UNSUPPORTED` 现在会正常弹）；②legacy `referenceImageData` 并入 `hasImage` 口径，统一走 `ASSISTANT_IMAGE_UNSUPPORTED` 而不是让图打到 provider 抛英文裸错；③超量**不抛错**，`droppedCount` 结构化带出 + 附件清单末尾明写「另有 N 个未发送，请如实说明且不要描述其内容」。错误码与 i18nKey 一字未改。

⭐ **顺带消灭了一个隐患**：`buildReferenceInventory` 原本自己也 `slice` 一次——**同一个上限两个主人**，一旦漂移清单里的 `#n` 就会指向模型没收到的附件。现改为接收已截断的那份，三处 handle 编号（清单/视频链接指令/媒体输入）从此同源。

⚠ **设计席拍板：校验上限与送模型上限拆成两个数**（`ASSISTANT_MEDIA_LIMITS.maxReferencesPayload = 32` vs `maxReferences = 8`）。起因是 agent 核实出的事实——原 schema 卡死 8，**第 9 个附件会让整轮对话 400，用户连打好的字一起丢**，还吐 Zod 英文裸串。放宽后 9–32 走「截断＋告知」，>32 才判异常载荷。这也把本批从「纯纵深防御」变成线上真正可达的路径（此前三洞因 schema 硬拒 + legacy 字段无 HTTP 生产者而从外部打不进来）。

**未做**：`droppedReferenceCount` 到 UI 的最后一跳（流式需在 route 加响应头；**告知在会话层已闭环**——模型被指令要求主动说明，UI chrome 属锦上添花）；legacy `referenceImageData` 参数已无活的 HTTP 生产者，按原则 1 该删但要动位置参数签名，留待清理批。
