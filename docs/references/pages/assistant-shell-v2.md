## 工作区归属与可靠性（2026-10-04）

助手共用引擎、人设、语言和模型偏好；业务内容按 `image-natural`、`image-tags`、`lora`、`video`、`cards`、`canvas:<projectId>` 分开。同一画布项目里的节点共用会话，操作仍绑定实际节点 ID。自然语言台与标签台之间换模型走一张「换到另一台」的卡（`switch_workbench` → `confirm(workbenchHandoff)`）：快照带上对面那台能跑的模型（`otherWorkbenchModels`），`set_model` 指到它们时直接出卡、不先拒；用户点「带我过去」才选中型号、带走提示词、换路由，并把助手写的下一句填进那边的输入框，由用户按发送。目标型号已不在目的工作台时保留待确认，只有切换成功才记录「已换台」；「先不要」不改表单和路由。

- 当前账号 + 工作区决定客户端 scope；新会话先分配本地 thread ID，首存回包只归原 thread。会话、排队消息、问题与确认、续跑、撤销、输入草稿与附件均在这个范围内。切台后旧流、旧查询、旧上传不能写进新位置。
- 会话归属由请求里的 `workspaceKey` 加库里已有的 `surface` / `projectId` 决定（图片台两台再靠首条消息上的戳区分），**不依赖任何新列**，服务端核账号、画布项目归属和会话范围；没有戳的旧图片会话一律归自然语言台，照常续聊（owner 2026-10-04）；不再有「只读旧历史」这一档。
- 自动记忆和助手写的规矩按域存（图片 / 视频 / 画布 / LoRA / 全局），自然语言台与标签台同属图片域；关闭记忆或隐身时不新增。学出来的创作偏好只在图片、LoRA、画布三台注入，视频与角色页不带；常挂上下文卡不再自动注入，素材与卡片仍可通过显式工具选择。
- 保存失败保留当前页面草稿并提供重试。流必须收到合法终态；错误、坏帧或提前结束都不能触发自动生成。恢复历史本身不重新提交生成。
- **自动生成**（owner 2026-10-14 改）：开关跟着工作台走（账号 + 工作区记在本机，新会话、重置、换会话都不复位）。开着时请求带 `autoGenerate`，服务端在这一轮的话前面挂一行 `AUTO-GENERATE ON`：这一轮改了会影响产出的东西（提示词、模型、参数、参考，或要修 / 重出结果），助手收尾时自己把**这一轮动过的**卡放上生成确认卡，客户端替用户按下；纯提问、没动过的卡不出。单轮最多 4 张（`ASSISTANT_AUTO_GENERATE_LIMITS`，按出图张数算，画布每张卡按它自己的张数），超过就不替你按，线程里落一行 `autoGenerateHeld`。自动看一眼那一轮不带 `autoGenerate`，不会连环出图。
- **出图后自动看一眼**（owner 2026-10-08）：只在自动生成开关开着、由客户端替用户按下那一枪时生效。图落地后（画布：那张卡的产出图换了；工作台：那张结果卡收齐）客户端自己发一轮，附件是刚出的那张、请求带 `autoReview`；服务端只让模型用 `critique_result` 对照参考看一次，说一两句哪里不对，不改词、不重出。一枪只看一次；在那之前用户开口了就作废。手动确认的生成照旧不自检。
- LoRA 手机端与桌面共用 operator 宿主。各工作区仍使用原有媒体执行链，不因隔离更换模型内置联网路径。生成请求及每项结果携带原工作区、thread 和 pending 卡归属；不同工作区不能消费彼此结果。底层仍只保留最近一批 activeRun；已认领的 pending 卡来源被后续批次替换，且在等待期内未恢复时提示回流中断，不据此宣称真实生成失败。
- 撤销等待宿主真实回执；部分失败停止并保留未撤销项，切台后的迟到回包不更新新会话。谨慎模式在计划两步起先要求确认（2026-10-04 起；单步改动不再拦，见 §11.1）；讨论仍可看图和查证。
- 视觉与参考简报从同一份 Zod 契约生成输出说明与 provider schema；仅 `LLM_STRUCTURED_OUTPUT_MODELS` 列出的 Gemini／GPT／Claude 型号使用 provider 结构化约束，其余型号保留 JSON 模式和本地校验。格式错误至多定向修正一次；上下文超限的辅助调用真实压缩输入。
- 主回复、视觉辅助和原生联网的取消信号传至 provider 与媒体预读。深入调查规划器和外部网页读取尚未接入停止信号，迟到回包不能更新已切换的会话。流式请求分别限制响应头等待与连续无数据时间；持续有数据的长回答不会因总时长被掐断。Gemini 临时文件在取得真实文件名时登记，媒体准备的部分失败、取消与回复正文消费均执行独立清理。
- 会话结账与证据编号在锁定同一会话的事务内分配、保存。调查工具完成后先保存证据再给 UI 编号；结账引用既有编号，保存失败不编造可钉住的引用。
- 原生联网回执区分已搜索、无结果、失败、未调用、暂停和部分完成；只保存 provider 实际披露的查询，不用规划器查询补齐。引用分别标明回答片段、来源摘录或无摘录，回答片段不能当网页原文；仅已搜索的回答进入快搜结论，暂停后不自动追加检索。

- **工具出错不再整轮报错**：规划或执行某一步时抛出的技术故障记为一条 `toolFailed` 步，助手接着做不依赖它的部分或如实说这一步没成；只有缺 key、未登录、额度不足这类要用户动手的错仍整轮上抛。模型超时 / 限流 / 临时不可用时先原样重发一次，仍不行就借用户配过的另一把 key 把这一步跑完并让模型说一句「这一步换了家」（owner 2026-10-08；安全拒答、余额不足、key 失效不借）；`set_prompt` 缺参考图视觉事实时服务端自己补读，不先拒一轮；模型连着两次回不出可读的 JSON 时，捞得出人话就当收尾，捞不出就说一句兜底，不吐 error 帧。
- **出图质量的三处结构性补丁**：① 图片 / LoRA / 画布三台的系统提示要求按构图定画幅与清晰度（单人全身竖图、三视图宽图、小脸要还原时开最高档）；② 画布按展开的镜里每个节点挂的模型给写法（此前那一段在画布上永远为空）；③ 自然语言模型带参考图写提示词时，服务端按核过的参考简报在末尾补一段「Reference roles」图例，逐张写明这张图管什么、保留什么、别抄什么（再次写入时整段替换，标签方言不加）。

- **标签台角色构图**（owner 2026-10-05）：快照带 `novelAiCharacters`（V4.5 网格档 ≤6 人 / V5 自由档 ≤22 人 + 现有名单），助手用 `set_tag_characters` 一次写整份名单（每位的标签、负向、位置、开关、互动、台词；空名单 = 拆掉；没给的互动 / 台词沿用同一格原来的），可撤销；每位标签与互动的动作标签照样过 NAI 方言硬闸，台词不过闸。整体提示词只留场景、画风、质量与人数，个人特征写进各自那一格。种子仍不碰。
- **标签台画面文字**（owner 2026-10-07）：快照带 `novelAiSceneTexts`（现有清单 + 这个模型台词与画面文字合计的字数上限、是否只认英文），助手用 `set_scene_texts` 一次写整份清单（招牌 / 标题 / 封面 / 其他；空清单 = 清掉），可撤销；字原样存、不过方言闸，发送时由系统补那句自然语言与 `Text:` 段。台词属于人，仍走 `set_tag_characters`；两条写字的路按同一把尺判超限与只认英文，只拦这一步造成的问题。

以上为当前本地代码契约；工作区归属不改库结构，无需迁移。

## 2026-09-30 · 先讨论、说了才动手；只给看回复

Owner 原话：「讨论问题的时候希望他能和我讨论，而不是每次都输出一个结果，可以和我反问。真正执行的时候再去执行。搜索联网要开。我不关心他是怎么思考的，我关心的是助手回复的内容。」三处取舍当场定：助手自己判断讨论还是执行 · 反问一律用问题卡 · 过程只留回复和来源。本节覆盖下文与之冲突的旧规定（问答快车道里「怎么改 = 准备改动」、`message` 两句 + 可折叠「为什么」、跑完保留「做了 N 步」/ 调查行 / 计划清单）。

- **讨论与执行由模型判**（`ASSISTANT_OPERATOR_ANSWER_FIRST_RULES`）：只有「改 / 写进去 / 换 / 就这样 / 生成」或对它提议的「好」才动手；问看法、怎么办、比较方案都是讨论，给真实观点和理由、不碰工作台；拿不准按讨论。在讨论卡上选一个方向**仍是讨论**：接着谈这个选择，再用问题卡问「要我按这个改吗」。
- **反问全走问题卡**，`message` 不以问句收尾；讨论轮的回答写在 `message`、卡跟在后面。服务端所有停在卡上的出口（问题卡 · ask 工具 · 覆盖三选 · 歧义选图 · 生成确认）一律**卡前先发 `message`**（`messageBeforeCard`）。
- **联网不设门槛**：答案依赖不确定或会变的事实（作品、画师、角色、技法、模型能力）就查，熟知的不查；附着的图照旧靠看不靠搜。
- **没有「为什么」**：`detail` 从 turn schema、`message` 事件、客户端条目整条删掉；推理留在模型那边。`plan` 只用于要动好几步的执行，讨论里不出。长度档只约束执行后的回报，讨论按段落给；「末尾一条下一步」只在执行后，卡片在时卡就是下一步。
- **快搜用所选模型自带的联网**（同日 owner 选「各家用自带的联网」，照 Claude 的做法）：Gemini 走 `google_search`（跳转链接只读跳转头换成真地址）、GPT 走 Responses API 的 `web_search`（用所选模型本身）、Claude 走服务端 `web_search`、Grok 走 Responses API 的 `web_search` + `x_search`（2026-10-10 补上；X 上的帖子 / 串只有它搜得到，X 搜索按拉到的帖子计费，实测一问 X 舆情约 $0.4、30 秒）；模型自己写查询、读结果、给带引用的回答，那段回答直接当结论。快搜**不再**先改写、查完**不再**归纳（各省一次 LLM 往返），自带联网那一路也不再由我们读页。**能用自带的用自带，用不了才走管线**（owner 2026-10-10，八题对比：GPT 自带 15/16、Gemini 14/16、管线 6/16）：深入调查档也交给自带联网（只打网页那一源，Claude 一次可搜 `deepNativeSearchUses` 次、Grok 按同一个数收轮数）；所选模型没有自带联网时走外部检索，⛔ 不借别家的 key（旧的 `findNativeSearchRoute` 已删，owner 2026-10-15「全跟助手」，见 `assistant-v3.md`「只用所选那一家」）。Grok 搜 X 时默认只看视频封面，创作者明说「看看视频」才让它看视频本身，并在调查那一行写看了几段。仍走管线的：来源名单这一家装不下（见下一条）、「再多找几个源」（百科 / danbooru 连接器补在自带联网旁边）、联网找图、联网找视频（Serper `/videos` + B站连接器，§9.4）。Claude 用不带动态过滤的 `web_search_20250305`（带过滤的那一版过滤代码报错、次数耗尽）。入口 `llmNativeWebSearch`，扇出的 `nativeWebSearch` 顶替「网页」那一源（时限 `nativeSearchTimeoutMs`，不走 Serper 熔断器）。
- **各家自带联网补齐**（2026-10-14，owner「把缺口也补上」）：

  - 刻意没做：GPT 自带联网的图片结果、Claude `web_fetch`（找图走 Serper、读页走 Jina，已覆盖）。
- **查资料一开口就亮「查资料中」**：检索全跑在规划期，所以 `research` 在规划前先吐一帧 `running`（同 id，跑完覆盖）；前端把跑着的查资料步也认成一次调查。旧版这一行要等查完才出现。

## 0. 定位与范围 / 非目标

**定位**：助手是工作台上唯一那只「替你拧旋钮的手」。它不生成媒体，它把参数、提示词、参考图和 LoRA 铺到你看得见的控件上，把扳机留给你。v1 把这只手做出来了，v2 只做一件事——**让它像一个 Agent，而不是一个工具面板**。

### 2.2 模型只见五个入口

五个入口工具的 schema 长这样（要点，不是完整定义）：

| 入口                 | 必填参数                                            | 组内细分怎么定                                                                                                                  |
| -------------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `look`               | `action`（枚举）+ 该动作原有的参数                  | `action` 是**封闭枚举**，值 = 本组原工具 id（§2.1 表「看」列）；代码按它派发到原实现，原入参 schema 一份不复制                  |
| `research`           | `action`（枚举）+ 原有参数                          | 同上；「查证 / 找图」两档与 `scope` 的合并在 #16 落地，本组届时只剩两个 `action`（§9）                                          |
| `ask`                | `question` · `options[]`（2–4）· `why?`             | 只有一种形态：单选，无 `action`。多步计划由模型在 turn 上写 `confirmPlan: true` 出 `confirm(multistep)`，不走它                 |
| `apply`              | `action`（枚举）+ 原有参数                          | 一次调用只改**一项**（不是 `changes[]`）——错一项只重发一项，报错仍是模型学得会的 `malformedArgs`；`action` 枚举按域裁剪（§2.3） |
| `request_generation` | `action`（`prime_generate` / `request_generation`） | 参数从工作台快照现取，模型不填模型 / 张数 / 比例（用户在卡上改，§5）                                                            |

真值只有一份：`ASSISTANT_OPERATOR_ENTRY_ACTIONS` 由 `ASSISTANT_OPERATOR_TOOL_VERBS` 过滤得出，五组并集 = 全部工具、两两不交，由测试锁住（⛔ 不在文档里钉死那个数字，见 §2.1）。`step` 帧带必填 `verb`（= 入口名），面板状态词直接读它。

**为什么这样切**：v1 的模型要在 31 条描述里挑一条，挑错的代价是白烧一步 LLM 往返（`maxSteps` 只有 8）。收成 5 条之后，「挑哪个动词」这个判断人和模型都做得对，剩下的「具体哪一支」是确定性的字段派发——那是代码该干的活。

**⛔ 别做的事**：别把 `action` 做成开放字符串。开放了就等于把 31 选 1 换成了 31 选 1 加拼写错误。域裁剪（`ASSISTANT_OPERATOR_ENTRY_ACTIONS_BY_DOMAIN`）继续生效，裁的是**枚举值**而不是工具条目；枚举被裁空的入口不进提示词，`ask` 永远在。

### 2.3 audio 域工具怎么处理

`ASSISTANT_OPERATOR_DOMAINS` 现在是**四个**：`image` · `video` · `lora` · `canvas`（2026-09-19 并入画布，读码点数）。

`mount_audio_reference` 与 `set_sound` 两条**列进「改」组**，但域表里**仍然没有 `audio`**——它们在 v1 里就住在 video 域的工具表里（`ASSISTANT_OPERATOR_TOOLS_BY_DOMAIN[video]`），至今保持原样：`apply` 的 `action` 枚举在 video 域下包含 `mount_audio_reference` / `set_sound`，在 image / lora 域下不包含。

为什么：这两条动的是**视频工作台上真实存在的两颗旋钮**（配音参考、声音开关），不是一个独立的音频工作台。给它们单开一个域，等于造一个界面上不存在的工作台，而域裁剪的全部意义就是「界面上没有的旋钮，模型压根看不见」。

### 2.4 提示词 / 事件 / 卡片如何按同一五分法对齐

| 层           | 五分法怎么体现                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------------ |
| **系统提示** | 工具段由 31 条描述缩成 5 段，每段一句「什么时候用它」+ 一张枚举表                                |
| **SSE 事件** | `step` 帧的 `tool` 字段值域收成五个动词；`verb` 是新的一等字段（§3.1）                           |
| **卡片**     | 「查」→ 证据卡；「问」→ 问题卡；「请求生成」→ 确认卡；「改」→ 消息卡里的一行摘要；「看」→ 消息卡 |
| **加载态**   | 五个动词各一句状态词（§3.6）                                                                     |
| **结论记录** | 「看」的产出进「事实」；「问」的产出进「决定」；「请求生成」的产出进「待办」（§7.2）             |

**为什么要对齐到这个程度**：用户读一屏面板时脑子里只该有一套分类。v1 的问题不是卡片多，是**日志的分类、卡片的分类、提示词的分类互不相干**——同一件事在三处叫三个名字。

参考图分析仍分「逐图事实 → 本次分工简报」（2026-09-26）。逐图 `characterEvidence` 分脸部、上半身、全身比例、腿部、侧面、背面六区记录 `clear / partial / unknown`、观察与限制；`unknown` 是有效分析结果，不靠反复看同一图补出细节。旧缓存缺少六区结构时重新分析，保留相同 URL 且结构完整的已有事实。

简报的 `evidenceGaps` 只列影响**本次输出**的证据缺口：腿部未知不阻止头像；要求忠实还原全身或三视图时，相关区域缺证据才询问补参考或授权设计补全。已获授权的补全部分作为设计草案处理，不冒称原角色事实，也不重复询问。简报技术失败直接报告错误，保留已有修改，不再构造空缺口的默认简报。

写入前**没有模型复核**（owner 2026-10-08）：写提示词只有确定性检查能退回（引用了不存在的 @Image、不合模型方言、参数越界），模型判断类的疑问只走简报的 `uncertainties` / `evidenceGaps` 问一次；写好的词交给确认卡，由创作者判断。此前的 `issues / conflicts / unsupportedClaims` 复核已删除：它让每次写词多一次模型调用，而且遗漏退回不留痕，画布接力时在同一步无限重写。画布写词与生成提案的输入检查见 [画布助手](node-canvas-v2.md#1321-canvas-域的三条工具--助手能碰的那一格)。

### 3.4 问题块：一组 ≤4 题，一次一题，与输入框同框

> ⚠ **本节 2026-10-14 再改（反问卡多选 + 完整交互，owner 拍板 4A）**。2026-09-19（56b 切片 4）那一版的「⛔ 没有确定」「就地展开其他输入框」「Esc 整组作废」三条作废，理由写在各条里。组件仍是 `StudioOperatorQuestionBlock`。

- **一帧带一组（≤4 题，每题 2–6 项），界面一次只画一道**。⭐ 「一次只问一个」是**界面**的纪律不是**帧**的纪律：旧规矩「模型想问两件事就分两轮」的代价是每答一题都要重跑一整轮工具环（真机：同一道题被问了三遍）。⛔ 别回到一帧一题。选项上限 4 → 6 是给多选题的（「这几个角色里哪些出场」常超过 4）。
- **坐在输入框上方、同一个 composer 容器里**，不随时间线滚走。未答的问题是当下唯一挡路的东西。
- **块上摆什么**：已答小标签 · 问题一句加粗（多题才写「1 / 3」，多选题旁一句「可多选」）· `why` 一行灰字（模型给了才画）· 选项**竖排一行一个**（单选：编号键帽；多选：方形勾选框；可带缩略图；标签 + 一句灰色说明；推荐项排第一并打「推荐」，⛔ 不预选）· 「其他…」一行（`allowOther` 时）· 底下一行「跳过 · 全部用推荐」，多选题右边一颗「确定（N）」。
- **单选没有「确定」**：点任一行即选中并进下一题（多一颗确定钮等于让用户为同一个决定按两次）。
- **⭐ 多选是唯一的例外**（owner 2026-10-14 拍板 4A）：点一行 = 勾 / 取消勾，⛔ 不提交；底部近黑实底药丸「确定（N）」交出全部勾选。0 项且输入框为空时不可按；输入框有字时按它 = 勾选 + 那句话一起交。覆盖三选（`overwrite`）三档互斥，即使标了多选也按单选走。
- **勾选住在 store**（`StudioOperatorQuestionPrompt.checked`）：收放面板会卸载组件，勾了三项一收一放就归零是假承诺。⚠ 只存过收放 / 重挂，⛔ 不落库 —— 刷新后从第一道重来（`StudioOperatorPendingSchema` 只存题面）。
- **「其他…」= 下面那一行输入框**（Q6 不变）：点它只是把焦点交过去，⛔ 不就地展开第二个输入框。闭集题（`allowOther: false`）不画这一行。
- **下面的输入框始终可用**：直接打字 = 用一句话回答当前这题（`otherText`），⭐ **已勾的选项一起带上**（「选 A + 补一句」并存，⛔ 打字不再清掉勾选）。
- **「跳过」/ `Esc` = 这一题记一格「跳过」进下一题**，整组照常一次发；跳过那一句也进对话（「跳过了问题『…』，由你决定」）。⚠ 替掉旧的「Esc 整组作废、一行不落」：那一版模型下一轮不知道用户拒答了。覆盖三选上的跳过 = 「保留」。
- **「全部用推荐」**：当前与之后每道题都取推荐项（没有推荐项的那道算跳过，⛔ 不替用户挑第一个），整组一次发。所有剩下的题都没有推荐项时不画。
- **键盘**：`↑`/`↓` 移动（漫游焦点，含「其他…」那一行）· `1`–`9` 直选（多选 = 勾）· `空格` 选中 / 勾 · `Enter` 单选选中、多选确定、「其他…」行交焦点 · `Esc` 跳过。块出现时焦点落在**第一个选项**上 —— 落在输入框上的话，用户打的「1」会变成一次选择。
- **无障碍**：单选 `role="radiogroup"` + `role="radio"`，多选 `role="group"` + `role="checkbox"`，都用 `aria-checked`；组名指向问句。
- **已答的先收成小标签**留在块上方（多个标签 + 补的那句按界面语言拼成一串）。⚠ 它们此刻**还没进时间线**：整组答完才一次性落成几行系统行 —— 「← 上一题」只要 pop 一格，并把那一题当时的勾选放回 `checked`。
- **面板只交 id**：文案、缩略图（→ @chip）、覆盖三选那一档全由 `useAssistantOperator` 从卡上取；`StudioOperatorQuestionAnswered.labels` 是数组。
- **v3 服务端**：`ask` 入参的 `multiSelect` / `allowOther` 带 `.describe()`，五张脸共用一段 ASKING 提示（何时多选、闭集、缩略图、跳过怎么接）；选项 `image` 是**句柄**（卡句柄 / `ref-N` / `card-N` / 附图名或 id），服务端换成这一轮手上已有的图，⛔ 不收模型写的地址；顶层 `why` 一行。
- **落账规则**：整组答完后 ① 时间线插几行 `问题 · 你选了 X`（每行自带题面的 `userText`，2026-10-14 起走 i18n：`StudioOperator.question.answerText` / `answerOther` / `answerBoth` / `skippedText`，标签按界面语言 `Intl.ListFormat` 拼）；② 写进本轮结论的「决定」栏（§7.5）；③ 下一轮请求里作为 `planAnswers` 一次带上去。
- **反问时机由模型判**（2026-09-23 owner 更新）：身份、身材、画风、参考图优先级、数量、费用或节点布局有冲突或缺少决定时，第一次就问，不能因「大概猜到」先改。清楚的指令及已回答的选择直接沿用；技术失败说明原因和恢复路径，不要求用户重述已明确的目标。

  - **点名常驻**：一轮里最后一段说完的回复点到的卡，常驻一圈 2px 黑框（`data-find-named`），读屏多念一句「回复里点到了这一项」。这一轮还在跑时不算（正文还在长）。

- **资料挂在哪一段回答下面**：判据是**位置**不是 runKey —— 消息条目身上没有 runKey，而「这段话用了哪几条资料」在时间线上本来就是「查完再说话」。实现是 `collectOperatorAnswerSources`：攒着查到的证据，遇到下一条助手消息就挂上去并清零。⚠ 一轮里「查 → 说 → 再查 → 再说」时两次分别挂，⛔ 不按轮堆到最后一句下面。
- **钉住改为钉来源卡**：底下认的仍旧是证据编号（`pinnedEvidence`，§7.3），⛔ 不是「收藏一张卡」。
- **⛔ 不为角标另写一个 markdown 渲染器**：`[3]` 在 markdown 里本来就是普通文字，所以做法是在**渲染出来的 React 子树上**递归替换（`withCitations`，`p` / `li` 两个覆盖叠在 `INITIAL_COMPONENTS` 之上）。只映射段落的直接子节点会漏掉紧跟在加粗后面的那一个。
- **还在流的时候不摆资料**：否则来源卡会在正文长高的过程中一直往下跳。
- **⛔ 分析卡退场**（56b 切片 5，`StudioOperatorReferenceAnalysisCard` 整文件删）：挂进来的图直接进当前多模态模型，回答就是一段普通正文 —— 说这是什么画风、凭什么这么判、提示词里该怎么写，末尾顺手问要不要落到工作台。那张卡把同一件事拆成「一段分工简报 + 一折『参考依据 · N 张图』」，而用户问的是「这是什么画风」。⚠ **`analyze_references` 这条工具本身没有删**：在 v2 内核里它仍旧是 `set_prompt` 的取材与分工来源，而且历史里那一份 `referenceAnalysis` 还在喂 `readOperatorReferenceProfiles`（「没换过的图复用已核实的视觉事实」那条省钱路）。删掉的是它在界面上的那张卡。⚠ v3 内核（五张脸）写词、出图都⛔ 不再走它（`run.skipReferenceReview`，owner 2026-10-15「不要求很严的表，让模型自己去看去判断」）：要看就用 `look`，图交到主模型眼前（`docs/references/assistant-v3.md`「看图」）。
- **视频链接**同一条路：`verify` 取回标题 / UP主 / 时长 / 简介（`video` 证据），模型据此说话。⚠ **关键帧抽取本仓没有服务端能力**（`lib/video-frame-capture.ts` 跑在浏览器里，服务端只复算计划核对时间戳），所以这一档目前是**元数据喂**，⛔ 不许描述没看过的镜头。

- **收尾轮逐段追加**（56b 切片 3）：服务端只发差值（`message_delta`），客户端**追加**到同一条 `streaming` 气泡后面，末尾画一根**不闪的光标**；定稿帧 `message` 按 id 整体覆盖并降旗。⛔ `message` 上的 `partial` 已删 —— 两条「正文还没写完」的表达方式必然分叉。工具轮仍然不发旁白。
- **`motion-reduce` 直接整段落**（owner 2026-09-19）：逐字追加本身就是一种动效，关掉动效的人要的是「写完了再给我」。这一档**不画半截正文** —— 占位行 / 状态词一直留到定稿帧。
- **历史回放不重播流式**：历史条目没有 `streaming`，所以既没有光标也没有增量。
- **渲染 markdown**：复用仓里已有的 `src/components/ui/markdown.tsx`（`react-markdown` 已是依赖）。⛔ 不为助手另写一个渲染器。还在写的长正文不折叠。
- 长回话折叠（首句 + 「展开全文」）逻辑保留，判据仍数换行数；仅定稿后生效。

#### 3.6.1 调查那一行（两档 · 56b 切片 2）

**⭐ 进度是加载态，不是常驻卡**（owner 2026-09-19）。一张常驻卡的问题是它跑完之后还在那儿占一整块，而那时唯一要读的东西是下面那段回答。

| 态   | 长什么样                                                               | 判据                                                                     |
| ---- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 跑着 | 一行微光 +「深入调查中 · 约 1 分钟」/「查资料中 · 约 10 秒」           | 预估**写在行里**（`ASSISTANT_RESEARCH_ESTIMATE_SECONDS`），⛔ 不做倒计时 |
| 点开 | 就地展开那几条步骤日志，再点收起                                       | 与 `StudioOperatorToolGroup` 同一套开合                                  |
| 跑完 | 灰底一行「搜了 N 条 · 读了 M 页」/「深入调查 · 查了 N 条 · 读了 M 页」 | 折在回答上方，形状与跑着那一行一致                                       |

- 组件是 `StudioOperatorResearchProgress`；判「这一组是不是一次调查」的是 `summarizeOperatorResearchBlock`（有跑完的 `research` 步才算，⛔ 单独的 `read_url` 不算）。**有失败步时退回 `StudioOperatorToolGroup`**：那一行上没有失败的位置，而失败恰恰是那一刻唯一要读的东西。
- 微光走 `animate-pulse` + `motion-reduce:animate-none`（`ui-defaults` 的现有配方，与占位脉冲同一支），⛔ 没有为这一行新造渐变扫光。

**两档**（`ASSISTANT_RESEARCH_DEPTHS`）：

| 档              | 打什么                                                      | 大约多久  |
| --------------- | ----------------------------------------------------------- | --------- |
| `quick`（缺省） | 一轮网搜 + **服务端读前 `quickReadPages`（3）页全文**       | 几秒      |
| `deep`          | 现有规划器 / 扇出多轮 + 全部连接器（wiki / B站 / danbooru） | 约 1 分钟 |

- **入口两处**：模型按用户的说法判（「深入查 / 尽量全 / 一定要准」，判据写在工具说明里，⛔ 不设死阈值），或回答底下那颗「深入调查」按钮那一轮带进来（`expandSources` 一律按 `deep` 算）。
- **快搜读页不新增证据条**：读到的正文原地顶掉那几条的 `snippet`（放宽到 `maxReadUrlExcerptChars`），所以来源卡与正文角标仍旧一一对应。读不出来就留着摘要，⛔ 不在日志上假装读过。
- **用户设了来源名单时快搜那条收窄不生效**：名单是用户的决定，而「网搜」很可能根本不在名单里 —— 照收窄的表现是他指定的源一个都没打、回来一句「查不到」。
- ⛔ **不弹确认卡**（owner 定）：花的是搜索额度不是生成费。

### 3.7 失败那一条：三段 + `traceId`

> Last Verified: 2026-09-20（owner 真机第 1 条，原话「我甚至不知道为什么出错」）

**起因**：56a 的记忆注入直接打库，而 `20260920120000_assistant_memory` 还没执行 —— `findMany` 在一个 `undefined` 上炸开，异常冒到成帧器，`toErrorEvent` 对非 `GenerationError` 一律回同一句兜底，面板上只剩 `error.generic`。两个洞各修各的：**可选增强不该拖垮整轮**（[`backend.md`](../backend.md)「可选增强」节），**说不出分类的失败也得说得出是哪一次**（本节）。

**错误帧多两个可选字段**（`AssistantOperatorErrorEventSchema`）：

| 字段      | 谁给                                                  | 生产环境                  |
| --------- | ----------------------------------------------------- | ------------------------- |
| `traceId` | 成帧器，8 位十六进制；同一个值同时写进 `logger.error` | **有**（唯一那根线）      |
| `detail`  | 原始 `message`                                        | **没有**（⛔ 更没 stack） |

- **判据在服务端**（成帧器按 `NODE_ENV` 决定下不下发），⛔ 客户端不自己判环境：两份 `NODE_ENV` 判两遍，迟早说两句不一样的话。
- `GenerationError` 那一族**不编短码**：它本来就带 `errorCode` + `i18nKey`，编一个日志里查不到的号比没有更糟。
- 非 `GenerationError` 的统一码是 `ASSISTANT_OPERATOR_INTERNAL_ERROR_CODE`（`'INTERNAL'`），住 `constants/assistant-operator.ts`：成帧器发它、客户端那张 `ASSISTANT_OPERATOR_ERROR_MESSAGE_KEYS` 按它取三语文案，两个消费方，⛔ 别各写一个字面量。
- 请求快照校验失败的 HTTP 400 同样返回与服务端日志对应的 `traceId`；开发环境附首个失败字段及原因，生产环境不返回 `detail`。客户端在流建立前也保留这两个字段，避免只剩泛化的请求失败文案。

**错误条长成三段**（`StudioOperatorErrorBar`，`status-risk` 档）：

1. **一句人话** —— 阶梯照旧：操作员自己的码 → `getGenerationErrorMessage`（`i18nKey` → `Errors.generation.*`）→ 原文；都走不到就是 `error.internal`「这次请求在我们这边出了问题」。⛔ 别说成「请稍后重试」——重试对一个没修的内部错误没有用。
2. **`traceId`** —— 等宽槽（`ui-defaults.md §1`：机器串）。它存在的全部意义是被念出来 / 截图 / 粘过来。
3. **「复制详情」** —— 一次点击把人话 + 短码 + `detail` 一起进剪贴板；触屏命中区靠 `touch-target-y` 补到 44。⛔ 不做「展开更多」：要的人是要把它发出去，不是要在面板里读它。

**就地动作**（`actions`，第一颗是主动作）：缺 key →「配置 Key」（Hard Rule 8，就地 `QuickSetupDialog`；一把都没有配 Gemini 免费档，选定的助手模型那一家缺 key（`ASSISTANT_MODEL_KEY_MISSING`，错误帧带 `missingKey`）→「配置 {厂商} Key」配**那一家**、不改工作台的出图模型，验证过就自动重发「接着做完」，owner 2026-10-15 ⛔ 回落别家），其余 →「重试」（发一句「接着做完」，⛔ 不原样重放上一条）；两种情况都另有一颗 **「换个模型」**（2026-10-14 设计方案 §9.1）——打开输入框底下那颗模型 chip 的选单（`StudioOperatorModelChip` 的受控 `open`），⛔ 不另起一张选模型的面板，缺 key 的模型照旧就地弹配置。

非生产环境另外把 `detail` 原样画在第三行（等宽、可换行）。三段的数据在 store 里是**两格**（`errorText` 那句人话 + `errorTrace` 那两样）：合成一个字符串的下场是「复制详情」只能把翻译过的那句话再抄一遍。

#### 历史会话行的两个动作（owner 2026-09-20 真机第 3 条）

> 原话：「点击编辑后应该直接编辑；点击删除后按钮切换成确认删除的按钮，再点一次才删」。

| 动作     | 状态机                                                                                                                                                                |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **编辑** | 点铅笔 → 标题那一格**就地**换成 `<input>`：**回车保存 · Esc 取消 · 失焦保存**；编辑态里两颗动作钮让位。⛔ 不弹层                                                      |
| **删除** | 点垃圾桶 → 该按钮**原位**换成「确认删除」（`status-risk` 红字，**内距一格不变**）；再点一次才真删。退回确认态三条路：**3 秒无操作 · 指针离开这一行 · 焦点离开这一行** |

- 就地改那一套**逐字沿用 56a 记忆列表**（`SettingsAssistantSection` 的 `MemoryRow`），连 `cancelledRef` 那一手都一样：Esc 之后紧跟着的那一拍 blur ⛔ 不许当成保存（`setDraft(null)` 要到下一次渲染才生效）。

#### 会话标题怎么派生（owner 2026-09-20 真机第 4 条）

> 起因：胶囊上写着「reference image 1 reference image 2 reference image 3 这几张图的画风抽出…」。前面那三段是**挂上去的图**在正文里的占位 —— 界面上它们是 chip，进了标题只剩噪音。

规则整条住 `src/lib/assistant-conversation-title.ts`，**三个调用方共用它**：头部标题胶囊 · 历史行 · 服务端新建会话时的 `titleFromMessages`。⛔ 三处各写一遍必然漂成三种长度。

三步，顺序有理由：

1. **先剥参考图提及** —— 两种形态：`@名字`（`mention-input` 的序列化字面量：`@Image1` · `@Attachment[...]` · `@莫宁`）与「reference image N / 参考图 N / リファレンス画像 N」那类短语。⛔ 不能放到截断之后：噪音会先把额度吃光。
2. **再取首句** —— 三语句号 + 感叹问号 + **换行**都算收尾（按回车就是换了一件事）。
3. **最后按视觉宽度封顶** —— `TITLE_MAX_WIDTH = 36` **半角格**：CJK 一个字两格、拉丁一格，于是 18 个汉字与 36 个西文字符是同一条视觉宽度。超出加 `…`（省略号自己占一格）。

- **CSS `truncate` 只作兜底**：它按容器宽度裁，而容器宽度随面板拖宽变 —— 同一条会话在两台机器上会显示成两个长度不同的名字，而这个名字正是用户用来认它的。
- **存量标题在渲染时才过这条规则**，⛔ 不写数据迁移：函数是幂等的，跑第二遍还是它自己（有测试钉着）。
- **历史行上是两个标题**：库里那一份给读屏与改名初值（用户要改的是真名字），派生那一份只给眼睛。
- **剥成空退回原文**（整条消息都是提及时）：一个噪音标题仍旧好过一个空标题。

#### 动画机制与铁律（owner 09-20 定相位机 · 09-26 形状改 B）

形状 = **B「先横成一条，再落下」**（owner 2026-09-26 从三方向原型里选定，原型 artifact `GFfqsraLtaRRBBKigkmCuT`）：面板按全尺寸排版，只动 `clip-path: inset()` 的左 / 下两条内缩。收起形是右上角一颗头像大小的圆 → 第一拍横向拉成 44px 头部条、头部进场 → 160ms 后纵向长成面板、正文进场。收回反着走。弹簧与节拍只住 `constants/motion.ts` 的 `LIQUID_SPRING` / `LIQUID_TIMING`。

四档相位：`closed → opening →`（第二拍弹簧落定，外加一条兜底定时器 `openMs`）`→ open → closing →`（**定时器** `closeMs`）`→ closed`。

| 铁律                                                         | 为什么                                                                                                  |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| 面板**只裁剪不变尺寸**：动 clip-path 内缩，⛔ 不动宽高与位置 | width / height / top / left 每帧都要重排整棵面板                                                        |
| 头像不单独计时，骑在形状左上角                               | 进度 = 左边沿走了多少（`dockProgress`），头像只动 transform                                             |
| 静止档 `clip-path: none`，⚠ 与动着时是同一个 motion 值       | motion 的 style 从 motion 值换成静态字符串时不解绑，DOM 会留着最后一帧的裁剪                            |
| 动着时投影挂在外层包裹的 `drop-shadow` 上，静止后撤掉        | 滤镜先于裁剪执行，box-shadow 会被自己的 clip-path 裁掉；静止档撤滤镜，`@` 候选菜单的 fixed 定位不受影响 |
| **定时器**卸载                                               | ⛔ 不靠弹簧的 `finished` / `transitionend`：后台页 rAF 冻结，它们永不来，留下幽灵面板（09-26 真机复验） |
| ⛔ 不用 `AnimatePresence`                                    | 同上一条，2026-08-30 真机实测                                                                           |
| **动着时不开 `backdrop-filter`**                             | `assistant-glass-panel` 在 `open` 相位才挂；`prefers-reduced-motion` 直接挂                             |
| 内容分两批：头部随第一拍、其余随第二拍，带 6px 短模糊        | 与形状同时出会看起来像一张纸被拍上来；收起时内容先退 90ms，形状才开始收                                 |
| 动着时面板 `pointer-events: none`                            | 动着的面板上点中的格子与松手那一格不是同一个                                                            |
| `prefers-reduced-motion` 全部直切                            | 没有中间相位，毛玻璃当场就挂                                                                            |
| 连点不从头播                                                 | 新一段 `animate` 从当前位置与速度接着走，只作废还没发出的那一拍                                         |

画布宿主（owner 2026-09-30 改）：与图片 / 视频工作台同走布局 A，⛔ 再用上面这套 B 形状（此前「头部条从头像正下方长出来」那条作废）。

内容入场的起始帧靠 CSS 的 `@starting-style`；形状的起始帧由 layout effect 在上屏前量好尺寸、把内缩跳到收起形——⛔ 不用「先挂 closed 再 rAF 翻 opening」那种两帧 setState，低端机上照样漏第一帧。

### 5.2 与工作台参数的同步规则

**工作台是真值，卡是它的一个可编辑视图。**

| 时机                       | 谁写谁                                                                                  |
| -------------------------- | --------------------------------------------------------------------------------------- |
| 卡**出现**时               | 从工作台快照取初值（模型 / 比例 / 张数 / 分辨率四项）                                   |
| 卡上**改一项**             | **立刻写回工作台**（走 `apply` 的同一条 op 通道，带 `inverse`）；工作台控件同步高亮一拍 |
| 卡**未确认**时用户改工作台 | 卡上对应项跟着变（工作台是真值）                                                        |
| 点 `确认生成`              | 用工作台**此刻**的值触发，⛔ 不用卡上缓存的那一份                                       |
| 点 `先不要`                | 卡转「已取消」态；**已写回的改动不回滚**（用户可以用 checkpoint 撤）                    |

**为什么卡上改立刻写回、而不是确认时才写**：如果卡自己攒一份参数，工作台上显示的就和即将生成的对不上——用户点确认前看着 3:2，出来的是 16:9。让卡永远只是工作台的一个视图，这类错配在结构上就不存在。

## 7. 跨轮记忆：每轮结账（方案 A）

### 7.1 现状断点（读码核过）

| 上一轮产生的东西 | 下一轮能看到吗 | 现状                                                           |
| ---------------- | -------------- | -------------------------------------------------------------- |
| 用户说的话       | 能             | 全文（`buildMessages`）                                        |
| 助手回复的文字   | 能             | 全文                                                           |
| 参考图分析结果   | 能             | 事实摘要，每轮重发                                             |
| 生成出来的图     | 部分           | 只有名字和地址（`resultArtifacts`）                            |
| 查证得到的证据   | **不能**       | 只剩标题（`collectStepArtifacts` 明确只记名字地址）            |

| 整份工作记忆     | —              | 只在浏览器内存（`getOperatorState().workingMemory`），刷新即丢 |

### 7.2 数据模型：本轮结论

一条结论记录保留三栏文字、证据编号与来源元数据：

| 栏               | 类型                                           | 内容                                                                     |
| ---------------- | ---------------------------------------------- | ------------------------------------------------------------------------ |
| `facts`          | `string[]`                                     | 「看」组产出的事实及纯文字反馈中用户明确说明的证据边界                   |
| `decisions`      | `string[]`                                     | 「问」组产出的决定、确认选择与用户明确认可的局部特征                     |
| `todos`          | `string[]`                                     | 待生成、待修改、明确否定的部分及本次任务的证据不足                       |
| `evidenceRefs`   | `string[]`                                     | 证据编号（`#e12` 形态），指向证据本                                      |
| `sourceRefs`     | `{assetId,nodeId?,name?,url}[]?`               | 服务端从本轮实际附件绑定的图片版本；仅 URL 精确且唯一对应时附节点 ID     |
| `pinnedEvidence` | `{refs,conclusion,sourceCount,corroborated}[]` | **钉住的那几条结论**（2026-09-12 实测第三组 B），走 §7.7 那条 PATCH 读写 |

⚠ `pinnedEvidence` 与 `evidenceRefs` **是两列**：后者是这一轮查到的**全部**编号（结论块的证据 chip 行读它、结账时服务端自动写满），把钉住塞进去等于每张证据卡一出生就是钉住态。它带着那一句结论是有意的——刷新之后历史里没有证据卡，常驻条要画的那句话只能由记录自己带着。

外加 `roundIndex` · `createdAt` · `editedByUser`（用户改过的标记，§7.7）· `memoriesWritten` / `incognito`（56a，见 §7.8）。

`sourceRefs` 复用现有 `rounds` JSON，不新增数据库表或迁移；模型不能编造来源，用户编辑三栏也保留原来源。列出附件不代表附件已获认可。评价只属于所记 URL，同名节点换图后不继承旧评价；旧记录没有来源时不猜版本。部分认可与整体采用仍是两件事，不自动写整图 `approved`。

### 7.3 证据本

**工具全文按编号存**，模型不重发、只按需翻。

| 项           | 决定                                                                                                                                 |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| 存在哪       | **复用 `ResearchRun` 表**——它已经有 `conversationId` 弱引用、`evidence Json`、`conclusions Json`、`perSource Json`，就是为这件事长的 |

| 怎么翻       | **新工具 `recall_evidence`**（归「查」组），入参 `refs: string[]`，出参对应条目的正文                                                |
| 不进下一轮的 | 证据正文、评审原文、候选尺寸——它们只以编号出现在结论记录里                                                                           |

### 7.5 服务端生成时机

**每轮 `done` 帧发出**之前，服务端用本轮已有的材料写一条结论记录：

1. 从本轮 `step` 的 `verb` 分桶：`look` → `facts`；`ask` 的答案 + `confirm` 的结果 → `decisions`；`request_generation` 未落地的 → `todos`。
2. 「问」的答案由**客户端在下一次请求里带上**（用户是在流结束之后才点的），服务端收到后**补写**进上一条记录的 `decisions`。⚠ 这是唯一一条「回头补写」的路径，别扩大。
3. 结论文字由一次**轻量 LLM 调用**压缩成每栏 ≤ 3 条、每条 ≤ 60 字。⛔ 不让主模型在正文里顺手写——那会让它把结论说两遍（一遍给人、一遍给记录）。
4. 记录随 `done` 帧的 `roundSummary` 载荷一起下发，客户端**直接渲染，不再请求一次**。
5. **以卡结束的那一轮也结账**（a1563804）：停在确认卡 / 问题卡 / 上下文卡上的轮次在 `stopped` 之前先写这条记录 —— 用户点完卡不再新开一轮，不结账那一轮在时间线上就没有结论块。

正常完成的纯文字轮也可结账，无需为了保存反馈调用视觉或检索。压缩器将「脸没问题、腿不对、原图没有可靠全身」分别保留为局部认可、待改和证据边界，不把明确限制改写成检索失败；闲聊未形成结论时返回空栏、不存空记录。新放开的无工具结账路径不写长期记忆，特定图片的评价也不属于长期偏好。技术失败或取消不触发这条纯文字结账路径。

### 8.1 助手提议上下文卡

流程：`propose_context_card`（「问」组）→ 面板确认卡（同时写一行**待确认**）→ 用户点头才进长期记忆；当场没点的，留在设置里的**待确认区**补点。

| 环节         | 规则                                                                                              |
| ------------ | ------------------------------------------------------------------------------------------------- |
| 工具入参     | `kind`（character / style / brand）· `name` · `summary` · `body` · `negative?`                    |
| 服务端       | **不落库**，只吐一帧 `ask`（`kind: "contextCard"`），载荷是卡的草稿                               |
| 客户端       | 渲染成一张问题卡形态：卡片预览 + `存这张卡` / `不用`；**同时**把草稿写成一行 `status: "proposed"` |
| 「存这张卡」 | PATCH 那一行 `status` → `confirmed`（那一行没写成时回落成 `POST … status: "confirmed"`）          |
| 「不用」     | DELETE 那一行 —— 明确的拒绝，⛔ 不留在待确认区里反复问                                            |
| 待确认区     | ⛔ 已随设置里的上下文卡页签一起删（2026-09-26）                                                   |

⚠ **为什么服务端不落库、而客户端落**（owner 2026-09-11）：写库这一跳必须长在用户那一侧 —— 服务端自己落库等于助手能不经过人就写用户的长期记忆；而「当场没点，后来在设置里补点」这条路要走得通，前提是那张卡还在。两条同时成立只有一种落法：**服务端不写，客户端收到提议帧就写一行 `proposed`，用户点头翻面、放弃删除**。

## 9. 搜索：查证 + 找图

### 9.1 「查证」内部流程

用户看不见工具，只看见一次「查证」。入口是 `research`（`want: "facts"`），内部四步：

| 步     | 做什么                                                                                             | 为什么                                           |
| ------ | -------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 改写   | 一句话拆成 2–3 条搜索词，**中 / 英 / 日各一份**                                                    | 画风、角色、术语类的词，英日命中率高得多         |
| 选源   | 按内容类型自动挑：二次元 → Danbooru + Wiki；现实 → 网页 + 图搜；中文热点 → B 站；给了网址 → 直接读 | 让模型「想起」该去哪查，是 v1 那次实测失败的根因 |
| 并发   | 多源同时打，去重，**互相印证的排前**，只有一个来源说的标「单源」                                   | 排序本身就是判断力，不该交给用户逐条读           |
| 给证据 | 结论 + 来源列表 + 日期；每条可点开原文、可**钉住**进本轮上下文                                     | 「谁说的、什么时候说的」是可信度的全部           |

⭐ **结论那一句是归纳，不是摘录**（2026-09-12 实测第三组 A）：收尾**一次**结构化 LLM 往返（persona 的那把脑子、用户语言）把排在最前的几条证据压成 ≤2 句，只许基于证据。解不出来回落到确定性摘录（`summarizeResearchConclusion`）。证据卡、钉住条、结论块的「事实」栏共用这一句 —— 这一步进结账原料的那一行写的就是它，⛔ 不是整条链路观察。

⭐ **题型偏置**（2026-09-12 实测）：改写那一次结构化输出同时标 `questionType`（`style_technique` / `entity_facts` / `general`，常量与词表在 `constants/research.ts`）。画风 / 光影 / 材质 / 技法 / 提示词这类「怎么描述、怎么画」的题，四处一起偏：改写词补技法限定词并删掉生平词、选源换成网搜 + danbooru + B站 +（排最后的）百科、结果排序在同印证数内把生平条目压后、归纳要求先给「可复用的描述词」。⚠ 起因是「新海诚式黄昏光怎么描述」命中的全是导演生平条目。⛔ 另两个题型逐字不变。

⛔ **不合并「找图」**：图搜通常是「我要参考图」而不是「我要答案」，产出形态（网格 vs 列表）与后续动作（挂参考 vs 引用）都不同。`want: "images"` 走 `search_web_images` 那条，出候选网格（摆在回答底下，§3.5）。

⭐ **网图在面板里怎么取**（2026-10-15 搜索期切片 1，附录 I §3.4）：面板里每一张**第三方**网图（候选网格、灯箱里的原图、回答底下的媒体条、角色页候选图卡）都走 `useThirdPartyImage`：`referrerPolicy="no-referrer"`（大多数图床拒的是别家站的 Referer，空 Referer 放行）；连空 Referer 也拒的那几家（`WEB_IMAGE_HOTLINK_PROXY.hosts`：pximg / hdslb / sinaimg）先走自家图片代理 Worker 的 `/hotlink/<host>/<path>` 那一支（`workers/civitai-image-proxy`，带对应站点的 Referer 去取），取不到退直连，再退调用方给的退路（灯箱退搜索结果的缩略图），全取不到画断图标，⛔ 破图标。代理域名复用 `NEXT_PUBLIC_CIVITAI_IMAGE_PROXY_BASE`，没配就只是 no-referrer 直连。Worker 那一支是**白名单**不是开放代理：名单外 / 仿冒域 / 带端口或 userinfo 一律 404 不发请求，只认自家页面（打代理那一下 `referrerPolicy="origin"`），别家页面的 Referer 或不带 Referer / Origin 一律 403，重定向只在名单内跟，非图片 415、超 20 MB 413（`workers/civitai-image-proxy/README.md`）。⚠ 只管**看**：服务端导入（「选用」）对这几家仍是「取不回来」（`hotlinkProtected` 判据不变）。自家 R2 / CDN 的图不走这一层。

### 9.2 证据卡字段

沿用 v1 的 `AssistantOperatorEvidenceSchema` 六字段（`title` · `url?` · `publisher` · `snippet` · `kind` · `confidence`），细节见 [`assistant-shell.md` §7.1](assistant-shell.md)，本文不重抄。v2 只加两项：

| 新字段            | 说明                                                                                                    |
| ----------------- | ------------------------------------------------------------------------------------------------------- |
| `evidenceRef`     | `#e12` 形态的会话内编号（§7.3）                                                                         |
| `corroboration`   | 印证源数（`2 源印证` / `单源`），由服务端算                                                             |
| `cite`            | **正文里 `[n]` 的 n**（56b 切片 1）——本轮内 1 起、跨 `research` 调用连号，由服务端分配（⛔ 不由模型写） |
| `mediaUrl`        | 能摆进正文的那张画面（`image` 是原图、`video` 是封面）。⚠ **只下发客户端**，⛔ 不进 `observation`       |
| `durationSeconds` | 视频时长 —— 封面右下角那枚角标。取不到就缺席，⛔ 不回落成 0                                             |

⚠ `confidence` 仍由**源的层级**算，⛔ 不由模型写——让模型给自己找的东西打分，它给的永远是 high。

⭐ **四种资料**（56b 切片 1，owner 2026-09-19）：文字 = 正文本身 · 图片 = `image` 证据 · 链接 = 来源卡 · **视频 = 新增的 `video` 证据**（`videoUrl` · `thumbnailUrl?` · `durationSeconds?` · `site` · `excerpt?`，schema 在 `types/research.ts`）。它与 `image` 分开而不是「带时长的图片」：点下去的**去处不同** —— 图开站内灯箱，视频不开灯箱。~~⛔ 不嵌播放器~~（2026-10-15 搜索期第二片改，owner 2026-10-14「视频优先面板内直接播，难实现才退回新窗口」）：`video` 证据（媒体条封面、标成视频的来源卡、过程行证据条）与 `search_web_videos` 找到的视频走同一个判据（`resolveWebVideo`）、同一个播放器（`StudioOperatorWebVideoPlayer`，各家**官方嵌入**），认不出稿件号的与别的站仍开新窗口（§3.5「找到的视频」、§9.4）。⛔ 不转存、⛔ 不下载、⛔ 不解码任何一帧（边界 18 不动）—— 嵌入是对方站点自己的播放器，我们这边一个字节都不碰。

- **谁产出**：B站连接器（单稿件与搜索两条路都出 `video`，此前是 text + image 两条同 URL 的证据）· 网搜连接器（命中 `RESEARCH_VIDEO_SITES` 白名单的播放页）。白名单与 `detectResearchVideoSite` 在 `constants/research.ts`。
- **为什么是白名单不是 `/video/` 这种路径启发**：后者会把一篇讲视频的博客判成视频，而判错的代价是界面上多一颗点开不是视频的播放钮。
- **模型读到的是元数据**（标题 / UP主 / 时长 / 简介），⛔ 不是播放地址 —— 与 `image` 档「有意不放图片地址」同一条纪律：给它一条能直接粘的地址，它下一步就会写进提示词。

### 9.3 来源白 / 黑名单

落在 **`ProjectRule`**，一列 `kind` —— 这张表**现在只装来源名单**：

| `kind`        | `text` 装什么     |
| ------------- | ----------------- |
| `sourceAllow` | 一个域名或来源 id |
| `sourceDeny`  | 一个域名或来源 id |

- 白名单**非空时**：查证只打名单内的源；打不到就如实说「你的名单里这几个源没有」，⛔ 不偷偷扩源。
- 黑名单：任何时候都过滤掉。
- 入口：助手设置「记忆」页下半块「搜图来源」（§11.6）+ 在话里指定来源（只作用于本轮，不写库）。`POST /api/assistant/rules` 只收这两种，`text` 过 `ProjectRuleSourceTokenSchema`（地址收成域名，一句话 400）。
- ⚠ 原来的 `note`（普通规则）已并进记忆（§7.8「你写的 / 助手记的」）。库里 `ProjectRuleKind.NOTE` 这一值暂留（新代码不读不写）：迁移随生产构建执行，那一刻之前的旧部署仍可能写它。

为什么复用 `ProjectRule` 而不是新表：它已经有 `userId` / `scope`（域）/ `source`（谁记的）三个维度，来源名单需要的正是这三个。

### 9.4 找视频（`search_library` kind `web_videos`，2026-10-15 搜索期第二片）

模型那一侧是 v3 `search_library` 的第三种 kind（契约见 [`assistant-v3.md`](../assistant-v3.md)「找图 / 找视频」），内部落到旧执行器的 `search_web_videos`（INTERNAL，v2 的五个入口看不见它）。

- **去哪搜**：平台的 Serper（`google.serper.dev/videos`，同一把 `SERPER_API_KEY`）+ 已有的 B站连接器（查询是中文 —— 有汉字没假名 —— 或查询 / 创作者那句话里点了 B站时才打）。两路并发，按嵌入地址（认不出就按规整后的原链接）去重、轮流取，最多 8 条；同一支视频两边都有时缺的字段互补。⛔ 不走任何模型的自带联网、⛔ 不碰用户的 GPT / Gemini / Claude key（钱闸测试 `assistant-operator.money-gate.test.ts` 锁着这个服务的源码）。
- **来源名单照样管**：名单滤掉「网页」就不打 Serper、滤掉 B站就不打连接器，两路都滤光如实说「什么都没搜」；逐条结果再过一遍 `filterEvidenceIndices`，被滤掉的条数写进观察。
- **Serper 那边容错解析**：每个字段单独 `.catch`，缺链接或标题的条目丢掉；每次调用记一行 `webVideoSearch.serper raw shape`（条数 + 字段名，⛔ 不带值），用来对真接口的字段名。上游失败 = 零条，⛔ 不抛（与找图同一条 best-effort 契约）。
- **给谁看什么**：整卡数据（标题 / 平台 / 频道 / 域名 / 时长 / 封面 / 日期）走步骤事件下发面板；模型只拿到每支一行 `#n · 标题 · 频道 · 平台 · 时长`，外加「你没看过这些」「⛔ 别导入、别把地址写进提示词、用 #n 指代」。
- **画在哪、怎么播**：§3.5「找到的视频」。查证（`research`）出的 `video` 证据点开同样走这一个播放器（§3.5 那条「全面板一个判据、一个播放器」）。

### 9.5 找到的东西的编号与查证短版（2026-10-15 搜索期第三片）

模型那一侧的契约在 [`assistant-v3.md`](../assistant-v3.md)「找到的东西的编号 `#n` 与查证短版」，这里只记面板与请求这一侧：

- **整卡不进模型**：卡片数据（缩略图、原图、链接、尺寸、时长）只随步骤事件给面板；模型只拿到每条一行 `#n · …`，要用哪张写号，服务端换回地址。
- **下一轮带着上一轮的**：`use-assistant-operator.ts` 开新一轮时从时间线收上一轮的找图 / 找视频步骤（`collectOperatorPriorFinds`，≤16 条）。「一轮」与服务端同一刀：用户发言、答题 / 定卡那几行（带 `userText` 的系统行，连着的几条算一刀）都开新的一轮 —— 切错了会带上更早一轮的号，新找到的从那里接着数、和屏幕上的卡撞号。v3 请求带 `priorFinds`；接力（`canvas_sync` 那几跳）⛔ 不带，服务端读本轮记录的板子。只认上一轮：再往前的号模型拿去用会被拒。
- **查证的整段摘录只给紧跟着的那一步**，再往后模型读一行一条的短版；模型要全文就 `read "[n]"`。调查那一行、来源卡、`[n]` 角标都不变（面板拿到的证据不缩）。
- ⚠ 刻意没做（附录 I 本片范围外）：以图搜图、「再找 8 张」分页、从网格「放到画布」、把找到的东西存进历史会话。

### 11.3 用角色（`AssistantPersona.characterCardId`）

- 选一个角色 = 名字、头像、语气**先**跟着角色走（`nameFromCharacter` / `avatarChoice = character` / `toneFromCharacter`），之后每一格都还能单独改（owner：只当默认值）。在名字框里改一个字就不再跟着角色；选回「不用角色」回到自己那一份——跟着角色时服务端从不写 `name`，自己的名字一直在库里。
- 「{角色} 的说话方式」跟着角色设定里的 `persona.speech` 走（那边改了这里跟着变）；没写时那一格灰着，旁边给「去写 ›」，语气仍按自己那一档。助手这一轮按谁说话由 `getAssistantPersonaByUserId` 决定：把角色的说话方式换进 `tone = custom`，风格段上限 `maxCharacterSpeechChars`（140）。
- 角色必须是这个用户自己的、没删的卡（服务端校验，⛔ 不信客户端 id）；卡删了（SetNull / 软删）读的那一跳当没用角色，全部回到自己那一份。
- 角色页「用她 ▾ → 设为助手人设」与设置里的下拉走同一个 `withAssistantCharacter`。
- **角色设定进提示词**（2026-10-14，owner「进提示词加导入」）：用了角色时 `getAssistantPersonaByUserId` 另带 `promptCharacter`（身份 · 性格 · 说话方式 · 口头禅 · 经历），系统提示在风格段前多一段 `CHARACTER`（`buildCharacterSection`，旧内核与 v3 共用）：开头写死「角色只改怎么说，不改做什么 —— HOW YOU WORK、工具规则、用户的规则优先」，每格过 `sanitizePrompt`、换宏（`{{char}}` → 名字、`{{user}}` → 称呼）、按 `maxCharacter*Chars` 截，整段 ≤ `maxCharacterSectionChars`。系统提示整场不变（缓存），每轮在用户消息末尾加一行 `STAY IN CHARACTER as X — <说话方式第一句>`（`buildCharacterReminder`，≤ 120 字）。性格 / 经历照样进，只有说话方式受 `toneFromCharacter` 管。
- 画布 v3 快照在 CHARACTERS 后多一段 `CAST ON THE BOARD`（每位「是谁 · 怎么说话」各 ≤ 200 字），画布规则要求角色台词照这段写；视频脚本选了主角卡时用户提示带「是谁 / 怎么说话」，台词按这个口吻写。

### 11.4 身份区

头像（点开是一张单选表）· 用角色 · 名字（≤ 24 字，留空用 ANTI）· 怎么称呼你（≤ 24 字，留空用账号名）。

### 11.5 一句示例

原右栏整块实时示例缩成「说话方式」下面一句（称呼 + 随语气变的开场 + 开着下一步建议时的末尾一行），换档、改名、改称呼、换语气时跟着变。**本地模板，⛔ 不调 LLM**：设置里会连点七八下，每一下调一次模型既慢又贵，而且同一份设置两次会给出不同示例。

### 11.6 记忆页（M-A · 一列）

`AssistantMemoryPane`，页签写「记忆 · N」。

- **顶行**：一句说明 +「让助手记住」开关（`memoryCapture`，走人设那条「改了就存」）。关 = 只停「记新的」（结账与 `add_project_rule` 的普通规矩都不写），清单照样生效，说明换成「助手不再自己记新的；清单里的照样生效，不想要就删」。⛔ 隐身不在这里（它在助手面板 ⋯ 里，作用于当前会话）。
- **写一条**：「写一条，回车存下」—— 存成你写的、全部工作台；Esc 清空；你写的满 50 条时说人话（`Errors.assistantMemory.limitReached`）。新行从列表顶上长出 + 浅底 1.2s 褪掉（`animate-row-fresh`）。
- **筛选**：全部 / 你写的 / 助手记的，纯前端收窄（一次全取：你写的单独取满 50，与助手记的最近 200 合并）。**清空跟着筛选走**：「全部清空 / 清空你写的 / 清空助手记的」，确认卡写清会连带删掉什么（全部清空且你写的不为 0 时点名），`POST /api/assistant-memories/clear` 带 `source`。
- **每一行**：文字（点一下就地改）· 行尾「范围标签（非全部工作台时）+ 你写的 / 助手记的 · 今天 HH:mm / 昨天 / MM-DD」· 悬停出「删」（触屏常显），点一下原地变红「确认删除」再点才删，⛔ 不弹框。就地改 = 输入框 + 右边「用在哪」下拉（全部工作台 / 只在图片 / 视频 / 画布 / LoRA，选了当场存），回车存、Esc 退、焦点离开这一行也存。
- **空态**：全站空态原语，「写第一条」把光标送进输入框。
- **搜图来源**：下半块，「只从这些站找 / 不从这些站找」两行 chip，× 移除、「+ 添加」就地写一个站点（前端先过 `ProjectRuleSourceTokenSchema`，一句话当场提示）。
- 菜单与确认卡「从按钮长出来」（`getChipZoomMotion`，与工具行弹层同一种）；删 / 清空的行 120ms 淡出、高度 200ms 收起，退完才出空态、清空后才把筛选归到全部。

## 12. 视觉规范 · 方向 B「玻璃仪表·浅色」

> 画布：<https://claude.ai/code/artifact/7003a63a-b804-4937-8c65-18235f886843>
> 前提：**配色与现有浅色产品统一**（owner 明令：不要深色）。脊柱、语义 token、`--primary` 的独占强调地位全部沿用 [`ui-defaults.md`](../ui-defaults.md) §2，⛔ 本域不新增任何调色板。

### 12.1 三层玻璃

| 层       | 用在哪                                        | 原则                                                                                |
| -------- | --------------------------------------------- | ----------------------------------------------------------------------------------- |
| **面板** | 助手覆盖层本体                                | 最不透明的一层：它要压住工作台的内容，读字优先于透视                                |
| **卡片** | 五类卡片、结论记录块                          | 比面板再亮一档、边界靠极细描边而不是阴影：卡与卡之间是并列关系，不该有层级落差      |
| **浮层** | 历史下拉、「+」菜单、模型选择器、确认卡内下拉 | 唯一允许真正半透 + 模糊的一层：它是临时的，透出下面的内容才说得清「我盖在什么上面」 |

⚠ 三层之间靠**明度与描边**分，⛔ 不靠阴影堆叠——浅色底上多层阴影会糊成灰块。

⚠ **画板冲突时以 `Main.dc.html` 为准**（owner 2026-09-11 对稿定）：`BCards.dc.html` 的「玻璃仪表 · 组件表」里「加载态药丸」与「结论记录圆角卡」两格与主稿口径不一致，**按主稿走、实现不改**。组件表是配件目录，主稿才是这些配件装在一起之后的样子。

### 12.2 信号位

- **信号只用近黑实底 + 白字**：确认键、发送键、已选中的人设卡、被钉住的证据。
- 为什么是近黑而不是彩色：这套界面上唯一的彩色预算是 `--primary`，而 `--primary` 已经被工作台的生成键占着；助手面板里再用一次同色，用户分不出「这颗是助手的确认」还是「那颗是真的出图」。近黑是安全的第二重量级。
- 状态语义（成功 / 警告 / 危险 / 应用）仍走 `ui-defaults.md` 的四个 token，⛔ 不自造。

### 12.3 圆角与字体

- **圆角区间 8–18px**：小控件（chip / 图标按钮）取下限，卡片取中段，面板与浮层取上限。⛔ 不用全圆角胶囊，除了 chip。
- **字体沿用产品现有三槽**（`ui-defaults.md` §1）。画板上写的 `Geist` / `Noto Sans SC` 是画板自己的取值，**不迁进产品**——字体是全站脊柱，助手域无权改。

### 12.4 动效

沿用 `globals.css` 的既有配方与时长档。本轮**减少**动效总量：删逐字淡入、删进度带的持续动画。保留的只有三处——卡片入场、折叠开合、按压反馈。每一条带 `motion-reduce:` 降级。

为什么减：v1 一屏里有四种动画同时在跑（逐字、进度环、stagger、按词淡入），叠起来的观感是「界面在抖」，而它们各自单看都没问题。

**2026-10-07 owner 加了一族「同一个元素变形」**（PC 动效方向，原型 artifact `DnFQeyCBK22jKvB1ZjEdA7`，助手共 28 处分三批落地）。它不推翻上面的减法：仍守「一屏同一时间只动一处」，⛔ 不恢复逐字淡入和持续循环。第一批「出图」已落：

| --------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 发送 ↔ 停止           | 同一颗键换底色，图标走 `BlurSwap` 糊着换，⛔ 不是两颗键互换                                                             |
