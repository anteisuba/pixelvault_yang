# 助手外壳与画布助手归队（施工基准）

> 关键切片经 owner 确认（2026-07-27）。方向 **A · 壳接管表面**。
> ⚠ **本文只覆盖「归队」** —— 把画布助手的皮和壳拉回统一标准。**助手内部内容的重新设计另开一轮**（owner 同轮拍板）。

## 0 · 域定义 ✅ 已拍板

> **画布助手不是要「重新设计」，是要「归队」。** 壳（`AssistantShell`）和色（通用设计系统）都已经有标准答案，画布这一个 dock 是唯一没跟上的。

### 调查得到的三条事实（别再重新调查）

| #   | 事实                                                                                                                                          | 证据                                                                                                                                                                       |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **共享早就做了一半** —— 三个 dock 一直共用 `assistant/AssistantShell.tsx`                                                                     | `grep -rln AssistantShell` 命中 `LoraAssistantDock` / `StudioNodeAssistantDock` / `StudioAssistantDock`                                                                    |
| 2   | **壳几乎不管视觉** —— 只有 `<aside role="complementary">` + `flex-col` + `overflow-hidden` + Header 一行。**零背景 / 零边 / 零圆角 / 零投影** | 通读 `AssistantShell.tsx`（85 行）                                                                                                                                         |
| 3   | **暗色几乎全集中在画布这一个 dock**                                                                                                           | 暗色 `--node-*` 用量：`LoraAssistantDock` **1** · `StudioAssistantDock` **1**（两者都是 `node-canvas-panel-motion`，**动画类不是颜色**）· `StudioNodeAssistantDock` **35** |

⚠ **更正一条流传过的错误说法**：曾有结论称「`--node-*` 不能 scope，因为 LoraAssistantDock / StudioAssistantDock 在消费它」。实测两者各只用 1 个且是动画类 —— **改色的爆炸半径只有画布这一个文件**。那条结论的行动建议（"不该塞进 bug fix"）仍然对，但理由错了。

**事实 2 就是画布能跑偏成暗色的机制**：壳没管颜色，画布 dock 自己画了 35 处，没有任何东西拦得住。

## 1 · 职责边界 ✅ 已拍板（方向 A）

| 归                               | 内容                                                                                                                        |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| **`AssistantShell`（新增接管）** | 背景 `bg-card` · 边 `border-border` · 圆角 · 投影。Header 已有的字色层级（`text-foreground` / `text-muted-foreground`）保持 |
| **各 dock（仍自理）**            | 宽度 · 定位 · 收起/展开 · 拖拽改宽 · **全部内容**                                                                           |

### ⛔ 下面这节已被 owner 推翻（2026-07-27）—— 保留原文以备追溯

> **owner：「LoRA 那边是做了一个框点击覆盖。不是挤压且占满全部高度。这个可以放进共享的组件的设计中。」**

我当时否掉方向 B 的理由是「没有证据表明该统一的东西不统一」。owner 给出了那个证据：**覆盖式 vs 挤压式不是两个页面的偶然差异，是助手这个部件该有的统一行为。**

代码事实（实读）：

|          | 定位                                                                                                                          | 结果                                                              |
| -------- | ----------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| **LoRA** | `fixed` 贴视口右边（注释：「不值得为一个面板重排整页布局，改用 fixed 同样能做到分摊右侧宽度」），主内容只让一段 `marginRight` | 占满**视口**高度，浮在上层                                        |
| **画布** | `canvas-assistant-rail` 桌面档是 `lg:relative`（移动端才是 `absolute inset-0`）                                               | **在 flex 流里 → 真的挤压画布**，且被夹在顶栏下方，够不到视口满高 |

**新条款（进共享组件）**：

1. **覆盖，不挤压** —— 助手浮在内容之上，内容不重排。画布是无限可平移的，被遮住的部分平移一下就回来；重排画布则会让所有节点的屏幕位置突变，代价大得多。
2. **⚠ 也不占满** —— 是一张**四边留白的浮动卡片**，不是贴边满高的栏。
3. 宽度记忆仍走已有的 `useDockLayout`（两边本来就共用）。

> ⚠ **我一度把 2 写反了**。owner 原话「不是挤压且占满全部高度」，我读成「不挤压 **且** 占满高度」，实际是「**既不挤压、也不占满**」。owner 补了参考图才发现。歧义句先问清楚，别自己挑一种读法就往下走。

### 几何（据 owner 参考图读出，实现时以视觉为准不必逐像素抠）

```
┌─ 视口 ────────────────────────────────┐
│                                        │
│    画布（不重排，被盖住就盖住）    ┌──────────┐ ← 上留白
│                                    │ AI 助手  │
│                                    │          │
│                                    │  对话区  │
│                                    │          │
│                                    │ ┌──────┐ │
│                                    │ │ 输入 │ │
│                                    │ └──────┘ │
│                                    └──────────┘ ← 下留白
│                                          ↑ 右留白
└────────────────────────────────────────┘
```

| 项       | 值                                                                                                  |
| -------- | --------------------------------------------------------------------------------------------------- |
| 四边留白 | 约 `16px`（右/上/下同值，视觉上是「浮在画布上的一张卡」而非「钉在边上的栏」）                       |
| 宽度     | 沿用现状 `360`（可拖拽改宽，走 `useDockLayout`）                                                    |
| 圆角     | 卡级圆角，比节点卡的 `8` 大一档 —— 它是**浮层**不是卡；取 `--radius-lg` 档，具体值实现时对齐规格 §2 |
| 投影     | 需要，它浮在内容之上必须读得出层级（vs 节点卡的「静态无投影」）                                     |
| 高度     | `视口高 − 上下留白`，**不贴顶不贴底**                                                               |

⚠ 这三条（留白 / 圆角 / 投影）与节点卡的材质纪律**故意不同**：节点卡是「桌面上的纸」（静态无投影、小圆角），助手是「浮在桌面上方的面板」。两者混同会让浮层读起来像一张巨大的节点卡。

⚠ **连带条款：控件让位，内容不让位。** 画布现在靠 `--canvas-minimap-left` 之类的变量给右侧 dock 让位，改成覆盖后要分开处理：

| 对象                                              | 覆盖后                                                                         |
| ------------------------------------------------- | ------------------------------------------------------------------------------ |
| **画布内容**（节点/连线）                         | **不让位**，被遮住就遮住 —— 可平移，代价近乎零；重排则会让所有节点屏幕位置突变 |
| **常驻控件**（minimap / 底部胶囊 / 顶栏右侧按钮） | **继续让位** —— 它们位置固定，被浮层永久盖住就等于没有                         |

（这条我定的，理由如上；owner 若认为浮层该彻底覆盖一切，一句话推翻即可。）

⚠ 实现排在**令牌反转之后**（owner 定：助手内部内容等换皮全部收口再开；本条属于壳与行为，可先于内容做，但不要和令牌反转同批改同一批文件）。

### 为什么不接管宽度和收起（否掉的方向 B）· 原文存档

画布助手是**右侧可收起的 dock**，LoRA 那个是**页面内的栏** —— 两者的收起语义未必该一样。

> **没有证据表明该统一的东西不统一。**

实际发生的故障是**颜色分叉**，方向 A 精确堵住它；方向 B 顺手统一的是还没出过问题、也没论证过的东西。

## 2 · 画布 dock 的 35 处映射

**目标词汇 = LoRA dock 已在用的那套**（`bg-card` · `border-border` · `text-foreground` · `text-muted-foreground` · `text-primary` · `bg-primary/*`）。**不新造 token。**

### ⛔ 上面这句话是错的（2026-07-27 实测更正）

> **「用 LoRA 的词汇」会得到近黑，不是白。**

| 实测               | 值                                                                                                                                              |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `.domain-lora`     | `color-scheme: dark`，基调「近炭暖灰」。`lora.css` 头注明写基调历程「深炭黑✗ → **冷瓷浅✗** → 深靛✗ → 中性灰试 → 近炭暖灰(定)」—— 浅色方向被否过 |
| 助手 rail 的位置   | `canvas-assistant-rail` 是 `canvas-stage` 的**兄弟**，`.domain-canvas` 够不着它                                                                 |
| 照本节施工后的实测 | `getComputedStyle(aside).backgroundColor` = `lab(7.78%)`，与脊柱 `--card` 同值                                                                  |

**owner 的原话是「以助手那边的 UI 为准，不过颜色是白色」** —— 结构照搬 LoRA，颜色**显式覆盖成白**。我把「颜色也照搬」写进了 §2，与 owner 的指令直接冲突。这一节的映射表**只有结构语义可用，颜色目标作废**。

**正确的颜色目标 = 画布域皮肤 `--canvas-*`**（`--canvas-surface` = `#FFFFFF`），和 CastDock / CastCard 走同一条路：组件消费 `--canvas-*`，不消费脊柱 `bg-card`。

⚠ 连带三件必须做：

1. rail 要能拿到 `--canvas-*`（它当前在作用域外）
2. `color-scheme` 必须显式翻成 `light`，否则原生滚动条/控件仍是深色（本项目已有这个坑）
3. 字色/边色同步翻成 `--canvas-ink-*` / `--canvas-stroke-*`，否则白底白字

### ⛔ 11 处必须逐处判断，**禁止全局替换**

| 现状                                      | 用量 | 为什么不能 sed                                                                                                                                                                    |
| ----------------------------------------- | ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `bg-node-panel-inner`                     | 7    | 暗色系里它是「比面板**更深**一档」。翻到浅色系，该变成「比卡面更深」还是「更浅」，**取决于那一处是凹槽还是浮起** —— 同一个 token 在暗色里两种语义共用了一个值，浅色里会分裂成两个 |
| `text-node-canvas` / `bg-node-foreground` | 4    | 这是**反白对**（深底上的浅字 / 浅底上的深块）。浅色系里对应 `primary` / `primary-foreground` 那一对，同样要看用在哪                                                               |

**这 11 处是本片唯一需要判断的地方；其余 24 处是体力活。**
