## 二 · 几条关键判断是怎么来的（别重新推导，也别轻易推翻）

### 卡匣为什么要降级成注册表

不是"样式不好看"。根因是**它是画布节点的第二份副本** —— 同一个身份两处可选、可改、可操作。双重呈现必然产生"该在哪操作"的犹豫。代价三重：认知（不知道在哪操作）· 代码（576 行 + 自带一套指针拖拽，与 React Flow 原生并存两套）· 空间（240px 装卡面一屏只看得到 3 个）。

**所以解法是「废弃卡的副本、保留注册表」，不是"重画卡片"。** 一个对象只有一个可操作的地方。

### 任务模式 tab：我先否决又推翻了自己

第一轮我否掉它，理由是「模式和模型两个独立选择器会产生无效组合」。**那个前提是错的** —— owner 的多模型截图显示 tab 集合**本身由模型派生**（seedance 5 个 / Omni Flash 4 个 / Kling 2.5 只有 2 个），是两级派生不是两个轴。

由此得到本轮最重要的结构结论：**模式决定槽轨，模型决定参数**。它连带解决两件事：mode-by-input 退役（形态跃迁变成用户点的那一下）· UI 用 stale model id 的缺陷从根上消失。

### 强调色为什么要拆成两个角色

一个 accent 同时表"主动作"和"选中态"，**在画布上这两者天天打架**（选中的节点上再放主动作按钮 = 两个蓝抢主角）。拆成「主动作 = 墨色实底」+「accent = 指向（选中/活跃/@引用）」。代价是端口族色必须避开蓝色区 —— 这条已写进规格，改族色时别忘。

### 为什么 CD 第二轮比第一轮有用

第一轮让 CD 想结构 → 它抄参考截图的元件语法、造了五个假能力 tab。
第二轮**把结构、配色、字号、间距、动效时长全部给死**，只让它做视觉与动效，并明写「觉得结构有问题写在备注里，不要直接改」。结果：26 个 token 一个没被改动，它把两处结构冲突写进了备注而不是擅自改。

**方法论**：CD 擅长在约束内做精细化，不擅长在开放空间里守纪律。给它的自由度越小，产出越可用。
