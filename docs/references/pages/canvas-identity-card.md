## 0 · 域定义 ✅ 已拍板（owner 2026-07-27）

> **身份卡 = 角色的分类锚点。** 配置完之后，属于这个角色的节点都能通过它找到、定位；组装台需要素材时进「管理素材」按角色绑定，而不是拉连线过去。

### ⛔ 身份卡**不是 token，不进 prompt**（owner 2026-07-27 明确纠正）

> **它只做分类与过滤。** 进 prompt 的永远是**具体的图**。

|                       | 是什么                                     | 进 prompt          |
| --------------------- | ------------------------------------------ | ------------------ |
| **身份卡 / 角色档案** | 筛子 —— 找到、过滤、定位属于这个角色的东西 | ❌ **不进**        |
| **具体的图**          | 实际送给模型的素材                         | ✅ 可点 → 成 token |

身份卡的清单与展开模态，作用是**让用户在一堆图里挑出想要的那张**；挑出来之后**插 token 是消费侧（组装台 / 生成提示词框）的动作**，身份卡只负责把范围收窄。

⚠ 别把 `@角色名` 当成「身份卡的 token」来设计。

### 调解：「卡不进 prompt」与「卡 → 视频出边会递参考图」不矛盾（2026-08-26 补）

> 起因：《画布修法》05 节侦察发现「文档说身份卡不进 prompt，代码却把它连进视频时收割成参考图」——两处各说各话。这里把两句话摆在一起讲清楚，不再是「文档一句、代码一句」。

上表「身份卡不进 prompt」说的是**身份卡这个实体本身**——它不是 token，不会以`@角色名`的形式被塞进正文。这条不变。

但 §3「卡只出不进」明确保留的那条**出边**（`卡 → 镜头/视频`，owner 2026-08-10「卡片 → 视频这个应该保留」拍板）本来就有真实作用：下游收割时会展开这张卡的**出场组**（`getNodeStageMediaUrls` —— ★封面 + 已勾选 `onStage` 的额外图），把这些**具体的图**当作具名参考图递给视频/镜头模型，并在图例里标注「这张图来自哪张身份卡」（`harvestUpstreamVideoImageReferences` 用卡的显示名 `resolveNodeDisplayName` 当 `name`，槽架 token 与发送预览 `images[].name` 同一套值）。递出去的是**图**，不是「身份卡」这个概念本身——与上表并不冲突，只是容易被误读成「卡进了 prompt」。

⚠ **这不是本轮新加的行为**——`resolveNodeDisplayName` 早就是这条收割链的命名来源（见 `node-workflow-graph.ts` 里 `harvestUpstreamVideoImageReferences` 的注释）。《画布修法》05 节验收要求核对的是：这条早就存在的关系，用户在**界面**上能不能读出来。核对结果：能——`CanvasSlotRack.tsx` 的槽位按钮把 `token.label`（同一个 `resolveNodeDisplayName`）渲成常显文字（不藏在 hover 里），`buildVideoSendPreview` 的 `images[].name` 走同一条数据；选中一个下游视频节点、看它的槽架或展开发送预览，就能读出「这张定妆照来自常客」。这条结论是静态读代码核实的，**真机截图仍需编排会话在真实项目上补一次**（见任务报告「真机验证步骤」）。

### 为什么改成这个（原设计效果不好的诊断）

owner 原意是「把几张参考图 + 声音 + 背景打成一个整体喂给视频模型保证一致性」。这个意图撞上三堵**静默的**墙：

1. **跨模态总闸 ≤ 12**（Seedance Reference：`image_urls≤9` + `video_urls≤3` + `audio_urls≤3`），代码 `maxImages = 12 - videos - audios` **静默砍图**
2. **一半视频模型只吃一张图**（Seedance 基础 / Kling V3 Pro / HappyHorse / LTX 的「单张首帧」形态）
3. **多张参考图对一致性帮助有限** —— 给模型 3 个角度，它未必理解「这是同一个人」，可能产生混合特征

**正确链路是 `身份锁定 → 出一批一致的镜头图 → 镜头图喂视频`**，而不是身份卡直连视频。`shot` 节点今天就会收割上游 character + background 当具名参考图并注入 prompt 图例（主线 P3「零新建」指的就是这条）。

## 3 · 端口

**身份族 = 圆环 `#8A7B6A` 灰褐**（规格 §7，形状主编码、色辅编码，已避开强调蓝色相区）。

### ⛔ 卡**只出不进**：入端口已撤、入卡的边不画 ✅ 已拍板（owner 2026-08-10）

owner 原话：「之前不是通过连线吗，现在有了这个功能后，连线这个可以作废了。**但是卡片 → 视频这个应该保留**。」
「这个功能」= 槽架总包阶段 8-b 的**拖节点进卡**。

| 方向                   | 线   | 端口     |
| ---------------------- | ---- | -------- |
| `* → 卡`（入）         | 不画 | **已撤** |
| `卡 → 视频/镜头`（出） | 照画 | 留       |

**为什么两件事必须一起做**：入端口留着而线不画 = 用户拉一条线过来**什么都看不到**，正好掉进 `node-connection-rules.ts` 头注点名的坑 ——「静默失败，且和端口坏掉长得一模一样」（那个坑刚让我们花过三轮）。撤掉端口，「连不上」就变成一眼可见的形态事实。

**⚠ 停的只是「画」，边照建、收割一个字没改**：

| 入卡的边  | 谁在读它                                                         | 可见证据落在哪                                                |
| --------- | ---------------------------------------------------------------- | ------------------------------------------------------------- |
| 音色 → 卡 | `harvestUpstreamAudioBindings` Pass 1 的**两跳**（音色→卡→视频） | 卡面 🎙/「无音色」chip（由上游边算，与画不画无关）· rail 的 ♪ |
| 特写 → 卡 | `CharacterDetailBody.closeupItems`（并进图集，只读）             | ⤢ 详情面板图集 · rail 的「参考 N」                            |

新建入卡关系的两条现行入口：**拖进卡**（8-b）与「从画布选择」，两条都有回执（toast + 计数当场变）。

⭐ **这与 §5「找得到」不画边是同一条纪律的延伸**，不是它的重复：§5 管的是**归属**（那条关系本来就没有边，见 §4「打标签不是搬家」），这里管的是**真有边的那两类**。共用的判据是同一句 ——「找得到」和「关系可见」是两件事，一个角色二十条边会毁掉画布。

## 4 · 归属 = 打标签，**不是搬家** ✅ 已拍板

旧版 `fusedIntoNodeId` 会把散图复制进 `referenceAssets` 并折叠原节点。
**2026-07-30 已退役这条写入与渲染通路**：本地和服务端项目水合时会幂等
清除旧字段，原节点在原位置恢复可见；节点、边、位置和嵌套参考元数据均不丢。
解析器暂时保留 deprecated 字段，只用于让旧 JSON 先通过校验再迁移。

目标模型仍是：**节点留在原地，只被标记归属**。

- 合「成分永不消失」条款
- **一个节点可多归属**（一张合影同时归两个角色）
- ⚠ 连带作废一个待办：memory 记的「`fusedIntoNodeId` 那条通路仍然零边，补真边另开一片」—— **图本来就不该搬家，也就没有边要补**

本次兼容迁移**没有猜测多归属 schema**。旧 `referenceAssets` 可能承载用户写过的
role、label、weight、onStage 等信息，所以暂时原样保存；未来多归属模型需提供
明确的无损落点后再搬迁这些元数据。

## 5 · 「找得到」不画边 ✅ 已拍板

一个角色可能有 20 个节点，**20 条边会毁掉画布**。而且「找得到」和「关系可见」是两件事 —— 与「卡匣降级：只做找到，不做操作场所」同一条纪律。

1. **选中身份卡** → 名下节点在画布上高亮（`--canvas-accent` 环），不属于的降到 subtle
2. **点 `▦ N`** → 清单浮层
3. **点清单里一项** → 镜头飞过去并高亮那一个

### ⚠ 图**不按来源分组**（owner 2026-07-27 拍板）

清单与展开模态里，**所有图平铺成一个列表**，不再分「参考图 / 镜头图」两组。

**理由**：参考图 / 镜头图的区别是**来源**（上传的 vs 生成的），不是**用途**。用户挑图时看的是**长什么样**，来源帮不上忙 —— 按来源分组等于加了一层不影响决策的隔断。而身份卡本身就是个**筛子**，筛子里再隔一道只会让筛的动作更麻烦。

**音色仍单列** —— 它不是图，是另一个模态，混进图网格里既没法看也没法点。

⚠ **「归类」这个动作不在身份卡上** —— 它在**图片卡的工具条**里（「这张图归谁」是图的属性）。身份卡只有反向的「移出」。

## 5.6 · 展开态 = 模态 ✅ 切片 v2 已确认（owner 2026-07-27）

**这是通则的一个有理由的例外，不是破例。**

跨族通则是「**改参数 → 原地长大**」，其理由是**必须一直看见入边**。但身份卡**没有入边**（§5：分类不画边）—— **前提不成立，所以走模态**。

模态配方与图片详情、提示词框扩大态**共用同一套**（见 `canvas-image-card.md` §5）：浅色玻璃遮罩 `rgba(255,255,255,0.72)` + `blur(20px)`，**不是黑纱**。

**内容**：顶条（代表图缩略 + 名字 + 音色 chip + 「换代表图」）· 分隔线 · **平铺的图列表**（§5，不分组）· 选中项目时才出现的批量操作条（「移出 <角色>」/「设为代表图」）。

⚠ **只有反向的「移出」，没有「归类」** —— 站在角色的立场上「把谁踢出去」才是自然动作；「归到谁名下」是图的属性，在图片卡那边做。
