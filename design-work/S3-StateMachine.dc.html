切片 3 · 已应用 / 撤销 底层零 undo 机制，这不是 UI 态而是一套契约

studio-context 那五个 action 全是纯 setter，全文件零 undo / 零快照。 而且最尖锐的一条是：现状没有任何机制知道「值被用户改过」—— 天真的撤销会把用户后来手写的内容一起抹掉，比原问题更糟。

判据：已应用 ⟺ 当前表单值 === 这条建议的值。 整个「已应用」不存状态，每帧从 state 算出来。带来的三个后果都是我们想要的： 用户手改后它自动退回「应用」（因为事实上确实没应用了，撤销随之消失，不会抹掉用户后写的内容）； 刷新后仍然正确（值还等于建议 → 仍显示已应用，但没有快照 → 不显示撤销，诚实）； 同一字段被两条消息先后建议时，只有匹配当前值的那条显示已应用。

快照契约 · 逐动作定粒度（定错了撤销比不撤销更糟）

唯一可参照的既有先例是闭包快照（画布 composer 的模板选择器）。仓库里没有通用 undo 设施，本轮也不建议造一个。
九条转移 · 逐条给答案（现状至少四条没有答案）
情形本切片的答案
重复点同一行已应用态不可点（cursor: default），不是禁用样式——它已经是结果不是按钮。
撤销后再点应用正常，重新存快照（快照是「点的那一刻的值」，不是「最初的值」）。
连点两次撤销撤销后立刻回到未应用态，第二次点不到。
用户手改了该字段已应用自动失效、撤销消失。由判据自然导出，不需要监听。这是最危险的一条，也是整个设计的支点。
切历史会话快照随消息内存态一起丢 → 显示已应用（若值仍匹配）但无撤销。
刷新 / 重新水合同上。promptDraft / setup 已落库，chip 照出；快照不落库，撤销不出。
点「清空」整个会话槽重置，动作条随消息一起消失。工作台的值不回滚——已应用的东西是用户的了。
两条消息先后建议同一字段值匹配谁谁显示已应用。两条建议同值时两条都显示，正确。
历史消息上的动作条可点。⚠ 但首帧不是空态而是一屏历史——若每条都画带边框的配置盒，首屏会是一列盒子墙。见切片 4 的密度决定。
险 换模型有隐藏副作用：目标模型若已在多模型对比名单里，运行名单去重会让这一轮静默少跑一个模型。既有 bug，本切片只标记，但要决定是否在应用前提示。
决 与「复制」的既有反馈是两套时序：复制是 2000ms 自己消失（硬编码 setTimeout，卸载不清 timer）；已应用要留着给撤销。两者同屏并存，差异必须先说清。
