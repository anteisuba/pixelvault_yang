§1

时长统一：不是「某个下拉太慢」，是三套动效词汇并存

台账把这条写成「面板 / Sheet / Popover / 下拉展开 150–250ms，同一条 ease」， 并点名要逐个量 11 个表面。量完发现问题不在单个数值，在于项目里同时活着三套基准， 而其中一套不是任何人选的。

① 全局 canon --duration-fast  .12s
--duration-base  .20s
--duration-slow  .32s
--ease-standard
  cubic-bezier(.22,1,.36,1) 与 constants/motion.ts 同步
② 画布域 --canvas-dur-fast  .15s
--canvas-dur-base  .25s
--canvas-dur-slow  .42s
--canvas-ease-state
  cubic-bezier(.4,0,.2,1) 画布自己的一档，略慢
③ shadcn 原语 进场  150ms（下拉/popover/select/tooltip）
dialog  300 进 / 200 出
sheet   500 进 / 300 出
ease = 浏览器默认 ease 没用上面任何一套
第三套是没人选的。它是 shadcn 模板自带的硬编码值 + Tailwind 的默认动画曲线 （ease = cubic-bezier(.25,.1,.25,1)）。台账点名的 11 个表面里， 除了画布自己写的那几个，其余全落在这一套上 —— 也就是说「同一条 ease」这条判据 今天是不成立的：画布里的过渡走 (.4,0,.2,1)，画布里弹出的下拉走浏览器的 (.25,.1,.25,1)，两者贴在一起出现。

⚠ 另外两个**出带**的：sheet 500ms 进场（判据上限的两倍）、 dialog 300ms 进场。
⚠ 顺带订正台账：§13.2 要逐个量的清单里有 E2 项目菜单 —— 它在批 2 里已经不存在了 （项目管理搬进左面板，顶栏那个下拉整个删掉）。清单该减一。
§2

左面板展/收：没有动效，而 CSS 注释早就把这件事指给了这一批

实测 .canvas-left-panel 的 computed 值是 transition-property: all / duration: 0s —— 296px ↔ 56px 是硬切的。

这不是疏忽。canvas.css:1550 的注释写着：
「⚠ 这里故意不写 transition: width：真机实测带上它之后这条过渡永远不推进， computed width 卡在旧值不动。根因多半是内容区在同一次 commit 里被条件卸载，宽度过渡 每帧被重置。展开/收起的动效属于「动效十条」那一片，到时候用内容区的 opacity/transform 做，不要再回来给 aside 的 width 加过渡。」

—— 就是这一批。而且它连做法都指定好了。

⚠ 我在批 2 给 CanvasLeftPanel.tsx 写的注释说「过渡仍由 .canvas-left-panel 的 transition: width 负责」，与实测和这条注释都矛盾 —— 那句是错的，一并订正。

§3

要你拍板的两件

① 三套词汇怎么收？
A · 收成一套 —— 画布 token 直接指向全局 canon。 代价：全画布过渡手感整体变化（.15→.12 / .25→.2 / .42→.32，ease 也换）， 而 .42s 那一档是给「画布给助手让位」这种大位移专门留的。

B · 保留两层，把第三套并掉（推荐） —— 全局 canon 管通用 UI、画布 token 管画布专属，两者各自内部一致； shadcn 原语那套硬编码 + 浏览器 ease 并入全局 canon。 这样「同一条 ease」在每一层内部成立，而画布确实需要的略慢一档也保住。

C · 只修出带的 —— 只把 sheet 500→、dialog 300→ 拉进 150–250， 其余不动。最小，但「浏览器默认 ease」这条不解决。
② 左面板动效做到哪一层？ 我建议 按 CSS 注释指定的做法：内容区 opacity + translateX， 不给 aside 的 width 加过渡（那条路真机验过走不通）。 上面 demo 右边就是这个效果。
⚠ 若你想要连 rail 宽度一起平滑，那要改成 motion 的 layout 动画， 改动面大一档（要动 React Flow 旁边这块 chrome 的挂载结构），我会另开一片。
