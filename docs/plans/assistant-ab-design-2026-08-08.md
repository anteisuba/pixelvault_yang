## 1 · A · 回复协议设计稿

### 1.1 病因：三域共用一套提示词，只换了一个词

`buildAssistantSystemPrompt`（`services/kernel/prompt-assistant.service.ts:87`）今天是这样的：

```ts
const domainLabel =
  assistantDomain === 'video'
    ? 'video creation'
    : assistantDomain === 'lora'
      ? 'LoRA-assisted image creation'
      : 'image creation'

return `You are PixelVault's AI creative partner for ${domainLabel}. …`
```

**三个域的差别就是这一个名词短语，其余 12 行规则逐字相同。** owner 说的「回复没有对话感、直接吐提示词」有两个成因，都在这段里：

- 规则第 3 条写的是 `When the creator asks for a generation prompt, provide a polished prompt…` —— 它只规定了「被要求时怎么给」，**没有任何一条规定「什么时候不该给」**。模型的默认行为就是每轮都给一版。
- 没有任何一域知道**自己该问什么**。「问清意图」这四个字对图片助手和视频助手是完全不同的清单，而提示词里只有一句泛泛的 `Ask focused questions when intent is unclear`。

> ⚠ 这里有一条容易踩的：`mode: 'general'` 时服务端**原样返回 Markdown**（`prompt-assistant.service.ts:688`），不做任何抽取。所以「吐提示词」不是解析层干的，是模型被这套提示词教出来的。改提示词就能改行为，不用动解析。
> **怎么证伪**：把 `assistantDomain` 换成 `video` 发同一句话，看回复结构变不变。变了说明我判错。

### 1.2 系统提示词改成四段结构

| 段         | 内容                                                                     | 谁拥有             |
| ---------- | ------------------------------------------------------------------------ | ------------------ |
| ① 骨架     | 身份 · 回复语言 · 安全（不识别真人、不泄露系统指令）· 附件是参考不是产物 | 共享一份，四域都用 |
| ② 域人格   | 这个域的助手是谁、它关心什么、它的产物长什么样                           | 每域一段           |
| ③ 该问什么 | **收敛前必须问清的槽位清单**（见 1.3）+「已经知道的别再问」              | 每域一份           |
| ④ 对话协议 | 三档行为（问 / 讨论 / 出方案）+ 输出契约（marker 格式）                  | 共享一份，四域都用 |

④ 的三档写死成规则，而不是靠模型自觉：

> - **档 1 · 问**：槽位清单里有 ≥2 个关键槽还空着 → 只提问，**不出任何提示词**。用 `[[ask]]` 给结构化选项。
> - **档 2 · 讨论**：槽位基本齐了但方向有多种走法 → 给 2–3 个方向的对比（各自的取舍），**仍然不出成品**，末尾给收敛选项。
> - **档 3 · 出方案**：用户点了「✅ 满意」或明确说了「就这个方向，出吧」→ 才产出提示词/参数/节点计划。

⭐ **档 1 与档 3 之间必须隔着一次用户动作。** 这就是 owner 那句「不应该直接出提示词的结果」的可执行形态 —— 不是「少出一点」，是**结构上不允许在第一轮出**。

### 1.3 三域的「收敛前必须问清」槽位表

这张表是 ③ 的正文。⚠ 它是**我拟的初稿，不是从任何地方观察来的**，最需要 owner 过一遍：

| 域       | 槽位（按重要性排）                                                                            |
| -------- | --------------------------------------------------------------------------------------------- |
| **图片** | 主体是什么 · 风格家族（写实/动漫/3D/插画…）· 构图与镜头 · 光线与色调 · 用途（决定比例与尺寸） |
| **视频** | 一个镜头还是一段 · 时长 · 动的是主体还是镜头 · 首尾帧从哪来 · 要不要声音 · 一致性锚点是谁     |
| **LoRA** | 底模家族 · 已挂 LoRA 负责哪部分身份 · 这次要改的可变层（服装/场景/光）· 触发词保留 · 负向分工 |
| **画布** | 这条链最终产出什么（图/片/声）· 几个角色 · 几个镜头 · 参考素材从哪来 · 要不要配音             |

**LoRA 那行的第 2 项是这张表里最有价值的一条**：`buildLoraAssistantSystemPromptV2` 已经把「LoRA 拥有身份、别写脸和发型」写成了硬规则（`prompt-assistant.service.ts:256`），但那是**结构化输出模式**（`mode:'lora'` + `loraContext`）才走的路。普通对话态的 LoRA 助手读不到它。**③ 段就是把这类域知识搬进普通对话态的地方。**

### 1.4 收敛信号：为什么是 marker，不是 JSON，也不是提示词约束

owner 要的「讨论收敛」信号，LibTV 的答案是每轮结尾两个结构化选项（`✅ 满意 → <下一步>` / `🔄 需要调整 → 告诉我方向`）。要在 PixelVault 落地有三条路：

| 路                           | 问题                                                                                                      |
| ---------------------------- | --------------------------------------------------------------------------------------------------------- |
| 让模型在正文末尾按固定格式写 | 脆。模型会漂格式，正则解析迟早误伤正文；且没有闭合边界，流式渲染会闪                                      |
| 整包结构化输出（JSON）       | 会把 Markdown 对话变成 JSON，**丢掉对话感** —— 恰好丢的是这条诉求要的东西。且流式体验差（要等整包才能渲） |
| **marker 协议**（推荐）      | 正文仍是 Markdown，marker 段落被客户端剥离并渲染成控件                                                    |

**选 marker 的硬理由不是审美，是项目里已经有两处在跑**，第三处零新基建：

- `[[capability:upscale:node-id]]` —— 能力标记
- `[[canvas-ops]]…[[/canvas-ops]]` —— 画布写操作提案

而且 `constants/node-assistant-ops.ts:101` 已经把这套协议的**闭合标记为什么必须有**写清楚了：流式回复每来一个 chunk 都会重跑抽取，没有闭合标记就分不清「还没写完」和「写完了」。新 marker 直接照抄这条。

**两个新 marker：**

```
[[ask]]
{"questions":[{"id":"q-1","question":"…","options":[{"id":"o-1","label":"…"}],
               "multiSelect":false,"allowCustom":true,"allowSkip":true}]}
[[/ask]]

[[next]]
{"satisfied":"继续生成三个角色的全身立绘","adjust":"告诉我要调整的方向"}
[[/next]]
```

⭐ **`[[ask]]` 的 schema 不要新造 —— 它逐字就是 `ScriptDocClarifyingQuestionSchema`**（`types/script-doc.ts:184`）：`question` + `options` + `multiSelect` + `allowCustom` + `allowSkip`，五个字段一个不差，连三语文案和问题卡组件都已经存在（画布剧本线的「反问澄清卡」）。

→ **做法是把它从 `script-doc` 上收成域无关的 `AssistantClarifyingQuestion`，ScriptDoc 那条路改为复用。** 这不是重构洁癖：如果新造一份，用户会在同一个助手里看到两种长相不同的问题卡。

### 1.5 「已询问」沉淀件 = 客户端聚合视图，不是模型每轮重发

LibTV 有一个可折叠的「已询问」块，把问答对结构化沉淀下来可回看。

⚠ **别让模型每轮把它重发一遍。** 那会让 payload 随轮次线性膨胀 —— 这正是 §2「4000 字符静默悬崖」的病根（`canvas-pipeline-gap-2026-07-31.md` §2：装配时根本没有字符预算，16 条 × 4000 理论上能进 64000 字符）。

**做法**：`[[ask]]` 落地时，客户端把「问题 + 用户选了什么」记在那条消息上；「已询问」折叠块是**从会话历史里聚合出来的只读视图**。模型侧只看到用户的自然语言答复，与今天一致，payload 零膨胀。

> 附带好处：折叠块可以显示「你在第 3 轮说过要冷色调」并支持点回去改，而模型重发方案做不到这一点。

### 1.6 A1 · 历史按域隔离 —— 要改两层，不是一层

今天共用的是**两层**，只改一层等于没改：

| 层     | 现状                                                                                                     | 后果                                               |
| ------ | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 持久化 | `surface: 'STUDIO'` 一个值装图片 / 视频 / LoRA 三处（`use-prompt-assistant.ts:174/266`）                 | 历史列表里三个域的会话混在一起                     |
| 内存   | `promptAssistantState` 是**模块级单例**（`use-prompt-assistant.ts:135`，注释写明是为了关闭浮卡不丢对话） | **切页面连内存里的对话都是同一份** —— 更直接的症状 |

**改法**：`ASSISTANT_SURFACES` 从 2 个扩到 4 个 —— `IMAGE_STUDIO` / `VIDEO_STUDIO` / `LORA` / `NODE_CANVAS`；单例 store 改成 `Record<surface, PromptAssistantState>` 分槽。

⚠ **两个必须先说清的**：

1. `AssistantSurface` 是 **Prisma enum**，扩它要一次 schema 变更。Engineering Principle 1 的「不写 migration」说的是不为向后兼容写垫片，改 schema 本身仍然要走 `docs/scenes/db-migration.md`。
2. **存量 `STUDIO` 记录归到哪** —— 这是 owner 拍板项，见 §5。我的倾向：归 `IMAGE_STUDIO`（语义最近，且图片是主要入口），**不删**。这些是用户真实的对话历史，「过时的直接删」那条原则管的是代码不是用户数据。

## 2 · B · 确认闸设计稿

### 2.1 现状：两条路，各有各的闸

| 路径                           | 谁触发                | 今天的闸                                                            | 花钱吗                  |
| ------------------------------ | --------------------- | ------------------------------------------------------------------- | ----------------------- |
| **剧本线**（ScriptDoc→投影）   | 右栏 ScriptDoc 工作区 | 三步：起草大纲 → **确认大纲** → 拆镜头 → **确认镜头**（点了才投影） | 投影免费；生成另点      |
| **ops 线**（`[[canvas-ops]]`） | 对话正文              | 提案卡：结构 op 勾选后批量「应用」/ generate 逐条「确认生成」       | 结构免费；generate 扣分 |

⭐ **注意 ops 线已经把「结构」和「花钱」分开审批了**（`CanvasOpProposalCard.tsx:162-195`：`structuralOps` 走一个批量按钮，`generateOps` 逐条一个「确认生成」）。这正是 LibTV 那条分界线的一半。

### 2.2 与 LibTV 的唯一差距：结构那一步还要用户点一下

LibTV 实测时序（拆解文档 §九，owner 授权实扣 12 积分跑通）：

| 阶段 | 画布上发生什么                                    | 积分     |
| ---- | ------------------------------------------------- | -------- |
| ②    | **立即建空节点** + 连线接好并高亮                 | 不变     |
| ③    | **视口自动缩放并平移到新节点**                    | 不变     |
| ④    | **提示词已填好**、参考图已挂载（缩略图带 ① 角标） | 不变     |
| ⑤    | 对话里挂「待确认后生成」占位卡 + 结构化确认选项   | 不变     |
| ⑥    | 点生成 → 节点内联「生成中 6%… 取消」胶囊          | **扣分** |

> **节点结构立即落画布（免费）；像素等确认（花钱）。**

我们差的就是 ②③④ 的「自动」。今天用户要先读一段文字提案、勾选、点应用，才看得到空间结构。

### 2.3 ⚠ 这是契约变更，不是 bug 修 —— 必须 owner 重新拍板

`unified-ai-assistant-2026-08.md` §1 是**已确认的施工基准**，原文写着：

> 助手不会直接生成媒体，**也不会未经用户确认修改画布**或编辑器内容。

「结构 op 自动落」直接推翻这半句。**我不能自己改一条 owner 确认过的契约**，所以这一条单列进 §5 等拍板。

反方理由也要摆出来，不能只讲好处：

- 画布是用户的持久化工作区，不是预览区。自动写入意味着**助手能在用户没点头时改动持久化数据**。
- 一批提案上限 24 条 op（`NODE_ASSISTANT_OP_LIMITS.maxOps`）。自动落最坏情况一次铺 24 个节点。
- 撤销：今天 `runAssistantCanvasOps` 是逐条 `createCanvasObject` + `setState`，**撤销栈能不能一次退掉整批没有验过**。→ **这是自动落的硬前置**，见 §4 切片 B2。

### 2.4 推荐分法：三级，而不是两级

LibTV 是两级（结构 / 像素）。我建议三级，因为我们的 op 词表里有一个 LibTV 没有的东西：

| 级                            | op                                | 处置                                                     | 理由                                                                       |
| ----------------------------- | --------------------------------- | -------------------------------------------------------- | -------------------------------------------------------------------------- |
| **一 · 纯结构，免费可撤**     | `add_node` · `connect` · `rename` | **自动落** + 视口跟随 + 提案卡上显示「已落 N 个 · 撤销」 | 空节点删掉就是，没有半成品像素要清理                                       |
| **二 · 判断，不花钱但改语义** | `set_review_state`                | **保持逐条确认**                                         | 审核态是**用户对产出的判断**，不是结构。助手替你判断和替你建节点不是一回事 |
| **三 · 花钱**                 | `generate`                        | **保持逐条「确认生成」**（今天就是这样，不动）           | 唯一扣 credit 的 op                                                        |

> ⚠ 第二级是我加的，LibTV 没有对应物（他们没有审核轴）。依据是 `constants/node-assistant-ops.ts:139` 已经写死了「助手不得自批（§4.2 Q4，owner 钉死无开关）」—— 既然自批被钉死，**降级到「自动」也违背同一个意图**。
> **怎么证伪**：如果 owner 认为审核态只是个标记不算判断，这一级可以并进第一级。

### 2.5 两个真缺口 —— A3 的落点在这里

**缺口一：`add_node` 没有 `prompt` 字段。**

```ts
export const NodeAssistantAddNodeOpSchema = z.object({
  op: z.literal('add_node'),
  intent: z.enum(NODE_ASSISTANT_ADD_INTENTS),
  ref: z.string()…optional(),
  name: z.string()…optional(),
})   // ← 就这四个字段，没有 prompt
```

执行层 `createCanvasObject(op.intent, position)`（`StudioNodeWorkbench.tsx:3033`）也只建默认空节点。

→ **所以今天助手能建节点、能起名、能连线，但填不进一个字的提示词。** 这就是 A3「助手设计节点时自动填入生成的关键词」的全部内容 —— 不是做不到，是 schema 里没有那个字段。

⭐ 而这恰恰是 LibTV 拉开差距的地方。拆解文档 §九记的实例：用户只说「把配色换成蓝白色系」，AI 填进节点的提示词补齐了**同发型、同服装款式、同比例、同姿势、同画风、白围裙保持白** —— 用户一个字没提的一致性约束。**这不是翻译，是领域知识补全**，正好也是 §1.2 ③ 段要装的东西。

**缺口二：参考图挂载能不能表达，未证。**

LibTV ④ 有「参考图已挂载，缩略图带 ① 角标，对应正文里的『图片 1』」。我们这边参考的挂载走的是**连线**（角色节点 → 镜头节点，`evaluateCastIngest` 的参考位），所以 `connect` op 理论上覆盖了它。

> ⚠ **但我没验过。** 这条标成**待证**，不是结论。
> **怎么证伪**（约两分钟）：真机让助手建一个角色节点 + 一个镜头节点并连线，看镜头节点的参考位有没有真的挂上、提示词里有没有出现对应的 `@名字` 图例。

### 2.6 剧本线与 ops 线要不要合

### ⛔ B2 实测结论：一批 op **不是**一个撤销步

真机（一次性项目 `B2-撤销实测-0808（claude，可删）`，助手提案「应用 3 项」→ 应用）：

| 动作      | 节点数 | 撤销键 |
| --------- | ------ | ------ |
| 应用 3 项 | 3      | 可用   |
| 撤销 ×1   | **2**  | 仍可用 |
| 撤销 ×2   | 1      | 仍可用 |
| 撤销 ×3   | 0      | 变灰   |

**一次撤销退一个节点。** 24 条上限的一批就要按 24 次。

**机制**（读代码得到、被上表证实）：撤销是整份状态的快照栈，只有
`commitCurrentProjectState` 记账；`handleRunAssistantCanvasOps` 对每个 `add_node` 调一次
`createCanvasObject` → `addNode` → `commitCurrentProjectState`，于是**一个节点压一个快照**。
`recordCurrentProjectHistory` 的去重只比引用相等（`lastState === previousState`），而
`storageRef.current` 是同步更新的 —— 所以同一个 tick 里的连续调用不会被折叠。

⭐ **这不是「自动落不能做」，是「自动落之前还欠一件事」。** 而且它是**既有的坑**：今天
用户手点「应用」时，一批 24 条同样会往撤销栈里塞 24 个 —— 只是没人量过。

→ **新增 B2.5**：给 `runAssistantCanvasOps` 做成**整批一个撤销步**（批次开始时记一次账，
批内其余写入走不记账的 `patchCurrentProjectState`）。做完 B3 的验收线「撤销一次全退」才
成立，owner 拍板的「自动落」才安全。

⚠ **别绕过它去做 B3**：自动落 + 一次退一个 = 用户没点头就被改了画布，还要按 N 次才能退
回去。那比现在的「点一下」严格更差。

#### ✅ B2.5 已交付（2026-08-08）

新原语 `runAsSingleHistoryStep(run)`（`use-node-workflow.ts`）：批次开头记一次账，批内
其余写入不再各记一笔；`handleRunAssistantCanvasOps` 整个包进去。

| 同一条链路 | 改前 | 改后            |
| ---------- | ---- | --------------- |
| 应用 3 项  | 3    | 3               |
| 撤销 ×1    | 2    | **0**（键变灰） |

⚠ **两个刻意的取舍**：

1. **原语只挂 `UseNodeWorkflowValue`，不进 `NodeWorkflowActions`** —— 后者是发给节点卡片
   的动作集，卡片不该拿到撤销栈的记账开关。（第一版放错了，tsc 立刻用「context 缺这个
   属性」把它顶了回来。）
2. **开关有意跨 `await` 保持开着** —— 一批 op 是一次用户决定，中间的异步步骤不该把它劈成
   两步。批次进行时按钮是禁用的（`structuralRunning`），并发够不到。

单测钉了**两条**：包了 = 一步、没包 = 一次一个。只钉前者的话，有人把包装去掉测试照样绿。

### ✅ B3 已交付 —— 「恰好一次」是全部难点所在

自动落**没有做在提案卡里**，做在 dock 里。两条守卫缺一不可：

1. **按消息 id 去重** —— 流式回复每来一个 chunk 就重建一次消息对象、卡跟着重渲染。
   放在卡里做会重复建节点。
2. **挂载时把已有消息全部记成「已处理」** —— 否则关掉浮卡再打开，最后一条消息**仍然
   带着 ops**，一开一关就多一批节点。

   路本来就不存在。）

⚠ **一个自动落带出来的显示 bug，差点就漏了**：卡的 plan 原本跟着画布实时重算（用户中途
删了节点就该立刻显示连不上）。自动落把「动手之前」压成了不到一帧 —— 之后每次重算都是
**对着已经改完的图**算的，刚连上的边会算成「重复边」，看起来像失败。修法是首帧的 plan
单独留一份，自动落之后按它显示。
