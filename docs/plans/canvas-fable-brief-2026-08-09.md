## 4. Owner 口述痛点 → 设计问题（待 Fable 结构化）

下列为 **用户原意压缩**；Fable 须逐条变成：现状事实 / 用户目标 / 可选模型 / 推荐与风险。

### 4.1 节点膨胀与合并

- **现象**：图片相关能力被拆成多个节点（至少：通用图片、镜头图、关键帧；代码侧还有角色图/场景图/特写 role）。
- **Owner 直觉**：「图片 / 镜头 / 关键帧」应 **合在一起**。
- **设计问题**：
  - 合并的是 **添加菜单的入口**、**节点外观**、还是 **图上只剩一种 image 节点 + role 切换**？
  - 合并后如何避免「一个节点既是上传槽又是生成器又是关键帧」导致参数地狱？
  - 与已存在的统一 `image` + `NODE_IMAGE_ROLE_IDS`（character/background/shot/frame/closeup）如何对齐或简化？

### 4.2 连线（边）

- **痛点**：连线语义不清（谁供给谁、什么该常显、什么该折叠）。
- **设计问题**：连线是「数据流」「引用关系」「时间线顺序」哪一种心智？LibTV/Krea 怎么做？我们是否继续有向边，还是需要并列的「引用 chip」模型？

### 4.3 Token

- **痛点**：「token 有问题」（@ 引用 / 容量 / 展示 / 与 prompt 同步）。
- **设计问题**：
  - Token 是 **prompt 内第一公民** 还是 **连线的镜像文案**？
  - 空名字、重名、删除节点后 token 失效如何呈现？
  - Composer 上方的素材条 vs 画布上的边，是否双轨冗余？

### 4.4 输入框上方的「素材」

- **痛点**：要不要 **新开一个节点** 专门管「当前生成用到的素材」？
- **设计问题**：素材区是 **节点本体**、**composer 的上下文条**、还是 **详情面板的引用管理**？与 `ReferenceManagerPanel` 现状如何收敛成一种心智？

### 4.5 上传图 vs AI 生成

- **Owner 理解/疑问**：上传的图片是不是 **不能用 AI 生成、只能编辑**？
- **设计问题**（先查清事实再设计）：
  - 空图节点「上传 / 生成 / 从资产选」的能力矩阵真实如何？
  - 用户心智是否应固定为：**有源图 = 编辑轨，无源图 = 生成轨**，还是允许「对上传图再文生/图生」？
  - UI 如何让「生成」与「编辑」入口不互相伪装？

### 4.6 图片编辑与标注

- **需求**：图片编辑需要 **标注**（对局部说想改什么）。
- **已有草案**：`canvas-image-card.md` P2「区域标注 + 指令」——**不是自由画笔**，是区域 + 文字意图。
- **设计问题**：标注落在节点卡、全屏编辑 workspace、还是侧栏？与 Studio Image 编辑的边界？

### 4.7 助手 ↔ 节点互通

- **痛点**：助手和节点怎么互通不清楚。
- **设计问题**：助手是 **导演脑**（投影节点/改剧本）还是 **节点内 copilot**？操作结果如何在画布上可见（autospawn、高亮、待确认卡片）？失败与权限如何大声暴露？

### 4.8 输入框（Composer）怎么设计

- **痛点**：和 Studio 单次输入框混、和 token/素材条抢注意力。
- **设计问题**：Composer 属于 **选中节点的局部控件** 还是 **画布级全局条**？多选/未选中时写给谁？

### 4.9 卡片（收集器）职责混乱

- **Owner 原话**：一直以为卡片只负责 **收集图片**，结果发现也负责 **生成**，乱。
- **产品事实**：收集器卡 = 一致性身份单位（图集 + 可生成补充图 + 绑音色）；视频节点才是「制片」。
- **设计问题**：
  - 如何在 UI 上 **强制区分**「维护身份档案」vs「发起一次生成」？
  - 卡片上是否允许生成？若允许，入口命名与视觉层级如何避免与 seedance/视频节点撞车？
  - 卡匣是「复用注册表」还是「第二种节点库」？
