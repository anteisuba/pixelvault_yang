### 3.2 顺带查实的四条（都影响后面的切片）

**A · 编辑弹窗被卡死在 512px 宽**（阻塞 E2/E3，必须先修）
`CanvasImageEditWorkspace.tsx:563` 写的是 `w-[min(1120px,calc(100vw-2rem))] max-w-none`，但 `dialog.tsx:72` 的基类尾巴是 `sm:max-w-lg`（=32rem=512px）。`max-w-none` 没带 `sm:` 前缀 → 640px 以上视口一律被 `sm:max-w-lg` 压回去。**真机量到：窗口 1920，弹窗实际宽 512**（`getBoundingClientRect().width`）。后果：右栏可用宽 262px 而内容 280px，横向溢出；局部重绘面板里「提示词」输入框被压成一个字一行的竖条，「橡皮擦 / 清空蒙版」被切掉一半。
→ 同仓库里 `BaseModelPickerPanel.tsx:1334` 是写对的：`max-w-none … sm:max-w-none`。**一行修**。

**B · 源图尺寸判错 1024×1024，这多半就是第 4 条 500 的根因**
源图真实 1672 × 941，但弹窗左下角显示「1024 × 1024」，蒙版画布也按 1024×1024 建。原因：`getPositiveDimension()` 只读 `data.mediaWidth ?? data.width`，读不到就**兜底成 1024**；而这个节点是导入的、`mediaWidth` 为空。
⚠ 对照：同一个节点在卡片上显示的是正确的 1672 × 941 —— 因为 `LooseImageCard.tsx:207-254` 多一层 `naturalSize`（`<img>` onLoad 实测）兜底，**弹窗没有这层**。
→ 于是发给 fal 的 `mask_url` 尺寸和 `image_url` 对不上（FLUX Fill 要求同尺寸）。
✅ **已证实**：把蒙版换成 1672×941 原尺寸重放同一个端点，**成功**——Generation 表里留下了 `inpaint / 1440×800 / COMPLETED`、prompt 记作「[inpaint] from external image」的那一行（"external" 是因为重放没带 `sourceGenerationId`）。**同一条链路，只差蒙版尺寸，一边 500 一边出图。**

**E · 扩展画布：唯一一条传 `sync_mode: true` 的能力，结果被自己的 schema 挡在门外**
`image-edit.service.ts:589` 只有 outpaint 传了 `sync_mode: true` → fal 不给托管 URL，**直接把图 base64 内联回来**。实测该响应 `data.imageUrl` = `data:image/png;base64,…`，长度 **2,271,334 字符**。
而 `CanvasDerivedImageOutputSchema.imageUrl` 是 `z.string().trim().min(1).max(4000)` → `placeDerivedImages()` 的 `safeParse` 失败 → 返回 `[]` → `placeOutputs` 弹 `t('editFailed')`「图片编辑失败。」
⭐ **正确的 URL 就在同一个响应里**：`data.generation.url` 是已经落好的 R2 地址，只是 `oneOutput()` 读的是 `result.imageUrl` 不是它。

**F · 顺带炸出来的一条：三条「成功」的能力，落到画布上的是 fal 的临时 URL，不是 R2 持久副本**
真机读画布上派生节点的 `img.currentSrc`，两条是 `https://v3b.fal.media/files/…`。而 `/api/image/edit` 路由自己的注释写着「fal.ai's CDN URL is temporary，所以必须复制进 R2 + 建 Generation 行」——**服务端照做了，画布却把临时那条存进了节点**。→ 这些节点过一阵会变成裂图。
⚠ 这条影响面比 E 大：**超分 / 去背景 / 提取元素三条现在全都这样**。改法和 E 是同一处：派生节点一律用 `generation.url`。

**C · 4x 超分 ≈170s > 路由 `maxDuration = 120`**
本地 dev 不掐这个数所以跑通了，**Vercel 上同一条会 504**。要么默认档改 2x，要么这条走 worker/异步。

**D · 两条自动化/环境事实**（给下一个会话省时间）
① 画笔涂抹**用 CDP 真实鼠标拖拽驱动不了**（`left_click_drag` 打不出笔迹，蒙版 opaque 像素 0）；改用页面内合成 `PointerEvent` 序列即可，实测画出 8844 个像素。所以「手绘能不能用真手画」这条**没被自动化证伪也没被证实**，要 owner 手动确认一次。
② 底图 canvas 被跨域图 taint（`getImageData`/`toDataURL` 抛 SecurityError），**但不影响导出** —— `exportMaskDataUrl()` 只读蒙版那张 canvas，它是干净的。

### 3.4 尺寸链修完了 —— ⚠ 但真机把「根因已证死」推翻了一半，值得记

原判：`inpaint` 500 是因为蒙版 1024×1024 与源图 1672×941 **长宽比**不符。修完「量真实边长」后蒙版变成 **1024×576**（长宽比已经和源图一致）—— **真机重跑，仍然 500。**

→ **FLUX Pro Fill 要的不是同比例，是逐像素同尺寸。** `StudioInpaintEditor` 里 `fitCanvasDimensions` 上方那句注释「fal.ai requires matching aspect ratios」是错的，已就地改掉。

**最终两处改动**：

1. `CanvasImageEditWorkspace`：新增 `resolveSourceDimension()` + 一个 `new Image()` 探针，**量到的赢过字段**。⚠ 与 `LooseImageCard` 的取值顺序**故意相反**：那边这两个数只用于显示，这里要拿去定蒙版边长，位图才是事实源。也不能蹭渲染出来的 `<img>` —— 局部重绘面板压根不渲染 `<img>`，而它恰恰最需要真尺寸。
2. `StudioInpaintEditor.exportMaskDataUrl()`：绘制面继续按 `MAX_CANVAS_EDGE` 收着（4K 源图否则吃 ~64MB），**只在导出这一步**用最近邻放大回源图真实像素（双线性会插出灰边，二值蒙版就不二值了）。

**真机结果**：`POST /api/image/inpaint` **200**，toast「已保存到画廊。」，节点 **17 → 18**，新节点 `img.currentSrc` 是 `cdn.anteisuba.com`。
**护栏**：`StudioInpaintEditor.test.tsx` 加两条 —— 大图导出 `1672x941`（且断言**没有**导出 `1024x576`，否则这测试等于没测）、小图不做多余缩放。`CanvasImageEditWorkspace.test.tsx` 加两条 —— 量到的赢过声明值、量不到时退回声明值。

⚠ **教训**：08-18 白天我写「根因已证死」是**超前了**。当时的证据只是「1672×941 的蒙版能成功」，那只证明了**同尺寸可行**，没证明**不同尺寸的失败原因是比例**。真正证死要等到「比例对、尺寸不对」这一档也跑过一次。

### 7.4 三个结构方向

同一组真实内容（一次 4 模型 × 1 张的结果）、同一状态矩阵。差异在**空间结构**，不在配色。

**A · 舞台接管（Stage takeover）**
选中一张 → 右侧结果区整片切成编辑态：大图占主区，工具收在右侧一栏，顶部一条「← 回到结果」。左参数栏不动。

- 优点：编辑得到**最大画面**；与刚统一的画布弹窗（大图 + 右侧 320px 工具栏）**同构**，Q5 的对齐几乎零成本；不引入新层级。
- 风险：编辑时看不见其它结果 —— 多模型对比时「边比边改」断了；返回要记住图墙的滚动位置与选中格。
- 适合：首发验收场景（三视图批量标注）——那是**一张图上做很多事**，不需要看别的。

**B · 右侧编辑栏（Third column）**
图墙保持不变，选中一张后从右侧滑出 320–360px 编辑栏，选中格高亮，其它格仍可点可切。

- 优点：保留对比语境，能在多张之间来回改；不打断生成流；选中态天然有宿主。
- 风险：**三栏（288 + 舞台 + 340）在 1440 以下把舞台压瘦**，而涂抹/拉框是主力交互，画面一小精度就垮；这恰好是我们刚在画布上修掉的那个病。
- 适合：以「挑」为主、编辑只是轻修的用法。

**C · 结果带 + 编辑台（Filmstrip + bench）**
选中一张后，舞台上下分：上方压成一条横向缩略带（本次结果 + 最近结果），下方是编辑台（大图 + 工具）。

- 优点：既留住「在多张之间切」，又给编辑一整片宽度；**缩略带本身就是 Q2 和 Q4 的答案**——选中态和「继续创作」那排合并成同一个东西。
- 风险：垂直空间切两段，1080 以下编辑区高度吃紧；缩略带与左参数栏在信息上有重叠（都在讲「这批是什么」）。

**我的推荐：A，并把 C 的缩略带作为可嫁接件。** 理由：E2/E3 的主力交互是在图上精确画（框 / 笔刷 / 多框编号），**画面尺寸是第一约束**；A 给得最大，且与画布已经统一好的形一致，E5 直接共用组件。缩略带可以在 A 之上作为可选的一条（编辑态顶部），不必现在就定。

### 7.5 关键切片（选向后只深化这一个）

**「一张三视图 + 多框注释」的编辑态**，因为它同时暴露：大图比例够不够画、工具栏放不放得下框/笔刷切换、多框编号清单往哪儿长、以及「应用」与「回到结果」的动作优先级。配套只补它直接相关的四态：**空（没选图）/ 生成中 / 失败可单张重试 / 已选中**。

### 7.6 ⚠ 我没被点名、但认为必须一起解决的四条

1. **编辑派生 generation 的 prompt 是机器写的**（`[inpaint] from generation …`）。它现在会灌进用户提示词框（Q4），将来也会出现在 Gallery 和配方里。建议：派生 generation 保留**源图的 prompt**，编辑指令另存字段。
2. **失败的单张能不能只重试那一张** —— 图墙已经做到了（每格自报状态），编辑面必须同样做到，否则一步失败要重来整轮。
3. **编辑历史（E4）和注释清单（E3）是同一个东西**，别做成两份数据。账本 Q3 的推荐就是冲着这条去的。
4. **`/studio/edit` 那个 307 重定向该退役**：它今天把人重定向到画布，而方向已经反过来了。等 E1 落地后，它应该指向工作台，或者直接删掉（`ROUTES.STUDIO_EDIT` 与 `studioImageEditPath` 已经零非测试消费者）。
