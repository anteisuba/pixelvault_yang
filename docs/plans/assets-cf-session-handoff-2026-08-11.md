## 一、我判错了什么，模式是什么

本轮五次，**前三次是同一个病的三种发作**：把「上一轮的产物」当成既定事实继承，没问它自己成不成立。

### 1. ⭐ 把「上一轮为解决 X 打的补丁」原样抄进新设计，而那个补丁自己已经变成新的 X

给 picker 设计文件夹选择时，我直接用了**横向 chips rail**。owner 一句「文件夹多了这边就不好选择了」点破 —— 那正是**原始需求 F1「文件夹选择目前是横向的，很难选」本身**。

查历史才知道钟摆已经荡过一次：`280px 竖树（吃 40% 宽）` → 被否 → `横向 chips`（上一轮的补丁）→ 现在被否。我抄的是补丁，不是答案。

> **模式**：继承上一轮的实现时，只问「它是什么」，没问「它当初解决了什么、有没有引入新问题」。
> **下次**：看到「为解决 X 而做的 Y」，先问 **「Y 自己有没有变成新的 X」**。尤其当 Y 是上一轮刚打的补丁。
> 定案见 page §8.1（176px 可折叠导航栏 = 钟摆的第三个位置）。

### 2. 同一个病，发作在排序上：「最近使用」名字承诺的事一件也没做

我在 page 文档里写「复用 `sortFolderNodes` 已有逻辑，不重造」。owner 问「排序是怎么做的」，顺着查才发现 `recent` 档排的是 `Project.updatedAt`，而**全仓只有两处写 Project 行**（重命名/改父级、软删）—— 往夹里加素材改的是 `Generation.projectId`，**不碰 Project 行**。

实测 7 个夹：**4 个 `updatedAt` 完全等于 `createdAt`**；`dainia` 24 张素材陆续加入，时间没动过。

> **模式**：顺着字段名认语义，只查「谁读它」，没查「**谁写它**」。
> **下次**：判断一个字段的语义，**grep 它的写入方**，不是读取方。这是 memory 里 `reference-count-all-victims-of-a-shared-constant` 那个病的又一种形态。
> ⚠ 更要命的是：**这是我自己上一轮做的功能**，而我差点把它当既定事实传给施工会话。

### 3. 同一个病，发作在边界上：跨域改了别的会话在飞的文件

6c 切片我把 `GenerateComposer` 列进「要改」——它在 `node/` 下属画布域，而**我这个包的 Non-goals 第一条就写着「不接管画布并行任务」**。自己写的禁令自己违反。

owner 说「VideoComposer 那个我看下」才让我回头对边界，重数发现 17 个调用文件**按域正好对半开：非画布 8 / 画布 8**。

> **模式**：写 Non-goals 是开工时的动作，之后拆切片时没再回头对。
> **下次**：**每次拆新切片，对一遍自己包的 Non-goals**。禁令写下来不等于执行时会想起来（这条 `week-backlog-session-handoff-2026-08-07.md` §一.11 已经说过一次，我又犯了）。

### 4. 说「点击开右滑 Sheet」，实际它早就是全屏的

回答「全屏灯箱是什么」时，我本来要拿它跟「现状的右滑 Sheet」对比。查代码：`MediaDetailViewer.tsx:153` 是 `fixed inset-0 max-w-none`，**已经是全屏 + `object-contain` + 420/480px 侧栏**。缺的只是 `←→` 连续翻阅和 filmstrip（viewer 里搜不到任何 next/prev，调用处也只传单个 `generation`，没有列表上下文）。

> **模式**：拿印象里的现状去跟新方案对比。
> **下次**：**任何「现状是 X，改成 Y」的句式，X 必须现查**。这次差点让一个「已完成 80%」的功能被当成新功能立项。

### 5. 三次「不够紧凑」，两次我理解错了方向

owner 两轮说「不够紧凑」，我第一轮改间距（顶栏 56→50、gap 8→6…），第二轮他直接圈出右侧空白才明白：**他说的不是间距太大，是布局没铺满容器**。三个成因全是我造的——`max-width:1600`、超宽图独占整行、末行不铺满 + 容器宽手算 padding 算错。

> **模式**：把用户的现象描述直接当成原因描述。
> **下次**：「不够紧凑」这类主观词，先**程序化量一遍**（`行宽 / 容器 clientWidth`）再决定改什么。判据不能是目测。

## 二、关键结论是怎么推出来的（规格里只有结论）

### 为什么砍掉「按角色卡聚类」和「按生成批次折叠」

owner 问「有没有更好的分类方式」。我第一反应是这两个——AI 图库的成熟做法（Midjourney 把一次 4 图任务折成一张卡），而且 owner 的文件夹名几乎全是角色名，看起来是天然需求。

**查数据（135 条实测）直接封杀**：`characterCardId` **0 条** · `cardRecipeId` **0 条** · `runGroupId` **仅 1 条**。

> 这就是「依据的主人在不在链路上」那一问救回来的一次。**提之前查了，所以没把设计建在沙上。**
> ⭐ 但留了个观察值得下一轮记着：**owner 在手工做 `characterCardId` 本该自动做的事**（夹名 = dainia / 爱弥丝 / 流萤 / 达妮娅 / キサキ）。哪天生成链路开始回填这个字段，「按角色自动成夹」是这页最大的一次跃迁。**现在不做，但别忘了。**

### 为什么 picker 必须保留单选/多选两种（不能统一）

19 个生产挂载点只有 2 个多选。判据不是「允不允许多选」，是**消费端是槽还是集合**：填一个槽（替换语义）vs 往集合里加（追加 + 有容量）。

全改多选 = 17 个高频入口从 1 击变 2 击（选参考图是最常做的动作），且单槽消费端收到数组后每个调用点都得自己决定「取哪个算数」——把决策推给了 19 个地方。**是纯回退。**

→ 详见 page §8.3。这条推理链没写进 page 的只有一句：**我一开始是想统一的**，算完 17/19 的账才放弃。

### 为什么「置顶」是独立一层而不是第四种排序

owner 说「排序不能指定」。做成「自定义排序」档会出现无解问题：**按名称排序时我的手动序去哪了**。做成正交的 pin 层就没有这个矛盾——**排序管全体，pin 管头部**，而门牌行本来就只显示头部那几个。所以 pin 的真正目的不是「排 100 个夹」，是「决定首页那一行是哪几个」。

⚠ owner 2026-07 曾在「排序下拉」与「手动拖动排位」间选了前者。**这次不是推翻它，是补它覆盖不到的部分。**

## 六、⭐ 画布参考图改多选：owner 已拍板，交画布会话（含一条高置信预测）

> **owner 2026-08-11 原话**：「我是支持的，但是应该避免刷屏。」
> 归属：**画布域**（`node/**`），不在 Assets 包内施工 —— 本节是交给画布会话的设计输入。

### ⚠ 先证伪这条预测再动手：朴素 `for` 循环会让 N 个节点**叠成一个**

落位算法在 `StudioNodeWorkbench.tsx:2453` 一带：

```js
const existingUpstream = getUpstreamNodes(
  input.targetNodeId,
  workflow.edges,
  workflow.nodes,
).length
const anchor = target?.position ?? NODE_STUDIO_NODE_PLACEMENT.topbarAddPosition
const position = {
  x: anchor.x + referenceSpawn.offsetX,
  y: anchor.y + existingUpstream * referenceSpawn.rowOffsetY,
}
```

`existingUpstream` 读的是**本次渲染的快照**——**同一份文件 3391 行的注释自己写着**：「`workflow.nodes` 是本次渲染的快照。对**已有**节点它是准的，对**本批刚建**的节点它永远是空的」。

→ 同步 `for` 循环里连调 N 次 `spawnReference`，每次闭包读到的 `workflow.nodes` 都是同一份，`existingUpstream` 恒定 → **N 个节点算出完全相同的 position，精确重叠**。用户看到的不是刷屏，是「**我明明选了 3 张，怎么只多了 1 个节点**」。

⚠ **这是预测，不是确认**。而且 **`ReferenceLandingTabs`（现有唯一的画布多选挂载点）正是朴素 `for` 循环**（`handleSelectAssets` 逐个调 `land()`），**它很可能已经中招**。

> **一分钟证伪**：画布上用「参考图落地」多选加 3 张 → 得到 3 个错开的节点（预测错），还是 1 个、拖开才发现下面压着 2 个（预测中）。

### 四条落位约束（「避免刷屏」的具体形态）

| #   | 约束                                                                                                                 | 现成可复用的东西                                                                                                                   |
| --- | -------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **成批落位，不是 N 次单个落位** —— 位置按批内序号累加（`(existingUpstream + i) * rowOffsetY`），或直接走已有的批通道 | 画布**已有**成批建节点的路（助手 ops），`StudioNodeWorkbench.tsx:3390` 注释明写「`spawnReference` 走的是同一条路，只是它只建一个」 |
| 2   | **一批只占一个撤销步** —— 选 5 张后按撤销应一次退干净，不是退 5 次                                                   | `workflow.runAsSingleHistoryStep`，助手批量（B2.5）已为同一问题解决过                                                              |
| 3   | **视口跟随整簇，不是跟随最后一个** —— fitView 到这批节点的包围盒；或干脆不动视口，只给「已添加 N 个」提示            | 已有「selects + fitViews to the new box」的做法（同文件 2928 注释附近的 `handleFocusNode`）                                        |
| 4   | **给 `maxSelection` 一个上限** —— 别让一次选 40 张。建议按「一屏装得下多少」定（8 左右），不是拍脑袋                 | 照抄 `LoraTrainingDialog` 的 `MAX_IMAGES - 已有数` 写法                                                                            |

**落位形状建议**：现在是纵向单列堆叠（`rowOffsetY`）。N 个纵向排会把画布拉得很长 —— **N > 4 时改成两列网格**，簇更接近方形，视觉上才谈得上「不刷屏」。⚠ 这条是建议不是契约，由画布会话按实际 `NODE_STUDIO_NODE_PLACEMENT` 的尺度定。

### 范围
