## 1. 实测（2026-10-07 / 08）

- **300 秒超时是真的，集中在画布**。Vercel 错误聚合里，`POST /api/studio/assistant-operator` 的 `Task timed out after 300 seconds`：10-07 13:00 UTC 查 7 天窗口只有 1 次；16:13 UTC 再查 2 天窗口已是 **7 次**（最后一次在 15:05 UTC，只有一位用户）。另一个会话从 1 小时日志里抄下其中 3 次（14:58 / 15:03 / 15:10 UTC），都是 `domain=canvas`、`priorSteps=24`。
- **原因是一步慢、步数多，不是哪个工具卡住**（另一会话读 AI Gateway 日志，日志只保留 24 小时，我这边没法登录复核）：Grok 4.7 每次调用 10–80 秒，个别到 160 秒，一轮连跑约 11 次就到了 300 秒；DeepSeek V4.1 Flash 每次 28–64 秒，每次输出 6K–14K token，输入在约 26K 和 8–10K 之间交替。另有 4 步是模型对一个失败工具（`unknownAsset`，起因是前端 bug，已在别的会话修）反复重试，全部白跑。
- **代码里能对上的结构**：画布每做一次 `canvas_apply` 写入，这次请求就收尾，由前端落 op、带新快照再发下一次请求（`canvas_sync` 接力，整串最多 16 步）。超时发生在两次写入之间那一串只读步（读状态、查证、看图、重试）上。每一步一次主调用；写提示词、又挂着参考图的那一步还要额外做一次复核调用（失败会再试一次），这和日志里输入大小交替的现象对得上。助手链路**不给输出设上限**（`providerManagedOutput`），Grok 固定用低推理档，DeepSeek 的请求里没有推理相关的字段。
- **其余失败都在 provider 那一侧，换 DO 照样失败**：7 天里 Gemini 90 秒无首包 4 次、安全拦截 6 次，余额不足、限流、模型暂不可用、回复不完整各 1 次。
- **断流现在量不到**：前端断流只改内存里的状态，不落库。库里持久化的 1155 条消息中，⏹ 停止只出现过 1 次。联网查证本身不慢（`ResearchRun` p95 约 4 秒，最长 30 秒）。回合内也从不等图：钱闸规定服务端不能建 generation。
- 量级：7 天内有更新的会话里约 96 条用户消息。`.env.local` 连的就是生产库（见 [cicd](cicd.md)）。

## 2. 不用 DO 能兜住多少（第 0 片，先做）

| 手段                                                                                                                                                                                                                                                                      | 解决什么                                                                     | 解决不了什么         |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | -------------------- |
| **软截止接力**：开新一步之前，本次请求已经用掉 ≥120 秒就主动收尾；正在跑的那一步到 270 秒还没回来，就掐掉这次调用，这一步留到下一次请求重做。收尾发一帧新的停止原因「接着跑」，画布前端照现在 `canvas_sync` 的接力方式自动发下一次请求；其他域显示现成的「从第 N 步继续」 | 300 秒不再被平台杀掉，用户只看到一次自然的接力                               | 关页 / 断网仍会停    |
| **断流落库**：断流时前端在会话里落一行 system 记录，做法和 ⏹ `stopped` 一样                                                                                                                                                                                               | 以后一条 SQL 就能量出断流次数                                                | —                    |
| **同类失败两次就停**：同一个工具因同一个拒绝原因连续失败两次，就收尾说明原因，不再重试                                                                                                                                                                                    | 那 4 步白跑的重试                                                            | —                    |
| **每步记 token 与耗时**：在现有的 `assistant operator step` 日志里补上输入 / 输出 token 和耗时                                                                                                                                                                            | 判断 6K–14K 输出到底是推理还是正文，再决定要不要给助手链路设输出上限或推理档 | 本片只记录，不改上限 |

⚠ 软截止只依赖现有接力，不引入会话态；它把「被平台杀掉」变成了「可续跑的收尾」，对画布而言基本等于去掉了 300 秒上限。DO 额外带来的只有两样：**关页 / 断网后回合继续跑**，以及**回来之后能补看错过的输出**。

## 3. DO 方案：搬什么、留什么

- **DO 只做回合协调，工具环本身留在 Vercel。** 内核约 1.28 万行，依赖 Prisma、各家 provider 适配器和 R2，搬进 Worker 等于重写一遍。DO 按步调用 Vercel 的内部单步接口，每一步都是一次独立的 Vercel 调用（单步最坏约 160 秒加一次复核，在 300 秒以内）。
- **留在 Vercel**：Clerk 鉴权、Zod 校验、限流、全部数据库读写、LLM 调用、工具执行、钱闸。会话持久化也不变，仍由前端负责（见 §4）。
- **搬进 DO**：回合的生命周期（步与步之间的循环、步数与时长上限）、断点存档、事件日志（供重连补放）、停止信号。DO 用自带的 SQLite 存回合状态，**不连 Postgres**，所以不需要 Hyperdrive。只有将来真把内核搬进 Worker 时，才需要重新考虑 Hyperdrive。
- **认证**：DO 调 Vercel 走现有 execution worker 的共享密钥签名（`src/lib/signature-verifiers/internal-execution.ts` 那一套）。浏览器拿 Vercel 签发的短期回合令牌（用户 + 会话 + 过期时间），直接连 Worker 的 WebSocket，不经过 Vercel 中转，所以长连接不占 Vercel 的函数时长。
- **用 Agents SDK 的 `Agent` 基类**（底层就是 DO）：`runFiber` 加上每步之后 `stash` 存档，被驱逐或重启之后在 `onFiberRecovered` 里从存档接着跑；WebSocket 走 hibernation。⛔ 不用 `AIChatAgent`：它的可续流绑定 AI SDK 的消息格式，而我们的流是自定义的结构化事件。
- **一个会话一个 DO**，名字 = 用户 id + 会话 id。所以 durable 模式要求先有会话：第一轮开跑前，前端先 upsert 会话。
- **画布写入改由服务端执行**：单步接口里遇到 `canvas_apply`，直接用 MCP 那条路落库（`applyCanvasBatchV4` + 版本号条件写，见 [mcp](mcp.md) §2），再从库里的新版本重建快照的节点 / 连线 / 时间线三部分，喂给下一步。这样 durable 模式里不再需要 `canvas_sync` 回前端绕一圈。
- **只活在浏览器里的那部分快照**（当前焦点镜、选中 / `@` 的节点、各节点可选的模型、角色库、参考图）在开跑那一刻随请求带上一次，之后不再更新。可选模型按节点类型存，回合中途新建的节点按类型取。开跑前前端先保存一次画布，保证服务端读到的就是用户眼前的版本。
- **冲突照搬 MCP 第 3 条**：用户边看边改，助手下一次写入的版本号会对不上，这时把冲突原样报给模型，让它重读后重做。⛔ 不在服务端自动重放。部署重启时如果正好卡在「写入已提交、存档还没写」之间，重跑那一步会撞上版本冲突，模型重读后会看到改动已经在了，不会重复写；代价是那一批改动在撤销登记簿里缺一条。
- **上限**：一个回合最多 16 步（与现在的接力上限相同），最长 15 分钟（与 DO alarm 的上限、单个待完成 I/O 的 15 分钟窗口一致），先到哪个就停在哪个，停下后可续跑。

## 4. 断线与重连

- DO 把每一帧事件按序号写进事件日志。`message_delta` 例外：它不是正文的真值，不落日志；正在流的那段话由 DO 留在内存里，重连时作为一次增量补发。
- 浏览器连接时带上「最后收到的序号」：DO 先补发之后的全部事件，再接上实时流。前端按条目 id 覆盖、不追加，这条老规矩保证补放不会出现重复行。
- 断网后按指数退避自动重连。刷新页面或换设备打开同一段会话时，向 Vercel 要一张回合令牌，连上 DO，由 DO 告诉前端有没有正在跑的回合，有就从头补放。
- 画布跟随：DO 每次写完画布都会发一帧新版本号，前端版本落后就重新拉一次项目（跟随做法与撤销做法都沿用 [mcp](mcp.md) §6）；步事件照旧带 `inverse`，撤销登记簿照常记录。
- 会话持久化不换主人：哪个前端补放了这个回合，就由哪个前端照现在的方式落库。事件日志在 DO 里保留 7 天；7 天内没人打开，画布改动早已落库，丢的只是这轮的对话文字。

## 5. 停止

- ⏹ 走已经连上的 WebSocket 发一条「停」；WebSocket 断着时，经 Vercel 的停止接口（Clerk 鉴权并校验归属）转给 DO。
- DO 收到后：abort 正在进行的那次单步请求 → Vercel 的 `request.signal` 触发 → 内核走现有的取消路径（LLM 请求跟着断）→ 发 `stopped: aborted` 并写进日志。已经提交的写入保留，和现在一样，能撤销。
- 插话排队不变：仍在前端排队，等到下一个步边界，先停当前回合，再带上 `priorSteps` 开新回合。

## 6. 钱闸与自动生成

- DO 没有任何能建 generation 的路径。为它补一条源码扫描测试，和现有的钱闸测试同一种判据。
- 回合停在生成确认卡上就结束，等用户来按。**自动生成开关只在「确认帧到达时前端正连着」的情况下替用户按**；补放回来的确认帧一律不自动按，免得用户隔几个小时回来，一打开就花了钱。

## 7. 成本（按每月约 420 轮的上界估算）

| 项        | 估算                                                                                                            | 额度                                                                                              |
| --------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| DO 时长   | 有待完成的 I/O 时按挂钟计费，按 128MB 算：平均 2 分钟一轮约 6,300 GB-s/月；全部跑满 15 分钟也只有约 47,000 GB-s | Workers Paid 含 40 万 GB-s/月，之后每百万 GB-s $12.50；等待用户的那段时间走 hibernation，不计时长 |
| DO 请求   | 开跑、WebSocket 上行消息（按 20:1 折算）、fiber 每 30 秒一次的心跳 alarm，每轮约 10 次，合计约 4,200 次/月      | 含 100 万次/月                                                                                    |
| DO SQLite | 每轮约 60 行事件，合计约 2.5 万行写入/月                                                                        | 含 5000 万行/月                                                                                   |
| Vercel    | LLM 等待仍发生在 Vercel 的单步调用里，所以内存时长和今天同一量级；调用次数每轮多出约 10 次，合计约 4,000 次/月  | Hobby 含 100 万次调用、360 GB-hrs 内存时长                                                        |

结论：两边都落在已有额度之内，**新增花费约为 0**（账号已经在 Workers Paid 上：render-video 用了 Containers）。真正的成本是工程量，集中在第 1 片。

## 8. 回滚开关

- 服务端环境变量 `ASSISTANT_DURABLE_CANVAS`。开着时，画布回合的开跑请求返回 durable 模式的回合信息；关掉时，回到今天的 SSE 加 `canvas_sync` 接力，一个字都不用改。回滚 = 关掉开关再重新部署。
- 回滚时正在跑的 durable 回合会在 DO 里跑完；连接接口不受开关控制，前端照样能补放这些回合。
- 开关开着稳定两周后，删掉画布那支 SSE 接力，不长期保留双路径。
