# 助手回合托管 — 刷新接回进行中的回合（施工基准）

> 状态：**第 0 片已上线（2026-10-07）；「脱离浏览器跑完 + 事件日志补放」方案 11-11 定稿；第 1、2 片已写（服务端开关 `ASSISTANT_DETACHED_TURNS=true` 才生效，默认关），第 3 片起未做**。
> 11-11 改方向：⛔ 不再上 Cloudflare Durable Objects。10-08 那份 DO 方案（只覆盖画布，DO 协调 + Vercel 单步）
> 写于 v3 内核之前；现在一轮的中间状态本来就存在 Redis 里、团队是 Pro（路由 `maxDuration` 800），
> 用现有的两样东西就能做到「关页 / 刷新 / 断网后回合照样跑完，回来能接上」，而且**所有台**都受益，不只画布。
> 依据见 §2；DO 方案的取舍见 §8。

## 1. 现在为什么接不回

- 成帧器（`lib/assistant-operator-stream.ts`）在 `start()` 里主动驱动内核，并把 `request.signal` 接到内核的 abort 上：
  **浏览器一断开（刷新、关页、断网、手机切后台被杀）这一轮就停在原地**，停在两步之间还好，停在一步中间那一步就白跑了。
- 一轮的中间状态只在两种时刻落进 Redis（`features/assistant/state.ts`，1 小时过期）：过了软线（所有台每 120 秒）交接力条时、
  画布 `canvas_sync` 时。其余时刻断开，状态只在内存里，跟着这次请求一起没了。
- 时间线条目只活在浏览器的 store 里，回合跑完由前端写进会话；刷新之后能读到的只是**上一次写进会话**的那些，在飞那一轮整段不见。
- 第 0 片（软线接力、断流落库、同类失败两次就停、每步记 token）已上线，管的是 300 秒被杀，不管断开。

## 2. 方案：服务端不跟着浏览器断开，事件写进日志，回来的页面补放

**一句话**：开跑那一刻起，一轮由服务端自己跑到它的下一个停点（收尾、停在卡上、时间预算到了、画布要落改动）；
每一帧按序号写进 Redis 的事件日志；浏览器只是这份日志的一个读者 —— 在线就实时收，断了回来按序号补放、再接着收。

- **跑完不靠浏览器**：路由把「消费内核事件」这件事放进 `after()`（Fluid Compute 下函数在响应结束后继续活到 `maxDuration`），
  响应流只是旁听；浏览器断开不再 abort 内核。时间预算照旧（软线 120 秒交接力条、硬线 770 秒），所以单次请求的时长上限不变。
- **停只认明说的停**：⏹ 和插话不再靠「断开连接」表达，改为调停止接口在 Redis 里落一个停止标记；内核的 abort 信号由
  「硬线定时器 + 停止标记」合成。停在两步之间照旧，停在一步中间那一步收成「挪到下一段」，与时间预算同一条收法。
- **事件日志**：Redis list，键 `antei:assistant-next:events:<userId>:<turnId>`，每帧带递增序号，1 小时过期（与轮状态同寿命）。
  `message_delta` / `thinking.delta` 不进日志（不是真值、量大）：正在写的那段话另存一个「当前草稿」键，每 1 秒最多写一次，
  补放时作为一次增量发出；定稿以 `message` 帧为准，前端按条目 id 覆盖，补放不会出重复行（同 10-08 方案 §4 的老规矩）。
- **在跑的是哪一轮**：`antei:assistant-next:active:<userId>:<conversationId>` → `{ turnId, startedAt }`，开跑写、终态删。
  没有会话 id 的那一轮（还没落库）先落库再开跑 —— 前端在发第一条消息前 upsert 会话，现有逻辑已经这么做的照用。
- **回来接上**：面板挂上时问一次「这段会话有没有在跑的轮」；有就连补放接口 `GET …/turns/<turnId>/events?after=<seq>`：
  先把日志里序号之后的全部帧发出，再每 1 秒读一次新帧，直到终态帧或接近函数时长上限（到点关流，前端带着最后序号重连）。
- **轮号由路由定**：路由生成 `turnId` 传给内核（接力那一跳照旧用板子上的轮号），并在第一帧 `open` 里带给前端 —— 前端断了之后
  靠它找回日志。

### 2.1 落改动不重放两次

补放的帧里有已经应用过的改动步（图片 / 视频 / LoRA 表单的 op、画布的 op）。前端应用改动的那一跳加一道闸：
**按 `turnId + step.id` 记下应用过的步**（`sessionStorage`，跟着标签页走），补放时见过的步只更新时间线、⛔ 不再应用。

- 断开前已经应用、刷新后补放 → 闸住，不重复（追加型的提示词改动重复一次是看得见的错）。
- 断开时还没来得及应用（关页那一刻服务端刚吐出来）→ 补放时应用，与在线时同一条路。
- 画布 `canvas_sync`：服务端照旧停在那一步、把待落的改动存进轮状态；回来的页面补放时把这批改动落到画布，再按现有接力发下一次请求。
  ⛔ 不在服务端落画布（那是 DO 方案为「浏览器不在也要接着跑」付的代价，这里不需要：浏览器不在时这一轮停着等它）。

### 2.2 钱闸

不动：服务端照旧没有任何一条能建 generation 的路，生成确认卡停在卡上等人按；补放回来的确认帧同样只摆卡（11-10：所有台都不替用户按）。
停止接口、补放接口、事件日志模块都进钱闸源码扫描的名单。

## 4. 成本与上限

- Redis（Upstash，已是生产硬依赖）：每轮约 50–200 帧写入 + 草稿每秒一次；补放只在有人回来时轮询（每秒 1 次读）。按每月约 500 轮估算远低于现有额度。
- Vercel：函数时长与今天同一量级（模型等待本来就在这次请求里）；断开后不再提前结束，最坏多跑到下一个停点（≤ 软线 120 秒 + 一步）。
- 回合用量上限（11-10，每轮 100 万输入 token）照旧生效：浏览器不在时一轮也不会无限跑。

## 5. 回滚

服务端开关 `ASSISTANT_DETACHED_TURNS`：关掉时路由回到「断开即 abort」、不写日志，前端找不到在跑的轮就什么都不补放。第 5 片之前一直保留。

## 6. 第 0 片（已上线，留档）

软线接力（`ASSISTANT_OPERATOR_TIME_BUDGET`：开新一步前本次请求已用 ≥120 秒就收尾交接力条；正在跑的那一步到 770 秒还没回来就掐掉留到下一段）·
断流落库（`streamInterrupted` 系统行）· 同类失败两次就停 · 每次模型调用一行 `assistant llm call`（token、耗时、11-10 起加上这一步的工具数）进 Workers Logs。

## 7. 实测（2026-10-07 / 08，留档）

300 秒超时集中在画布（7 天 7 次，一位用户），原因是一步慢、步数多；其余失败在 provider 一侧。11-05 起团队是 Pro、`maxDuration` 800，
300 秒那条线已不存在。断流当时量不到（只在内存里），第 0 片起落库。

## 8. 为什么不用 DO（10-08 方案的取舍）

- DO 方案要把工具环拆成「可存档的单步 + DO 协调」、把画布落改动搬到服务端，工程量集中在高风险的内核与画布，而且只覆盖画布。
- 它额外买到的只有「浏览器一直不回来，回合也能在服务端一路接力跑下去」—— 本方案里这种情况停在下一个停点等人回来（状态留 1 小时）。
  一轮的中位只有 2 次模型调用（11-03→11-08 实测），长时间无人值守的接力几乎不存在。
- 以后真要无人值守地长跑（例如批量剧本），再在本方案的事件日志之上加调度，不推翻这一份。
