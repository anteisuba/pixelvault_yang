# Seedance 2.5 能力事实与设计输入

> **这篇管什么**：即梦 Seedance 2.5 官方使用手册的能力提炼，以及它对**画布节点建模**与**助手 ScriptDoc**的设计输入。
>
> **这篇不管什么**：接入通道状态（fal 白名单 / 火山无 model id / BytePlus）——那是 [`model-catalog.md`](model-catalog.md) §⑥ §⑨ 的地盘，本篇不复述。

## 边界声明（先读这条，否则会误用下面所有数字）

手册的分发面是**即梦 C 端**（jimeng.jianying.com，网页/App 会员），不是火山方舟 API。但手册的「参数设定」一节用的是纯 API 措辞——`R2V 链路`、`请求体大小不超过 64 MB`、`大文件请勿使用 Base64 编码`、`duration 支持的范围 -1 & [4, 30]`——**并且它列的 2.0 那一列与本项目代码里的 2.0 契约逐项吻合**（图 0–9 / 视频 3 段 15s / 音频 3 段 15s / R2V 不支持仅传音频）。

据此判断：**手册的参数表描述的是 API 层契约，不是 C 端 UI 限制**。这让 2.5 那一列成为目前最好的能力证据——但它仍**不是**火山 GA 后的正式 API 文档，GA 时必须以方舟文档复核后再改代码。

## §1 参数对照与代码对账

### 1.1 输入素材上限

| 类型           | 2.0（= 本项目现行契约）         | 2.5（手册）                   | 本项目代码状态                |
| -------------- | ------------------------------- | ----------------------------- | ----------------------------- |
| 图片数量       | 0–9 张                          | **30 张**                     | ⚠ 仍写 9 —— 见 1.4 冲突 A     |
| 视频           | 单条 [2,15]s ×3，总 ≤15s        | **单条 [2,30]s ×10，总 ≤30s** | ⚠ 仍写 3                      |
| 音频           | 单段 [2,15]s ×3，总 ≤15s        | **单段 [2,30]s ×10，总 ≤30s** | ⚠ 仍写 3                      |
| 多模态最低要求 | R2V 链路**不支持仅传音频**      | **支持仅传音频**              | ⚠ `audioRequiresVisual: true` |
| duration       | `-1 & [4,15]`，97–361 帧        | **`-1 & [4,30]`，97–721 帧**  | ⚠ 仍是 2.0 的 4–15 占位       |
| resolution     | 项目露出至 1080p（火山另标 4k） | **仅 480p、720p**             | ✅ 已正确                     |

单条素材的格式约束 2.5 未改：图片 jpeg/png/webp/bmp/tiff/gif/heic/heif、宽高比 (0.4, 2.5)、边长 (300, 6000)px、单张 <30MB；视频 mp4/mov、480p–4K、总像素 [409600, 8295044]、≤200MB、FPS [24,60]；音频 wav/mp3、单个 ≤15MB；请求体统一 ≤64MB。

实际时长限制比标称宽 0.2s（输出略长于标称）：2.5 单条 [1.8, 30.2]s，总 30.2s。

### 1.2 稳定性建议（手册原文，超出即「需要抽卡」）

| 场景               | 建议                                                                     |
| ------------------ | ------------------------------------------------------------------------ |
| 主体音视频个数     | 1–5 效果好；6–10 稳定性下降                                              |
| 主体音视频时长     | 5–10s 效果好                                                             |
| 主体图个数         | 1–8 效果好；9–12 稳定性下降                                              |
| 多视角主体图       | >5 主体时优先「单视图」；要多视角**拆成多张**（多图多视图 > 单图多视图） |
| 视频编辑输入时长   | ≤20s 效果好                                                              |
| 视频参考图编辑张数 | 1–5 效果好；6–8 稳定性下降                                               |

**这批数字的用途是 UI 的软提示，不是硬校验**——硬上限是 1.1，这里是「过了会掉卡」的经验线。画布的参考位在超过软线时应给提示而非禁用（对齐 Hard Rule 8 的「不禁用 UI」气质）。

### 1.3 GA 时必须重新推导的三处

| 代码位置                                                         | 现状                                         | 手册证据             |
| ---------------------------------------------------------------- | -------------------------------------------- | -------------------- |
| `video-model-capabilities.ts` `SEEDANCE_25_*.supportedDurations` | `[4..15]`，注释自认是 2.0 抄来的 PLACEHOLDER | `[4,30]`，721 帧     |
| `video-model-send-plan.ts` seedance `slots`                      | `images:9, videos:3, audio:3, total:12`      | 30 / 10 / 10         |

后两处目前是**同一个分支**服务 2.0 和 2.5 两代（`SEEDANCE_REFERENCE_IDS` 一个 Set 走到底）。2.5 GA 时这个分支必须按代分叉，否则要么 2.5 被 2.0 的上限卡住，要么 2.0 被放宽到它接不住的数字。

### 1.4 冲突立案

**冲突 A**：`video-model-send-plan.ts:77-79` 的注释写「2.5 keeps the 2.0 multimodal-reference shape (图 0-9 + 视频 0-3 + 音频 0-3, 音频不可独存) per 火山's own API doc」，与手册 1.1 直接矛盾。

两者都自称援引火山口径，无法在本地判定谁新。**处置：不改代码**（模型未 GA，改了也无法验证，且 `seedance-25-reservation.test.ts` 的 tripwire 正是为防止这类提前动手）。GA 当天以方舟 API 文档为准重新推导，并把结论写回本节。

## §2 四种模式 → 画布建模映射

手册的模式选择器：**【全能参考】【智能编辑】【超长视频】【首尾帧】**，其中智能编辑与超长视频是 2.5 新增。

映射到画布既有建模（**名词做节点、动词做动作**，见 `plans/canvas-master-2026-07-26.md`）：

| 手册模式 | 画布里是什么                      | 落点                                                              |
| -------- | --------------------------------- | ----------------------------------------------------------------- |
| 全能参考 | **已有** —— seedance 节点的常态   | `referenceMode: 'multimodal-reference'` + `positionalImageTokens` |
| 首尾帧   | **已有** —— `text-or-first-frame` | 非 reference 变体走 `FIRST_FRAME_SLOTS`                           |
| 超长视频 | **参数**，不是新节点              | duration 30–180s，是 `supportedDurations` 的扩档                  |
| 智能编辑 | **动作**，不是新节点              | 作用于已有 video 节点，画布无对应动作（见 2.2）                   |
| 视频延长 | **动作**，不是新节点              | 同上；`videoExtension` 目前只有 `KLING_V3_PRO`                    |

**关键判断：四种模式里只有一种需要新的节点族——一种都不需要。** 两种是既有形态、一种是参数扩档、两种是作用于已有节点的动词。这与「名词做节点动词做动作」的既定建模完全同向，不必为 2.5 重开节点分类。

### 2.1 超长视频对分镜预算的影响

180s 是**单次直出**，不是拼接。ScriptDoc 的 `maxShots: 24` 在 180s 下等于每镜 7.5s——够用，但 **ScriptDoc 没有「时间预算」这个概念**：`targetDuration` 是一个自由文本提示（`"8s"` / `"12-15s"`，上限 40 字符），既不参与校验，也不向下分配到每个 shot。

30s 以内时这不痛（模型自己分配），到 180s 就会痛：24 个 shot 谁长谁短、总和对不对得上目标时长，目前没有任何一层负责。**这是超长视频落地前必须先解决的建模缺口**，不是实现细节。

### 2.2 延长与编辑：能力在上游，配置在本项目

`model-catalog.md` §⑨ 已记：火山 2.0 能力表就含「编辑视频 / 延长视频 / 图生视频-首尾帧」，但项目 `videoExtension` 只配了 Kling。也就是说这不是「2.5 带来的新能力等 GA」，而是**2.0 时代就有、本项目一直没配**。

手册补充了两条硬约束，配的时候要带上：

- **延长的入口前提**：只有时长 ≤30s 的视频可延长；单次延长 4–30s；可「套娃式」多次，只要每次的底片仍 ≤30s，极限 30+30=60s。
- **延长的提示词只作用于新增段**：15s 原片延长 5s，提示词只对最后 5s 生效，前 15s 完全保留。这决定了 UI 必须让创作者知道「你现在写的是第 15–20 秒」，而不是复用整片的 prompt 输入框。

编辑侧手册分了三个入口（智能编辑=纯文字、高级编辑=本地上传后框选/画笔、视频编辑=对已生成产物），三者的差别只在**入口和标注能力**，指令结构是同一套（见 §3.4）。

## §3 提示词公式 → ScriptDoc 对账

这是本篇对助手设计最直接的部分。手册的长视频公式是**三层结构**，逐层对照 ScriptDoc（`src/types/script-doc.ts`）：

### 3.1 模块一【多模态参考层】

手册公式：`基于上传的[素材类型]，严格保持[…]一致，严格锁定[…]` + 全文多次 `@图/视频/音频`。

**ScriptDoc 没有这一层。** 项目里有两个相关但不等价的机制：

- `positionalImageTokens` —— 把本地 `@名字` 转成 provider 的 `@ImageN` 位置 token（`video-model-send-plan.ts`）
- `ScriptDocShot.roleIds` —— 角色绑定，投影成 character 节点到 seedance 节点的边

缺的是**参考声明的文本层**：手册强调「全文的 prompt 中也可以多次 @图/视频/音频，会更加准确」，即 @token 不只在开头声明一次，要在情节描述里反复锚定。这是可以由助手自动完成的——它知道哪个 shot 绑了哪个 role，理应在生成 `summary` 时就把 @token 织进去，而不是只在拼接期追加一行声明。

### 3.2 模块二【全局设定】

手册公式：`[基础环境与质感] + [视觉风格] + [镜头语言] + [人物造型] + [表演核心] + [禁止项]`

| 手册字段             | ScriptDoc 对应        | 状态                             |
| -------------------- | --------------------- | -------------------------------- |
| 基础环境与质感       | `background`          | ✅ 有（600 字符）                |
| 视觉风格             | `styleNote`           | ✅ 有（400 字符）                |
| 人物造型             | `roles[].description` | ✅ 有（700 字符）                |
| **镜头语言（全局）** | —                     | ❌ **缺**：`camera` 只在 shot 级 |
| **表演核心**         | —                     | ❌ **缺**                        |
| **禁止项**           | —                     | ❌ **缺，且是硬伤，见下**        |

**禁止项为什么是硬伤**：`video-model-send-plan.ts` 里 seedance 的 `parameters.negativePrompt: false` —— Seedance **没有独立的负向提示词参数**。手册对此的解法是把禁止项写进正向 prompt 的结尾（「禁止生成多余台词或 BGM、禁止生成字幕、禁止流鼻涕」）。

而 2.5 的第 5 项升级正是「解决随机字幕和无关 BGM」——**这条改进只有在 prompt 里写了禁止项才吃得到**。目前 ScriptDoc 没有任何字段承载它，`buildNodeWorkflowPrompt` 也只是把四个字段换行拼接，没有「结尾全局补充」的位置。这是助手当前拿不到 2.5 一项主要卖点的直接原因。

### 3.3 模块三【时间戳剧本分镜】

手册的每段切片公式：`[起止秒数] + [核心阶段/主题]` → `[动作/表情等物理层面指令]` → `[情感解析/镜头潜台词]`

| 手册字段        | ScriptDocShot 对应        | 状态                                            |
| --------------- | ------------------------- | ----------------------------------------------- |
| **起止秒数**    | —                         | ❌ **缺 —— 最重要的一处**                       |
| 核心阶段/主题   | `sceneLabel`              | ✅ 有                                           |
| 动作/表情       | `summary`                 | ✅ 有                                           |
| 景别/构图/运镜  | `camera` / `composition`  | ✅ 有                                           |
| 情感解析/潜台词 | `emotion`（双层情绪标签） | 🔶 语义接近，但手册要的是**逐条解释**，不是标签 |
| 台词            | `dialogue[]`              | ✅ 有                                           |

**时间戳缺口的严重性**：2.5 的第 3 项升级「时间戳文本控制」是它相对 2.0 的核心差异——手册明说其他模型的时间戳「仅能代表先后顺序，无法精准把控时长」，而 2.5 原生支持秒级区间。ScriptDocShot 没有 `startSecond` / `endSecond`，助手就**结构上无法**产出剧本级时间戳。

讽刺的是项目里已经有这个建模：`SEEDANCE_PROMPT_PLAN_OUTPUT_CONTRACT`（`constants/seedance-prompt-plan.ts`）的 `timeline[]` 就是 `{startSecond, endSecond, action, camera, composition}`。但那是**旧 planner** 的契约（系统提示词里写死 "Seedance 2.0"），而旧 planner 已被助手取代——现役链路是 ScriptDoc → `projectScriptDocToGraph` 投影节点。也就是说：**正确的建模存在于已退役的那条路径上，现役路径反而没有。**

### 3.4 编辑指令公式（对应智能编辑/高级编辑）

`[具体修改对象] + [动作与变化描述] + [生效时序]`

第三项「生效时序」值得单列：手册要求明确「一直存在」还是「特定秒数才变化」（如「仅在第 5-8 秒期间发生变化」「全片 15 秒统一修改保持一致」），并且与标注后系统自动插入的时间戳标签（`⏱️00:00 视频帧标注`）配合。**这又是时间戳**——编辑侧和分镜侧共用同一套秒级语义，值得作为一个共享概念建模，而不是两处各写各的。

### 3.5 真人公式（可直接做成助手的深度档）

`人物 = [年龄/种族] + [肤色/皮肤质感] + [面部细节特征] + [眼神/灵魂] + [发型/发色] + [服装/服装质感] + [体型/情绪/气质]`

两个可直接落地的技巧：

- **强制保真后缀**：肤色项必须带「保留真实的微细毛孔与肌肤纹理」（可加雀斑/瑕疵）——这是手册给的去 AI 感解法。
- **面部细节至少 3–4 点组合**：眼型 + 眉骨 + 鼻梁 + 唇形 + 下颌线，这是解决「多人像双胞胎」的抓手。

这套公式落点是 `ScriptDocRole.description`（现 700 字符，装得下）。与 `CINEMATIC_SHOT_GRAMMAR` 的 PHYSICAL PERFORMANCE 段同向但更细——那一段讲的是「表演写物理痕迹」，这一套讲的是「身份写骨相细节」，互补不冲突，可以并列进 role 的深度档。

## §4 转场词表（可直接做成 chips）

手册给了 11 种转场，每种都带「是什么 / 适用场景 / 宽泛版 prompt / 具体版 prompt」四栏。结构上与 `CAMERA_GRAMMAR_GROUPS`（`cinematic-grammar.ts` 的运镜 chips）完全同构，可以照搬那个建模加一组：

| 组       | 转场                                                                       |
| -------- | -------------------------------------------------------------------------- |
| 基础转场 | 自然镜头切换 · 淡入淡出 · 叠化 · 白闪/黑闪 · 擦除                          |
| 创意转场 | 遮罩转场 · 相似物转场 · 动作转场 · 动态接力转场 · 拉近/拉远转场 · 水墨转场 |

公式：`切镜设定 = [转场类型指引] + [基础约束要求] + [切镜逻辑要求]`，其中基础约束固定含「禁止生硬切镜、禁止物体凭空出现」。

手册还给了一个偷懒写法：把候选列出来让模型自选——`请从 [自然镜头切换 / 遮罩转场 / 水墨转场 / 相似物转场] 等转场方式中，根据本片风格选择最合适的一种`。这对助手很有用：不确定时不必替创作者选死。

## §5 白模（与 Comfy/3D 线的潜在交点）

粗颗粒度（几何体拼接）当前效果优于细颗粒度。公式：`【参考声明】+【对应关系映射】+【剧情详述】+【场景处理】+【整体收束】`，其中对应关系映射是「[视频1] 中的{颜色/形状特征}模型 → [图X] 的{角色名}」。

两条实操约束：细颗粒度参考视频要**去掉轨迹线/坐标线/相机 cone**；官方有 Maya/Blender 插件可直接导出 Camera 路线上传。

评论区对白模效果的反馈是**负面偏多**（「用了白模引导之后整个视频的表现力下降」「两个参考视频并没有对生成视频有影响，只是参考了站位图」）。**接入优先级应排在时间戳与禁止项之后。**

## §6 手册未答与外部存疑

来自手册评论区（58 条）的信号，都不是官方结论，但对预期管理有用：

| 事项                 | 状态                                                                                      |
| -------------------- | ----------------------------------------------------------------------------------------- |
| 时间戳的**格式规范** | ❓ 有用户提问未获答复。手册正文示例混用 `0s-3s` / `[00:00 - 00:09]` / `第 32 帧` 三种写法 |

| 手册自身笔误         | 「所有视频总时长限制为 0.2s」应为 30.2s（评论区已确认）                                   |
