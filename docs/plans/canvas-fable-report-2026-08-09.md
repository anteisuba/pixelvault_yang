## 二、对照页（各一页）

### 2.1 Krea Nodes（⚠ 公开资料，未实测）

- 节点 = **真数据流**：inputs / parameters / outputs 显式连线，模型是节点，输出接输入，可存成模板工作流复用。与 LibTV 的「引用镜像」是相反的边语义。
- 2026 主打 **Node Agent / Prompt-to-Workflow**：一句话 → 读画布 → 规划管线 → 自动接线 → 跑。与我们助手 autospawn 同物种，证明「助手建图」是行业主流方向。
- 详情面板实测（账本 §7–8，这部分是一手）：暗底、hover 显形、`Loading video…` 进度——三条都进了我们的「不能抄」清单；可抄的只有减法算术（R1–R12 已吸收进详情面板，不必重取）。
- **对我们的含义**：Krea 的用户是「搭管线的人」，LibTV 的用户是「讲故事的人」。我们的北极星是导演台——离 LibTV 近，离 Krea 远。数据流连线（谁的输出进谁的输入）对导演任务是实现细节，不是用户心智。

来源：krea.ai 官方 docs/features/nodes 与 blog（ai-workflow-agent · prompt-to-workflow），2026-08-09 检索。

### 2.2 Haivis（历史参考，拆解已删、结论存 `node-canvas.md` §3.1）

只继承**空间纪律**，不看皮肤：稳定分栏（助手收起时画布拿回真实宽度，非浮层挤压）· 三个常驻工作面（画布主区 / 可收起助手 / 素材 dock）· 命中区分档（fine 32/36、coarse 44）。这些已是我们的现行行为约束，三方向都不推翻。

### 2.3 UpDream（`cleanup §9.4` 实地）

B 站系 AI 视频平台，形态与我们高度重合（无限画布 + Agent + 积分）。两条已被采纳进现行实现：模式切换器 = 选中节点浮出参数面板顶部 tab（切片 4 已落地）· 模型选择在节点面板内不在全局（我们本来就对）。两条可抄未抄：**多参数压一个下拉**（`5S / 1080P ▾`）· **生成前显示消耗**（`⚡225`；LibTV 同款 `⚡12`——两家共识，我们单价数据已备好，落点在 `detailForOption`）。

## 五、三个结构方向（同一剧本任务）

**固定剧本**：1 角色（小满，3 张出场图+音色）+ 1 场景（茶馆）+ 2 张镜头静帧（先审）→ 1 段视频（全能参考）→ 片盒。
**三方向共同保住的硬约束**：图模型+收割链不断 · Seedance 袋型保真 · 收集器三件套一致性单位 · Studio 浅/Canvas 深 · lineage→Assets · 合法性唯一事实源 · 品质底线。
**结构差异轴**：绑定的「真相」住在哪——A 住**提示词**，B 住**槽位**，C 住**对话**。

### 方向 A ·「句子即装配」（提示词第一公民）

> 心智一句话：**你在给每个节点写一句带引用的话，画布只是这些话的空间索引。**

| 维度       | 方案                                                                                                                                                                                                                        |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 节点菜单   | 砍到 6：图片 · 视频 · 音色 · 镜头文本 · 片盒 · 收集。镜头图/关键帧**不再是菜单项**——用途是图片节点上的**可变分类标签**（复用 `imageCategory` 机制扩展），建完随时改                                                         |
| 关系呈现   | 提示词里的胶囊是唯一绑定动作；**供给边自动派生为影子线**（默认淡显、可开关）；制片骨干（镜头→视频→片盒）保留常显墨线。用户不再手工拖供给边                                                                                  |
| 生成上下文 | 现有节点下方 composer 升级为**富文本**：胶囊内嵌句中（`让 @小满 坐在 @茶馆 的窗边`），参考缩略行是胶囊的只读镜像。素材条与边的双轨冗余就此消除——真相只有一处（句子）                                                        |
| 卡片职责   | 纯收集器（维持 08-08 收口）。`@小满` 胶囊显示「出场 ×3 + ♪」，harvest 时展开出场组+图例（现有机制零改）                                                                                                                     |
| 助手边界   | 画布级导演。结构免费落画布 / 像素设闸（承接三态审核）；助手写的提示词就是带胶囊的句子，用户可改一个词重发                                                                                                                   |
| 标注       | 图片节点展开编辑器（P2 原案）；标注区域编号 ①② 可作为胶囊被句子引用（「把 ① 的灯笼换成红色」）                                                                                                                              |
| Token      | **第一公民**。空名节点胶囊显示类型+缩略图；删除节点→胶囊变失效态（红色空壳，点击移除）——「删边不删 token」问题从根上不存在，因为没有独立于句子的 token。容量：胶囊参与 `node-video-send-slots` 计数，溢出胶囊标「不会发送」 |

**剧本走法**：建角色卡拖 3 图 → 建图片节点写「茶馆内景……」生成场景 → 建两个图片节点各写一句（`@小满 在 @茶馆 靠窗独坐，中景`），分类标「镜头」，审核通过 → 建视频节点选全能参考，写 `@镜头1 起，@小满 抬头看向门口，@茶馆 环境音` → 生成 → 拖入片盒。

**简化状态**：空画布 = 中央一句提示（「写一句话，或让助手起稿」）+ 添加菜单 6 项；生成中 = 胶囊行锁定、卡内扫光（现行六态不变）；助手开 = 覆盖式 dock，助手消息里的句子与节点上的句子同构（一份格式两处显示）。

**优点**：与 LibTV 实证形态最近；直接消灭 4.2/4.3/4.4 三个痛点的根（双轨归一）；@翻译链（legend/位置 token）现成零改；「改一版」成本降到改一个词。
**风险**：富文本编辑器是真工程（`MentionInput` 现在是纯文本+尾部追加；内嵌胶囊 = contenteditable 或分段模型，i18n/IME/触屏都要过）；影子线太淡会伤「一眼看清谁喂谁」的图读性——需要「关系线」开关兜底；镜头文本节点的四字段结构化输入与「一句话」心智有张力（可能要并给助手承载）。
**证伪法**：拿现 `MentionInput` 做一个 contenteditable 胶囊 spike，中文 IME + 触屏软键盘不翻车才算立住；立不住整个方向降级为「胶囊只在缩略行、正文仍纯文本」。

### 方向 B ·「制片轨 + 素材腰带」（槽位第一公民）

> 心智一句话：**横向一条制片流水线，素材像零件一样卡进节点的具名槽位，线只画流水线。**

| 维度       | 方案                                                                                                                                                                                                                                                              |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 节点菜单   | 按「素材 / 制片 / 收集」三组重排：素材（图片·音色·参考视频）+ 制片（镜头·视频·片盒）+ 收集。**镜头保留为独立制片节点**（中间产物先审再喂的地位靠类型承载）；关键帧不是节点——是视频节点腰带上的「首帧/尾帧」具名槽（`159f0518` 已落地一半）                        |
| 关系呈现   | **只有制片轨画线**（镜头→视频→片盒 + 图生图 lineage）。素材→节点不画线，改为节点上的**素材腰带**：一排 typed 槽位，名字由模式派生（首帧·尾帧·图N·♪·视频N），容量实时显示 n/m。数据层仍建边（呈现级改动，收割零改）。反查：选中素材/卡 → 消费节点高亮 + 「出演 N」 |
| 生成上下文 | 内聚在节点上：腰带 + prompt + 参数摘要 = 组装台（视频）/ 同构小号（图片）。腰带就是 `ReferenceManagerPanel` 的进化，不新造                                                                                                                                        |
| 卡片职责   | 纯收集器，住**左侧名册 rail**（卡匣从「定位器」升回「素材之家」）：拖卡到腰带 = 再喂一镜。卡面档案夹化（名字+出场组计数+♪），与图片卡形态强区分                                                                                                                   |
| 助手边界   | 右侧 dock（Haivis 稳定分栏），投影节点直接落制片轨；结构免费/像素设闸同样承接                                                                                                                                                                                     |
| 标注       | 全屏编辑器（P2 原案原样），从图片节点近场工具条进                                                                                                                                                                                                                 |
| Token      | **降级为翻译产物**：用户不手写 @，腰带是真相；正文保持纯文本，发送时图例注入（现有 legend 机制）。@ 输入保留为快捷添加——敲 `@小满` 后转为腰带槽，**不在正文留 token**。「删边删不删 token」问题消解为「移除槽位」一个动作                                         |

**剧本走法**：左 rail 新建角色卡（3 图+音色）→ 素材组建图片节点生成茶馆 → 制片组建镜头节点 ×2，腰带卡入 @小满卡 + 茶馆图，写词生成、审核 → 建视频节点切全能参考，腰带出现 图×9·♪·视频 槽，拖两张镜头图+卡入位 → 生成 → 制片轨末端拖入片盒。

**简化状态**：空画布 = 左 rail（空名册+新建）+ 中央提示「从素材或剧本开始」；生成中 = 腰带锁定+卡内扫光，制片轨上游节点微亮指示来源；助手开 = 右分栏，画布真实变窄（Haivis 纪律）。

**优点**：正面解决 4.2——边只剩一种语义（制片流），「静默丢弃边」不可能再画出来（素材只能进 typed 槽，超限当场红）；容量/模式/槽位这半年的工程成果（模式三档、具名首尾帧、单一容量事实）全部直接升级为主角而非补丁；图读性最好（30 节点也只有一条主线）。
**风险**：素材无线导致「这张图被谁用了」不看反查就不知道——反查交互必须一等公民否则倒退；名册 rail 与 CastDock 定位器职责要重划（定位器功能并入还是并存，需 owner 拍）；腰带在小节点上的空间压力（多素材时溢出 +N 的披露层要设计）。
**证伪法**：把「鸣潮」真实项目按此结构画一张密度图——若 12+ 素材节点无线漂浮时找不到归属（反查点击超 2 步），方向不成立。

### 方向 C ·「对话导演 + 故事板」（对话第一公民，双视图）

> 心智一句话：**跟导演助理说话，画布和故事板是它整理出来的两种台账。**

| 维度       | 方案                                                                                                                                                                              |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 节点菜单   | 最小化：素材上传 · 收集 · 制片三件（镜头/视频/片盒）。多数节点期待由助手投影（autospawn），手动菜单是兜底不是主路                                                                 |
| 关系呈现   | 画布边保留现状两级墨线（不重做）；**主要阅读界面换成故事板视图**（LibTV 10.2 同款双视图）：按角色/场景聚合的关键元素栏 + 按镜头序的清单栏。关系在故事板里是分组与引用列表，不靠线 |
| 生成上下文 | **单一全局输入条**（底部或右侧）：目标 chip 显示「写给谁」（选中节点自动进入上下文——LibTV ④；可手动移除）。节点上不再挂 composer；详情面板保留深编辑                              |
| 卡片职责   | 纯收集器；故事板关键元素栏按卡聚合展示；**审核通过的角色图由助手代管归档进卡**（解决「补充图入卡正路」——人只点 approve，归档是助手的活）                                          |
| 助手边界   | 主轴。完整承接 LibTV 协议：已询问折叠块 + 结构化确认选项 + **结构免费落画布/像素设闸** + 待审队列露出（三态审核 UI 化）。剧本两阶段引擎的「UI 两道门」在此方向里就是主流程        |
| 标注       | **对话内标注**：在图上框选 → 编号 → 指令行进入输入条（「①的灯笼换红色」）——P2 的数据模型（区域+指令列表）原样复用，落点从编辑器移到对话                                           |
| Token      | 对话与生成共用 @ 与上下文胶囊；选中即入上下文。正文 token 弱化（助手代写为主）                                                                                                    |

**剧本走法**：对输入条说「一个发生在茶馆的两镜短片，主角小满」→ 助手反问收敛（已询问块）→ 投影：角色卡壳+场景节点+两个镜头节点+视频节点，结构免费落画布、连线全接好 → 用户传 3 张小满图进卡、逐镜点「生成」（花钱闸）→ 故事板视图里逐张 approve → 视频生成 → 助手问「合进片盒？」确认落袋。

**简化状态**：空画布 = 输入条唤起语「说说你要拍什么」+ 最小菜单；生成中 = 对话里占位卡 + 画布节点扫光 + 视口跟随（LibTV ③，可关）；助手开 = 常开（它是主轴），收起时退化为方向 B 形态的手动画布。

**优点**：最大化复用已建成引擎（两阶段剧本、三态审核、discuss-before-deliver、autospawn、统一壳）——差的全是呈现层；LibTV 实测中最惊艳的三件（免费结构落图、领域知识补全提示词、确认闸）全数吸收；故事板解决「30 节点找不到东西」和一致性检阅两个规模问题；4.8 的三输入面并存问题直接归一。
**风险**：建设量最大（第二视图是新面）；手动派用户的路变薄——助手宕机/额度尽时的降级体验必须完整（兜底=手动画布仍全功能）；「一个输入条两种语义」（聊天 vs 生成指令）的目标歧义要靠 target chip 压住，压不住会比现在更乱；与「Studio 浅/Canvas 深」的边界要重述（对话入口会不会把 Canvas 变成另一个 Studio 助手——不会，深在结构与审核，但要说清）。
**证伪法**：拿真实剧本任务跑一遍现有助手（引擎已绿）：若「结构免费落画布」在现引擎上做不到局部投影（只能整案投影），协议前半段就要重设计，方向成本翻倍。

### 8.17 v10：文本节点的 `@` = 给 LLM 的多模态输入（owner 2026-08-09 第九轮）

**我的框架是错的。** §8.16 我把「文本节点里 @ 指什么」判成**间接引用**（文本喂下游、下游才用素材），并标为待定。owner 的答案完全不同、且是对的：**LLM 本来就能分析图片与视频出文字**，所以文本节点里的 `@` 是**给模型看的输入**。

**代码核实（不是纸面能力）**：

| 线                                      | 图片 | 视频          |
| --------------------------------------- | ---- | ------------- |
| **Gemini**                              | ✓    | **✓（唯一）** |
| OpenAI                                  | ✓    | ✗             |
| DeepSeek / Anthropic / 其余 13 个适配器 | ✗    | ✗             |

事实源 `src/constants/assistant.ts` 的 `ASSISTANT_MEDIA_CAPABILITIES`。三条实证：

1. **视频分析真接通**：`toGeminiVideoPart`（`llm-text.service.ts:708`）完整实现 —— ≤20MB 内联 base64，超过走 Gemini Files API 上传 + 轮询 + 用完删除，上限 **50MB**。
2. **画布节点喂 LLM 的通路类型层已建好**：`AssistantMediaReference.source` 枚举含 `'canvas'`（`types/assistant-media.ts:8`）。文本节点 `@` 分析是**复用**，不是新链路。
3. **UI 标签已备**：`getAssistantMediaCapabilityLabel` 返回 `imageVideo / imageOnly / textOnly` —— 产品本就打算把「这条线能吃什么」显示出来。

**设计结论**：

- 文本节点 composer 的素材区 = **「给模型看的素材」**，与视频节点的「发给生成模型的素材」是**不同语义、不同容量口径**（上限 **8** = `ASSISTANT_MEDIA_LIMITS.maxReferences`，≠ 视频的 12）。⚠ 实现别复用 `node-video-send-slots`。
- **能力闸的表达**：模型旁一颗常显能力标签；换到读不了的模型时，素材**不销毁**、就地标「读不了」+ 说出原因、加号隐藏（与切模式保留素材同一条纪律）。
- ⚠ 视频 50MB 上限要在 UI 说出来，别静默失败。

**v10 实测**：新增状态 6「文本节点 · @ 分析素材出文字」；三档能力切换正确（Gemini 0 标记 / GPT 1 标记「读不了视频」/ DeepSeek 2 标记 + 加号隐藏 + 计数改写）· 无 JS 错误 · 无横向溢出 · 其余交互未受影响。
