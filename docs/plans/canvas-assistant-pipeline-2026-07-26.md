## 0 · 实测结论（2026-07-26，`/studio/node` 真机）

两次不同问法，助手两次**自己说它做不到**：

> 「由于我无法直接在你的画布上无中生有地"新建"节点……」
> 「我无法直接在你的画布上新建或连线，但你可以利用画布上现有的空闲节点……」

节点数三次测量恒为 9，一个没建。**内容质量不是瓶颈** —— 它写的三镜大纲有情感线、有机位、有视觉母题，可以直接用。瓶颈全在管道。

### 三个断层（从下往上）

| #   | 断层                                 | 证据                                                                 | 后果                                                                                           |
| --- | ------------------------------------ | -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| ①   | **助手没有写画布的能力**             | 它自己两次明说；`generateAll`/`queueAll` 全域 0 命中                 | 用户任何细粒度请求（加个节点/改名/重做这张）全部落在管子外                                     |
| ②   | **助手读画布是残的：拿不到节点名字** | 回复里出现 `选中节点 ****` / `使用空闲节点 `（名字位全空）           | 没名字 → 没 `@` 引用 → `filterReferencedImages` 只发被 `@` 提到的图 → **自动链最后一环必然断** |
| ③   | **剧本没落成结构化数据**             | 助手输出 Markdown 散文；`projectScriptDocToGraph` 吃的是 `ScriptDoc` | 就算给了手，这段剧本也投不下去，中间缺「散文 → ScriptDoc」                                     |

### 顺带发现的两个漏实现

- 助手对话框里**直接显示裸 UUID**（`92960357-5aae-…` / `a2d3f992-…`）。
- 「应用前先询问」开关 + 「收成一段」按钮已存在 —— **审批门的骨架有了**，但只服务既有路径，接不到建节点上。owner 要的审批不用从零做。
  > ⚠ **2026-07-31 更正（包 5 实做时查证）**：「应用前先询问」**不是开关**，是输入框旁的一行静态文案（`StudioNode.conversation.modeHint`），全仓没有对应状态。结论仍成立但主语要换 —— 真正的审批骨架是 `[[capability:…]]` 那条链：marker → chip → **用户点击才执行**。包 5 复用的是它。

### 一个关键的好消息

三个断层**都不需要动数据层**。图模型 + `projectScriptDocToGraph` + 收割装配 + `@token` 翻译 + provider 契约这条主链是通的、被测试覆盖的。要补的是**入口**，不是重写。

## 1 · 任务清单（按依赖排序，前一件不做完后一件没意义）

### P0-A · 把节点名字喂进助手上下文

**为什么排第一**：它最小，且是 ① 和 ③ 的共同前提 —— 助手能建节点却不知道叫什么，等于没建。
**落点**：`src/lib/node-assistant-request.ts`（节点摘要构造）· `NODE_STUDIO_ASSISTANT_LIMITS.maxNodeLabelLength` 已有但值没被填。
**判据**：助手回复里再出现 `****` 或空名字即未完成。
**顺带**：裸 UUID 不得进入对话框可见文本。

### P0-B · 修 `@` 提及的过滤顺序

**为什么在 P0**：自动流程下节点由投影批量生成、顺序不由人控，这个 bug 的触发概率远高于手动模式。
**内容**：`StudioNodeWorkbench.tsx:1240` 先砍容量、`:1291` 才按 `@` 过滤 → 点名的图若排在上限之外会被先砍掉，然后迁移护栏触发、发出前 N 张。调换两步顺序即可。
**状态**：已挂成独立任务（本会话 spawn），未做。

### P1 · 给助手一组写画布的工具 ✅ 已交付（2026-07-31 · `04b4ce69` · 包 5）

**内容**：建节点（族 + role + 名字）· 连线（走 `node-connection-rules` 校验，不绕过）· 改名 · 触发生成。
**红线**：所有写操作必须经过既有的合法性事实源，助手不得直接改 `NodeWorkflowProject.state`。
**接审批**：复用已存在的「应用前先询问」骨架，不新建一套。

> **交付实况见 [`research-landing-plan-2026-07-30.md`](research-landing-plan-2026-07-30.md) §6.3 包 5。** 三条与本节原文有出入的事实：
>
> 1. **「走 `node-connection-rules` 校验」今天是一道空门** —— `canConnectNodeTypes` 自 2026-07-28 起恒返回 true（owner「全部放开」）。实现仍走它（矩阵恢复时自动收紧），但验收判据换成了今天真在拒的三条：自环 / 重复边 / 参考位满。

> 3. **协议是 marker + JSON 块**（`[[canvas-ops]]…[[/canvas-ops]]`），不是 tool-calling —— 两条路由（gateway 流式 / BYOK 缓冲）都没有 tools，marker 是唯一两边一致又不加第二套基建的办法。

### P2 · 剧本结构化输出（散文 → ScriptDoc）

**内容**：助手写大纲/分镜时直接产出 `ScriptDoc`（`types/script-doc.ts` 已定义），而不是 Markdown。两阶段引擎已绿，缺的是让对话路径也走它。

## 2 · 对节点设计的重新评估

「谁来建节点」变了，节点设计要跟着变的是**权重**，不是切分。

### 2.1 不用改（与谁建节点无关）

六族切分 · 名词做节点动词做动作 · 卡名在卡外 + 卡内纯媒体 · 模式决定槽轨 · 三形态控件矩阵 · 连线三维度编码。

### 2.2 要改的四条

| #   | 改动                                                     | 理由                                                                                                                                                                                                                   |
| --- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ①   | **主动作从「生成」变「审阅」**                           | 自动铺出来的卡默认是"待审"。信息设计 §7 的四态（缺必填/就绪/生成中/失败）**少一态：已出但未审**。审阅是二选一（通过/重来），这是「每个对象最多一个主动作」唯一该破例的地方——但破例要显式写进规格，不能默默变成两个按钮 |
| ②   | **名字升为一等公民**                                     | 助手读不到名字这个 bug 证明了名字的分量。要求：卡外名可**原地编辑**；名字**就是** `@token`；**空名字必须显式暴露**（今天是静默传空字符串，害得助手只能说"节点 \*\*\*\*"）                                              |
| ③   | **批量审阅视图从"新增能力"升为必需**                     | 一次铺 12 个节点后逐张点开审是灾难。CD 简报里记过的「批量长成画布上的对象 + 网格审核区」不再是加分项                                                                                                                   |
| ④   | **卡匣降级成注册表**（owner 2026-07-26 拍板，详见 §2.4） | 它是画布节点的**第二份副本** —— 同一个身份两处可选、可改、可操作，双重呈现必然产生"该在哪操作"的犹豫。这才是"不方便"的根，不是样式问题                                                                                 |

### 2.4 卡匣 → 身份注册表（owner 2026-07-26 拍板）

**废弃的是「卡的副本」，保留的是「注册表」。**

#### 诊断

卡匣里每一张卡，画布上都已有对应节点。同一个身份被画了两遍，两处都能选、能改名、能触发操作。代价三重：

1. **认知**：用户不知道该在哪儿操作。
2. **代码**：`CastDock.tsx` 576 行；且它自带一套指针拖拽，与 React Flow 原生拖拽**并存两套**。
3. **空间**：左侧 240px 内容区装卡面，一屏只看得到 3 个身份。

#### 新形态

| 维度                        | 旧（卡面镜像）     | 新（注册表）                                          |
| --------------------------- | ------------------ | ----------------------------------------------------- |
| 呈现                        | 卡片，复刻节点卡面 | **紧凑列表行**：名字 + 一张小缩略图 + 「被 N 镜引用」 |
| 职责                        | 看 + 改 + 新建     | **只做"找到"**：列出 · 搜索 · 定位                    |
| 点击                        | 选中 / 编辑        | **定位并选中画布上那张真卡**                          |
| 改名 / 换图 / 加音色 / 删除 | 两处都能做         | **只在画布上那张真卡做**                              |
| 新建                        | 匣尾 ＋新建        | 交给助手与画布级动作（`＋添加` 已在图标轨）           |

> **它不再是操作场所。** 一个对象只有一个可操作的地方，卡匣是它的索引。

#### 依据

CD 简报证据表里 LTX Studio `Elements` 面板的借鉴点，原文写的就是「一致性单位的**注册表** + 引用方法」——当时借了形没借意。
与北极星同向：助手负责建，用户主要在**找和审**。列表服务于找；卡面镜像不服务于任何事。

#### 硬约束（不能因为降级而丢）

一致性复用是画布相对 Studio 的核心价值（`domains/canvas.md` §6.3）。注册表必须仍能回答「这个项目有哪些身份」和「这个身份被哪几镜用了」，否则就是退化成散图堆。

#### 与 P0-A 合并做

两者碰的是同一件事：**身份的名字要成为系统里的一等信息**。P0-A 让助手拿到名字，注册表让用户按名字找 —— 一起做，不要分两次改同一处数据结构。

### 2.3 「重做」的语义（必须钉死）

> **保留节点、保留连线、保留提示词，只换 seed 重跑。**

不新建节点、不断连线 —— 否则用户重来三次画布上就多三个孤儿节点，正是「成分永不消失」那条不变量的反面。
「改提示词再来」= 重做 + 先开 prompt 编辑。两个动作，一套语义。
