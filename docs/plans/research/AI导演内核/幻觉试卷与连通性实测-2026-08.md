## 0. 结论

**减幻觉可做，但瓶颈不在模型、也不在"要不要加检索"，在"喂哪个源"。**

三个数字：

| 臂                                         | 幻觉率        | 得分  |
| ------------------------------------------ | ------------- | ----- |
| `research=false`（**现状默认**）           | 14.3%（2/14） | 10/14 |
| `research=true`（现有 Serper+Jina 粗管线） | 14.3%（2/14） | 11/14 |
| 切片 1 管线落地后                          | 待测          | 待测  |

**开检索没有降低幻觉率**——它换掉了幻觉的位置：多答对两题（C3 视觉元素、D2 图量），但把一题从"诚实弃权"变成了"自信编造"（C1 视频时长）。这恰好是任务包 §3.4「防幻觉五道闸」存在的理由：**光加检索会让模型半懂就敢说，必须配引用校验和 basis 四分类**。

而真正有说服力的对照是：两臂都答错的 A1（长离发色），我实测的三个专用源——萌百 `prop=categories`、danbooru 共现 tag、Fandom infobox——**全都直接给出正确答案**。不是模型不行，是没喂对源。这就是切片 1「IP 角色组连接器」的价值证明。

## 1. 连通性实测

25 项检查：**PASS 22 · WARN 1 · FAIL 1 · SKIP 1**。

| 探针           | 结果            | 一句话                                                       |
| -------------- | --------------- | ------------------------------------------------------------ |
| 萌娘百科       | 6/6 PASS        | 不按 UA、不按速率拦，**按 API 模块白名单**拦                 |
| MediaWiki 家族 | 2 PASS / 1 FAIL | 「一个连接器吃全族」**能力层不成立**；wiki.gg 本出口整站 401 |
| Jina 渲染 SPA  | 2/2 PASS        | 火山 24,949 字 / BytePlus 25,760 字，关键词全命中            |
| Danbooru       | 4/4 PASS        | 鸣潮角色 tag 全覆盖，且**建 tag 早于角色上线**               |
| Gemini YouTube | 4/4 PASS        | fileUri 直传可用；**成本可砍到 5%**                          |
| Serper         | 3/3 PASS        | 时间过滤 `tbs=qdr:w` 生效                                    |
| B站            | 1 PASS / 1 WARN | `view` 元数据四要素齐；`search` 裸调 6 次成 3 次             |
| DashScope      | SKIP            | 无 key（本仓 BYO-only），待 owner 提供后补验                 |

### 1.1 萌百不是「反爬强度」问题，是 API 模块白名单

任务包 §3.3 写「API 取正文，不爬页面」——方向对，但能取什么必须按模块列：

| 模块                            | 萌百                   | 用途                       |
| ------------------------------- | ---------------------- | -------------------------- |
| `action=opensearch`             | ✅                     | 角色名 → 页名              |
| `action=query&generator=search` | ✅                     | 全文搜索                   |
| `action=query&list=search`      | ❌ `action-notallowed` | 标准写法反而被封           |
| `prop=extracts`                 | ✅ 2775 字             | 正文                       |
| `prop=categories`               | ✅ 24 个               | **外观特征已是结构化标签** |
| `prop=pageimages`               | ✅ 1139×1654           | 立绘直出                   |
| `prop=revisions`                | ❌                     | **拿不到 wikitext**        |
| `action=parse`                  | ❌                     | 同上                       |
| `list=allpages`                 | ❌                     | 枚举被封                   |

对连接器的硬约束：

1. 搜索必须用 `opensearch` / `generator=search`，**不能用 `list=search`**——照抄 MediaWiki 官方文档会踩空。
2. **拿不到 wikitext**，想从 infobox 模板取「发色=粉」这种字段，萌百这条路走不通。
3. 但 **`prop=categories` 是更好的替代**：长离的 24 个分类里 `粉发 · 挑染 · 金瞳 · M形刘海 · 下双马尾 · 呆毛 · 开胸高领衫 · 分离袖子 · 露背 · 腿环 · 黑色过膝袜 · 高跟鞋` 已经是可直接进提示词的外观标签。**少一次 LLM 提取就少一处幻觉面。**
4. UA / 速率完全不设防（四种 UA 全 200；12 并发全 200，最慢 260ms）。礼仪式 UA 即可，不需要伪装浏览器。

### 1.2 「一个连接器吃全族」——传输层成立，能力层不成立

| 站          | `prop=extracts`          | `prop=revisions` | `action=parse` | 结论           |
| ----------- | ------------------------ | ---------------- | -------------- | -------------- |
| 维基百科 zh | ✅ 4563 字               | ✅ 38882 字      | ✅             | 全开           |
| 萌娘百科    | ✅ 2775 字               | ❌ 封            | ❌ 封          | 白名单式       |
| Fandom      | ❌ **未装 TextExtracts** | ✅ 2521 字       | ✅             | 必须降级       |
| wiki.gg     | ❌ 401                   | ❌ 401           | ❌ 401         | **整站不可达** |

**修正 §3.3**：`MediaWikiConnector` 不能只写一条取正文的路，必须带**按站能力表 + 降级链**（`extracts` → `revisions`/`parse` → 放弃）。另外两个坑：

- **MediaWiki 的「拒绝」是 HTTP 200 + body 里的 `error.code`**，不是 4xx。只看状态码的错误处理会把「被封」当成「查到了空结果」——正是 §3.4 要区分的 `no_evidence` vs `failed` 被混淆的典型。
- **页名要按站解析**：zh.wikipedia 上「鸣潮」不存在，条目是繁体「鳴潮」。

**建议把 wiki.gg 移出首版源组**：本出口 API 401、页面 403（Cloudflare 挑战），换浏览器 UA 无效。为它写第四条降级路不划算。

### 1.3 Danbooru：覆盖不滞后，反而早于上线

鸣潮 11 个角色 tag **全覆盖**。

| 角色       | tag 建于   | 图量 |

| jinhsi     | 2024-05-17 | 1855 |
| changli    | 2024-05-18 | 3644 |
| camellya   | 2024-05-19 | 2321 |
| cartethyia | 2025-01-12 | 2368 |

## 2. 视频链路（对应任务包 §4.2 / §4.3）

### 2.1 Gemini YouTube fileUri 可用，且成本杠杆比「确认卡」更管用

18m41s 公开视频直传成功（免下载零存储），回答准确（时长 ✓、运镜"固定镜头无推拉摇移" ✓、视觉元素逐条对得上）。

| 配置                         | VIDEO token | 相对全片 |
| ---------------------------- | ----------- | -------- |
| 全片 18m41s（默认帧率）      | 101,923     | 100%     |
| `videoMetadata` 裁 0:00–1:00 | 5,460       | **5%**   |
| `videoMetadata.fps=0.2` 全片 | 42,787      | 42%      |
| 全片 1h00m02s                | 326,504     | ——       |

**单价 ≈ 5,450 VIDEO token / 分钟，随时长线性**（18m41s 与 1h 两点算出来一致）。

**这改变 §4.3「超阈值确认」的设计**：与其超过 N 分钟就弹确认卡打断用户，不如**先降级再问**——一致性审片本来就不需要满帧满长，裁片段（5%）或降帧（42%）够用。确认卡留给"用户明确要求全片满帧分析运镜"。

### 2.2 两个实现层的坑

1. **thinking token 从 `maxOutputTokens` 里扣**。给 800 实测得到 `thoughtsTokenCount=765` / 正文 31 字 / `finishReason=MAX_TOKENS`——表现是"视频分析回了半句就没了"，极易误判成模型能力问题。视频分析的输出预算要给足（实测 3000 够）。
2. **视频不可访问回 `403 PERMISSION_DENIED`，不是 404**。直译给用户就成了"你的 API key 没权限"，会把人引去查 key。必须映射成"这个视频不可访问（可能已删除或非公开）"。

### 2.3 B站：只出元数据这条边界对，但搜索要兜底

- `x/web-interface/view?bvid=` ✅ 稳定，标题/UP主/时长/封面四要素齐——元数据卡够用。
- `x/web-interface/search/type` ⚠ 裸调 6 次成 3 次（其余 HTTP 412 风控页）。**搜索入口必须带重试或退到 Serper `site:bilibili.com`**，否则一半概率静默失败。

## 3. 幻觉试卷

14 题 · 4 组。题库 `scripts/hallucination-exam.questions.json`，每题的标准答案带 `source` 字段指向取证来源。

**两臂设计**：现状 `researchEnabled` 默认 **false**（`PromptAssistantPanel.tsx:145` / `StudioNodeAssistantDock.tsx:209`），所以基线跑两臂——`research=false` 是用户实际体验到的现状，`research=true` 是现有粗管线已经能买到什么。切片 1 落地后跑第三次。

**跑法**：claude-in-chrome 驱动 owner 登录态，程序化 POST `localhost:3000/api/prompt/assistant`（`mode=general` · `responseLanguage=chinese` · 并发 3）。28 次调用零错误。

### 3.2 三个值得记住的现象

**① 检索让模型从"诚实"变"自信编造"（C1）。** 无检索时诚实说"我访问不了这个链接"；开检索后 Serper 摘要给了视频标题，模型就自信地报出"19 分 13 秒"——真值 18 分 40 秒（YouTube `lengthSeconds=1120` 独立取证）。**摘要里根本没有时长，模型是补出来的。** 这就是 §3.4「引用必须真实」那道闸要拦的东西：没有证据支撑的论断不该被放行。

**② 带对冲的幻觉不该被豁免（D2）。** `research=false` 先声明"我无法实时联网获取"，然后仍给出"大约 1,500 到 2,500 张"——真值 3,644。**声明不确定不能豁免编造具体数字。** 判分器把这类记为幻觉而非弃权，靠的是人工裁定（记在答卷 `humanAdjudication` 字段里，重跑可比）。

**③ LoRA 生态题 5/5 全对，两臂都是。** 模型对 Civitai/HF 这类公开生态事实的记忆相当可靠。**说明检索管线不必平均用力**——IP 角色和时效类才是幻觉高发区，通用生态知识不是。

### 3.3 出题勘误（本身是条教训）

初版 A3 把「迅刀」列进 `mustNotContain`——因为我看 Fandom infobox 写 `weapon = Sword`，就想当然映射成「单手剑」。实际**鸣潮中文版把 Sword 就叫「迅刀」**（萌百正文：「丹煌离火——长离(热熔·迅刀)」）。助手答对了，是题错了。

**教训**：英文源的字段必须回中文源核对本地化译名，否则连接器会把正确答案判成错的。切片 1 的 IP 角色组同时吃萌百（中）和 Fandom（英），这个坑一定会再遇到。

判分口径在首跑后修正过一次（剥 markdown 强调符 / 补弃权词 / B3 去掉误伤的 Apache / B5 补同义词 / 幻觉定义改为"自信错误"而非"任何答偏"）。修正针对断言设计缺陷，不是按答案调分；**此版为后续重跑的冻结基线**，细节记在题库的 `rubricRevision` 字段。
