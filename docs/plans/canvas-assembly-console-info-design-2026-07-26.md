## 0 · 为什么先做这个

组装台是画布上唯一真正下单的对象，而且是**今天正在漏的地方**：`GEMINI_OMNI_FLASH` 已 `available: true`，画布视频节点吃 `getAvailableVideoModels()` —— 用户现在就能选中一个没有时长参数的模型，界面却还挂着时长滑杆。

它还要同时服务三个场景（见 §2），所以不先钉死它，后面每个场景都要重画一次。

## 1 · 组装台必须回答的四个问题

任何场景、任何模型形态，这四问**都必须有答案**。信息密度可以变，答案不能缺 —— 这是密度分级的判据（不是「card 档少放点」，而是「card 档用最省的形式答完四问」）。

| #   | 问题                 | 为什么它是必答                                                     |
| --- | -------------------- | ------------------------------------------------------------------ |
| 1   | **这次会送出去什么** | 袋型合同是隐式装配（上游边收割），用户没有直接编辑 payload 的地方  |
| 2   | **还差什么**         | 形态 A 强制 `image_urls` 至少 1 张，缺了直接 provider 报错         |
| 3   | **上限还剩多少**     | 跨模态 ≤12 的闸今天**静默砍图**（`video-request-builders.ts:462`） |
| 4   | **下一步点哪**       | 域性格锚点就是这句                                                 |

## 2 · 三个场景（外面有没有画布）

| 场景                  | 何时出现                           | 组装台形态                           |
| --------------------- | ---------------------------------- | ------------------------------------ |
| **S0 单卡模式**       | 起手 / 移动端 / 「基础生成」那条路 | 全屏一张卡，无画布、无连线、无班底架 |
| **S1 画布 card 档**   | 卡在画布上，未展开                 | 紧凑；与其他节点并列可比             |
| **S2 画布 detail 档** | 展开                               | 信息完整                             |

S0 与 S2 的**信息量相同**，差别只在外面有没有画布 —— 所以本文只设计两档密度，S0 复用 S2 的内容。

⚠ S2 是「卡原地长大」还是「独立详情面板」尚未拍板（现状是后者，`node-detail/VideoDetailBody.tsx`）。本文的信息设计对两者都成立，遮挡策略等拍板后再补。

## 3 · 四问在两档密度里的表达

| 问题       | card 档                                                | detail 档 / 单卡                                                 |
| ---------- | ------------------------------------------------------ | ---------------------------------------------------------------- |
| 送什么     | **容量条**：`6/9 图 · 1/3 音 · 0/3 视`，`tabular-nums` | 成分清单：缩略图 + 名字 + `@token` + 来源节点                    |
| 还差什么   | 缺必填时容量条**整行让位**给 `还差：至少 1 张图`       | 同左，且指出该连哪类节点                                         |
| 上限剩多少 | 有效上限直接进数字（`6/6 图`）+ 一个可点的 `!`         | 一行原因：`3 段参考视频 + 3 条音色占用 6 个额度，图片上限 9 → 6` |
| 下一步     | 唯一主动作按钮                                         | 同左                                                             |

### 3.1 card 档的一处替换（净改进，不增行数）

今天 card 档三行 = 模型按钮 / 参数摘要（`720p · 12s · 16:9`） / 成分类型 chips（只说有哪几类，不说几件）。

改为：模型按钮 / **容量条** / **参数摘要 chip**。

理由：参数是「我设的」，我知道；容量是「系统算的」，我不知道。卡上寸土寸金，应该给我不知道的那件事。容量条严格强于类型 chips —— 它同时答了第 1、2、3 问。

**参数摘要 chip**（owner 2026-07-26 参考界面驱动）：形如 `⛶ 16:9 / 12s / 720p ▾`，**既是状态显示又是入口** —— 点开就是参数浮层。取代 v1 设想的「次级小字」，因为小字是死的，chip 一行干两件事。detail 档与单卡模式同样用它，参数不再各自占一栏。

### 3.2 编号角标与「入选」的真实规则

成分缩略图右上角印**发送序号**：这个数字就是 `@ImageN` / `@AudioN` / `@VideoN` 里的 N，也是 payload 数组里的位置。主标签用真名（`@林皎`）给人读，角标序号给模型读 —— 序号本来就存在于 payload 里，只是从未显示过。

⚠ **但「谁会被发送」不由顺序决定，由 `@` 提及决定**（实读 `filterReferencedImages`）：

| 状态                     | 条件                                 | 卡上表达                       |
| ------------------------ | ------------------------------------ | ------------------------------ |
| **会发送**               | 已连线 **且** prompt 里 `@` 提到了它 | 正常 + 序号角标                |
| **不会发送**             | 已连线但 prompt 没提到               | 明确标灰 + 「未被提及」        |
| **全部发送**（迁移护栏） | prompt **一个已知名字都没提到**      | 整条容量条切到"全发"模式并说明 |

**迁移护栏是一个隐藏的悬崖**：用户打下第一个 `@` 的瞬间，其余所有已连线的图会从"会发"整体翻转成"不会发"。这是代码里为了不炸旧项目的有意设计（`filterReferencedImages` 的迁移红线），但今天完全不可见。**设计必须把这次翻转显式化** —— 在用户输入第一个 `@` 时给出一次性提示，说明规则已从"全发"切到"只发点名的"。

⚠ 原 v1 写的「顺序即优先级、让清单可拖动」**已作废** —— 用户真正的控制杆是 `@` 提及，不是拖拽顺序。顺序仍是收割顺序，不可手改。

### 3.3 任务模式 tab（**2026-07-26 推翻原判，改为采纳**）

原判：「模式 tab 与模型是两个独立选择器，会产生无效组合，拒绝」。
**这个前提是错的。** owner 提供的多模型截图显示 **tab 集合本身由模型声明**：

| 参考站模型        | tab 集合                                                |
| ----------------- | ------------------------------------------------------- |
| seedance 2.0-fast | 文生视频 / 图生视频 / 首尾帧 / 全能参考 / 视频编辑（5） |
| Omni Flash        | 文生视频 / 图生视频 / 参考生视频 / 视频编辑（4）        |
| Happyhorse 1.1    | 同上（4）                                               |
| Kling O1          | 文生视频 / 首尾帧 / 全能参考（3）                       |
| Kling 2.5         | 文生视频 / 图生视频（2）                                |

是「模型 → 模式集合 → 在集合内选一个」的**两级派生**，不是两个独立轴 —— 无效组合根本不会出现。而且它比原设想更准：**一个模型支持的是一组模式，不是一个形态**。

#### 核心二分（本轮最重要的结构结论）

> **模式决定槽轨，模型决定参数。**

| 轴                  | 谁选       | 影响                                                                       |
| ------------------- | ---------- | -------------------------------------------------------------------------- |
| **任务模式**（tab） | 用户显式点 | 槽轨结构：有没有图槽、几个、有没有音/视槽                                  |
| **模型**（下拉）    | 用户显式选 | 时长 / 分辨率 / 画幅 / seed / prompt 字数上限 / 单价，以及**可选模式集合** |

#### 这直接修掉两件事

1. **mode-by-input 退役。** 今天文生/图生看 `getMode`（`referenceImage && i2vModelId`）、全能参考看 `hasReferenceInputs`（`resolveEffectiveVideoModelOption`）—— 全是输入倒推，用户点不到。改成显式 tab 后，§5.2 不变量 4「形态跃迁必须有声」自动成立：**跃迁就是用户点的那一下**。
2. **§5.3 ⑴（UI 用 stale id）消失。** 模式显式后，模型 id 由 `(品牌, 档位, 供应商, 模式)` 四元组确定性解析，不再存在"提交时才知道跑哪个 id"。

#### 禁用槽的表达（参考站做对了一半）

Kling 2.5 那张：图槽 2/3/4 与视频槽都打 `⊘` 但**保留在原位**，不是消失。这正是 §5.2 第 3 条要的形态。
**我们比它多一句原因** —— 它只给 `⊘` 不给理由。

## 4 · 任务模式 × 模型

### 4.1 六种任务模式 —— 我们今天支持哪些（实读）

| 模式           | 送什么                         | 我们支持吗  | 代码落点                                                                                   |
| -------------- | ------------------------------ | ----------- | ------------------------------------------------------------------------------------------ |
| **文生视频**   | 只有 prompt                    | ✅          | `getMode` 无 `referenceImage` → `text-to-video`                                            |
| **图生视频**   | prompt + 1 张首帧              | ✅          | `referenceImage && i2vModelId` → i2v 端点；Kling 用 `start_image_url`                      |
| **首尾帧**     | prompt + 首帧 + 尾帧           | ❌ **没有** | `GenerateVideoRequest` 无尾帧字段（`lastFrameUrl` 只存在于长视频 pipeline，UI 侧零消费者） |
| **全能参考**   | prompt + 图 ≤9 + 音 ≤3 + 视 ≤3 | ✅          | `_REFERENCE` id + `buildSeedanceReference`                                                 |
| **参考生视频** | prompt + 多图（无音 / 无视）   | ✅          | Omni Flash 的 Interactions API 内容数组                                                    |
| **视频编辑**   | prompt + 源视频                | ❌ **没有** | 无 video-to-video builder                                                                  |

### 4.2 我们的模型 → 模式集合

| 模型                                         | 可选模式                                                                       |
| -------------------------------------------- | ------------------------------------------------------------------------------ |
| Seedance 2.0 / Fast（fal + 火山 共 4 组 id） | 文生视频 · 图生视频 · **全能参考**                                             |
| Kling V3 Pro                                 | 文生视频 · 图生视频                                                            |
| HappyHorse 1.0                               | 文生视频 · 图生视频                                                            |
| Gemini Omni Flash                            | 文生视频 · **参考生视频**（它的 i2v 就是多图内容数组，没有"单张首帧"这个概念） |

⚠ 「首尾帧」与「视频编辑」两个 tab **本轮不出现** —— 能力不存在就不画 tab，这是"不伪装 provider 能力"的直接应用。它们是独立的接入任务。

### 4.3 模型的参数矩阵（与模式无关）

|        | **A 多参考聚合**                                             | **B 单张首帧**                                                | **C 内容数组**                                                          |
| ------ | ------------------------------------------------------------ | ------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 模型   | Seedance 2.0 Reference / Fast Reference（fal + 火山共 4 id） | Seedance 2.0 / Fast · Kling V3 Pro · HappyHorse 1.0 · LTX 2.3 | Gemini Omni Flash                                                       |
| 槽轨   | **三轨**：图 ≤9（**必填 ≥1**） / 音 ≤3 / 视 ≤3               | **一轨**：首帧 1 张（可空 = 纯文生）                          | **一轨**：参考图 N 张（无显式上限；有 = i2v，无 = t2v，adapter 自动切） |
| 时长   | 滑杆 4–15 + `auto` 档                                        | 各自枚举（Kling / HH 3–15，LTX 6/8/10，Seedance 4–15 + auto） | **整条消失** + 一行说明                                                 |
| 分辨率 | 480 / 720 / 1080p（fast 无 1080p）                           | 各自枚举                                                      | **降为只读事实**「720p」，不是可选控件                                  |
| 画幅   | 5 格                                                         | 3–5 格                                                        | **2 格**（16:9 / 9:16）                                                 |
| seed   | 有                                                           | 只 Seedance 基础档有                                          | 无                                                                      |
| 结果卡 | 显示尺寸                                                     | 显示尺寸                                                      | **不显示像素尺寸**，只显示画幅                                          |

最后一格的理由：形态 C 竖屏时轮询回报仍是 `1280x720`（`gemini.adapter.ts` 注释自认拿不到真实尺寸）。显示一个已知错误的数字比不显示更糟。

## 5 · 换形态状态机（本设计最容易翻车处）

### 5.0 两个显式轴，三类转移

采纳任务模式 tab（§3.3）后，原来的「六个方向」塌成**三类转移**，且全部由用户显式发起 —— 没有一次是系统偷偷换的。

⚠ **mode-by-input 正式退役。** 今天的隐式换档（`getMode` 看 `referenceImage`、`resolveEffectiveVideoModelOption` 看 `hasReferenceInputs`）由显式 tab 取代。模型 id 改由 `(品牌, 档位, 供应商, 模式)` 四元组确定性解析。

### 5.1 三类转移

#### ① 切模式（同一模型内）

槽轨结构变，参数全不变。

| 从 → 到         | 槽轨                           | 必须做的事                                                              |
| --------------- | ------------------------------ | ----------------------------------------------------------------------- |
| 文生 → 图生     | 无槽 → 1 图槽                  | 若上游已有图，自动填入第一张并**明示是哪一张**，允许改选                |
| 图生 → 全能参考 | 1 图槽 → 图 ≤9 / 音 ≤3 / 视 ≤3 | 已连线但之前发不出去的成分**立刻变成可发送**，容量条 `1/1` → `n/9`      |
| 全能参考 → 图生 | 三轨 → 1 图槽                  | 多出来的图、全部音色与参考视频标 `⊘` + 一句原因，**成分不删、连线不断** |
| 任意 → 文生     | 全部槽 → 无                    | 所有成分标 `⊘`「当前模式不发送任何参考」                                |

#### ② 切模型，当前模式仍在新模型的集合里

模式不变，只有参数变：时长 / 分辨率 / 画幅 / seed / prompt 字数上限 / 单价。走「就近取 + 标一次」。

#### ③ 切模型，当前模式不在新集合里

模式沿**降级阶梯**落到最近的一个，并标一次说明：

> 全能参考 → 参考生视频 → 图生视频 → 文生视频

例：在「全能参考」下换到 Kling V3 Pro（只有 文生 / 图生）→ 落到「图生视频」，提示「Kling V3 Pro 不支持全能参考，已切到图生视频；音色与参考视频不会发送」。成分一件不删。

### 5.2 四条不变量

1. **成分不删。** 任何降级只改"发不发"，不改"在不在"。连线保留，换回来立刻恢复。
   理由：成分是用户一件件搭的，模型是随时会换的选择 —— 选模型不能破坏装配。
2. **参数就近取 + 标一次。** 12s 换到 LTX（只 6/8/10）→ 取 10 并标「12s → 10s（模型上限）」。不静默改，也不弹窗拦。
3. **失效槽给原因，不给空壳。** 音轨在 B / C 上不是置灰空槽，是一行收起的说明：「当前模型不接受音色参考 · 接回 Reference 档可用」。占一行，不占一轨。
4. **形态跃迁必须有声。** ✅ **由 §3.3 的显式 tab 自动满足** —— 跃迁就是用户点的那一下。原先要为无声的自动换档补提示，现在不需要了；只有 ③ 的降级需要标一次。

### 5.3 状态机必须同时修掉的四个现存缺陷（实读，非推测）

| #   | 缺陷                                                                                | 证据                                                                                                                                                                                                              | 后果                                                                                                                                          |
| --- | ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| ⑴   | **UI 能力门用旧 id，发送用新 id** —— ✅ **由 §3.3 显式 tab 从根上消除**，无需单独修 | `use-video-composer.ts:596` 的 autospawn effect 首行 `if (data.model) return` —— `hasReferenceInputs` 在依赖数组里却永不触发重解析；而 `StudioNodeWorkbench.tsx:1442` 提交时才 `resolveEffectiveVideoModelOption` | 选 base Seedance 再接参考边：UI 按 base 算 → 上限显示 **1**（实际发 9）、音色槽显示"自动生成"（实际**会**发音色参考）                         |
| ⑵   | **火山 reference 档没有模型级上限覆盖**                                             | `provider-capabilities.ts` 只给 fal 的 `SEEDANCE_20_REFERENCE` / `_FAST_REFERENCE` 写了 `maxReferenceImages: 9`；火山两个 reference id 落到 adapter 级默认 **14**（那是 Seedream 图片模型的值）                   | 走火山线时 UI 会说上限 14，而 provider 实际是 9                                                                                               |
| ⑶   | **装配顺序把「点名」放在「砍容量」之后**                                            | `StudioNodeWorkbench.tsx:1240` 先 `assembleReferenceImagePayload`（按收割顺序砍到上限），`:1291` 才 `filterReferencedImages`（按 `@` 提及过滤）                                                                   | 连 12 张、只 `@` 第 11 张 → 第 11 张在砍容量时已出局 → `referencedNames` 为空 → **迁移护栏触发 → 发了前 9 张全部**，而不是你点名的那一张      |
| ⑷   | **跨模态 ≤12 的二次砍图 UI 完全不知情**                                             | `video-request-builders.ts:462` `maxImages = 12 - videos - audios`，在 adapter 内二次 slice                                                                                                                       | 3 段参考视频 + 3 条音色时，客户端认为上限仍是 9，实际只发 6。**这才是真正静默的那一刀** —— 客户端 9 的上限是有 `overflow` 透明机制的（见 §6） |

⑶ 的最小修法是**调换两步顺序**（先按 `@` 过滤，再砍容量），不需要新概念。⑴ 的修法是让 composer 也走 `resolveEffectiveVideoModelOption`。两条都属于实现期，但设计必须按"修好之后"的行为画，否则状态图会把 bug 固化成规范。

## 6 · 有效上限与被拒成分

只在形态 A 存在。代码事实：`maxImages = Math.max(1, 12 - videoUrls.length - audioUrls.length)`，然后 `imageRefs.slice(0, Math.min(9, maxImages))`。

**两级上限，只有第二级是静默的**：

| 级     | 值                                                | 在哪算                                                       | 今天透明吗                                                                                                                                                            |
| ------ | ------------------------------------------------- | ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 客户端 | `getMaxReferenceImages()` = 9（fal reference 档） | `assembleReferenceImagePayload` 返回 `{imageUrls, overflow}` | ✅ **已有透明机制** —— `overflow` 逐条列出被砍的 URL，`node-video-send-preview.ts` 就是为了"显示实际会发什么"而存在，`ReferenceManagerPanel` 已有 `overCapacity` 分支 |
| 服务端 | `12 - videos - audios`                            | adapter 内 `buildSeedanceReference` 二次 slice               | ❌ **完全静默**（§5.3 ⑷）                                                                                                                                             |

设计三条：

1. **容量条印有效上限，不印死 9。** 把服务端那级的算式提到客户端一起算：视频 + 音频合计 ≤3 时上限仍是 9；超过时数字自己变（3 视 + 3 音 → `n/6 图`），旁边挂可点的 `!`，展开一行原因。
2. **超出的成分不消失。** 在成分清单里保留，标灰 + 「本次不会发送」。`overflow` 已经把这份名单准备好了，设计只需把它铺出来。
3. **先点名、再砍容量。** 见 §5.3 ⑶ —— 今天顺序反了，导致点名的图可能先被容量砍掉。修正后，`@` 提及的成分享有优先保留权，这才让"点名"成为真正的控制杆。
